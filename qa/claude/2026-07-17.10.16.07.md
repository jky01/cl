## What's preregistered

- **Language**: typed sequence transduction. old {copy, inc, shift}; NEW stateful `csum_reset`
  (cumulative sum with conditional RESET — depends on the whole segment since the last reset, a short
  program, not a builtin/rename); interference-capable `rmax_reset` (same stateful+reset structure so
  phase 3 can damage phase-2 shared params). Compositions B(A(x)); held-out old→new (`inc+csum_reset`)
  and new→old (`csum_reset+shift`).
- **OOD axis = sequence length** (train [3,12], test [16,40]) — the direct analog of the toy's
  "extrapolate the rule beyond the training range"; tests learned recurrence vs memorized fixed-length.
- **7 shortcut classes** enumerated (fixed-length, position-only, local-window, reset-near-boundary,
  token-identity, template/delimiter, task-order).
- **5 environments as targeted interventions** (E0/E_len/E_reset/E_alpha/E_tmpl), each breaking ≥1
  named shortcut while preserving the program; marginals balanced; env labels train-only, never at
  inference. Held-out = familiar interventions in unseen combinations + one preregistered nuisance.
- **Minimal-environment identifiability study**: per environment subset, report the equivalence class
  of programs still consistent (not just accuracy); find the smallest env set that makes `csum_reset`
  uniquely identifiable.
- **4-phase protocol** (no raw replay): base+old → discover csum_reset (multi-env) + consolidate →
  learn interference-capable rmax_reset (shared params) → eval old/new/OOD/compositions. Diagnostic:
  discovered-vs-supplied diverging before vs after phase 3 localizes acquisition/consolidation vs
  later-interference.
- **6 arms** (discovered+sufficient / discovered+insufficient / supplied+same-consolidation /
  flexible-no-invariance / protected-module upper control / joint upper reference).
- **8-axis acceptance table** (knowledge-into-weights / rule-acquisition / retention / cross-integration
  / growth-necessity at matched active-inference-compute / compute-advantage / no-memory-inference /
  no-joint-retrain), all required, ID accuracy alone insufficient.

Generator smoke passed: ops+reset correct (`csum_reset([3,5,RESET,2,4,7])=[3,8,0,2,6,13]`), per-env

## Questions before I build the model/harness

1. **Model + compute**: I plan a small decoder-only transformer (≈2–4 layers, d≈128–256), char/token
   level, trained on the local RTX 2070 (8GB) — a micro-language this size should fit without a pod. Do
   you want a specific architectural constraint to make the "growth necessity" axis clean (e.g. a fixed
   trunk + a slot where a new operator module can be grown/consolidated), or should the first run be a
   plain shared transformer so we first see whether even a monolith can be pushed through the chain
   before adding growth machinery? I lean plain-shared-first (establish the identifiability/retention
   result), then add the growth/module axis as the second architecture.
2. **Discovery mechanism at LM scale**: in the toy, "discovery" was exhaustive support search. At LM
   scale there's no clean support to enumerate. I plan to operationalize "discovery from multi-env
   evidence" as **training the shared model on the multi-environment mixture with a worst-environment
   (invariance) objective**, and test whether that identifies the recurrence (OOD-generalizes) vs the
   single-env/ERM baseline that should shortcut. Is worst-env/IRM-style the right first operationalization,
   or would you start with plain multi-env ERM and treat the invariance penalty as arm 2? I lean plain
   multi-env ERM first (does mixture alone identify?), invariance penalty second.
3. **Consolidation without replay**: phase-2→3 "no raw replay" — I'll self-distill the old ops over
   model-generated inputs. Acceptable as the no-joint-retrain mechanism, or do you want a bounded
   training-time summary instead?
