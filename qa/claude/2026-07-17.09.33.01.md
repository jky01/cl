## Diagnosis: I charged modules, not edges

The surviving product is `z = (A·x)·(B·x)` with `A,B` linear over the FULL input `x=[n/K, bits]`. So
even a single product unit is a free quadratic form in `[n/K, bits]`, and it exploits the BITS to fit
the training range — which does not extrapolate the magnitude. Module-level L0 shrank the operator
count but left each operator's INPUT EDGES dense, so "one product unit" is still `(mix of x,bits)·(mix
of x,bits)`, not clean `x·x`. You explicitly said `L_structure` must charge "active operators, edges,
and modules"; this first version charged operators/modules only. That gap is exactly the residual
failure.

## Proposed edge-level fix (want your review before building)

Add hard-concrete gates on the INPUT EDGES of each product's two linear maps `A, B` (per-coordinate),
charged under the same accounting: `L_structure = Σ operator gates + λ_e · Σ edge gates`. Then the
cheapest graph that fits square is "one product; each factor reads only the `n/K` coordinate" = `x·x`,
which extrapolates. Bits become expensive to include, so the shortcut is penalized.

Design details I plan, flag any you'd change:
1. Edge gates on `A` and `B` (shape [din, P] each) via hard-concrete; L0-charge the number of active
   (input-coordinate → product) edges, summed with the operator gates under one β.
2. Keep γ (coefficient precision) so magnitude can't be made free.
3. Preregister β, λ_e, γ and seeds on ID/prequential criteria only; OOD shells stay sealed until after.
4. Graph-recovery readout: report not just active operator counts but the active INPUT SET of the
   surviving product(s) — success = it reads only `{n/K}`, not bits.
5. Keep the four-arm ladder (none / weight-L1 / operator-only-L0 / operator+edge-L0) so the edge term's
   marginal effect is isolated.
