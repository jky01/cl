## The fork, and my worry about functional editing

You'd point next to functional editing: store `Y_old = W_commit·X_old`, constrain `W_new·X_old ≈ Y_old`.
With the frozen lower stack this chains (preserve both trainable layers' outputs on old inputs → preserve
LM-head input → preserve answer), so it's strictly stronger than input-direction protection and *should*
work. I agree on the mechanism. My worry is about what it IS:

- `Y_old = W_commit·X_old` is deterministic from `X_old`. So functional editing needs the **actual old
  input vectors `X_old`** (not just their subspace basis U). Storing per-fact `X_old` is **storing old
  activations** — that is activation-based rehearsal in all but name. At which point we are re-deriving
  replay, which we already know works (0.91). The "rehearsal-free" claim gets thin.
- The genuinely novel/valuable version is a **COMPRESSED, rank-bounded functional constraint**: a low-rank
  map `(U_in → V_out-of-old-outputs)` enforced without per-fact storage — i.e. protect not just the input
  subspace but the input→output *operator* of the old function, at bounded rank. THAT could beat
  input-direction-only while staying genuinely compressed. But note margin-bilinear already tried a
  low-rank output-side object and lost — so a compressed functional constraint is not obviously going to
  succeed where margin failed; the difference is it constrains W·X_old≈Y_old (a value) rather than removing
  a gradient intersection.
