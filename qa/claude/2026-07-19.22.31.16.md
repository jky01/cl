## The routing problem — why growth here is NOT continual2

In continual2 the two operators were distinguished by an explicit COMMAND TOKEN in the input, so an exact
mask (route=1 iff cmd==rmax) gave byte-identical retention for free. Here A and B are BOTH arithmetic; a
sequence's only identity is its delta, which must be INFERRED from the prefix, and "is this delta in set A
or set B" is an arbitrary membership predicate over inferred deltas. So:
- There is no command token to mask on. Prefix-only routing must (a) infer the delta and (b) decide which
  frozen module owns it — and the router itself is trained sequentially, so it is the new forgetting
  bottleneck you warned about.
- An always-on B-adapter over a frozen A-trunk will hit the continual2 output-override trap on A-rules
  (the B-branch adds B-shaped residuals over A inputs).

So the clean command-masked-growth trick does not transfer. This is a real design fork and I want your
read before I spend the run. Options I see:

1. **Delta-inferred discrete router**: a small head reads the prefix, predicts the delta (or a hash/bucket
   of it), and routes to the module whose training deltas cover that bucket. Retention of A becomes exact
   iff the router sends A-deltas to the frozen A-module. But the router is trained on A then B and can
   forget A-routing; and held-out deltas have no owner. Feels like it just moves the forgetting into the
   router.

2. **Prefix-conditioned (not discrete-routed) single module**: condition one shared adapter on the
   inferred delta (a FiLM-style modulation from a prefix summary). This is really "learn the general rule
   parameterised by delta" — i.e. it only works if we first solve the held-out generalization we currently
   can't. So it couples growth to the unsolved rule-induction problem.

3. **Reframe the task so routing is legitimate and prefix-computable**: make the two phases STRUCTURALLY
   different (e.g. phase A = arithmetic / order-1, phase B = quadratic / order-2) rather than two arbitrary
   delta subsets of the same family. Then the "which module" decision is inferable from the prefix by a
   real, generalizable feature (is the 2nd difference zero?), routing is not an arbitrary memorized
   partition, and retention-of-a-general-behavior is meaningful. This also matches your point that
   arithmetic→quadratic is the stronger STRUCTURAL-acquisition test, and order-2 is now learnable at p=23.
   I lean strongly toward this: it turns routing from "memorize which deltas are A" into "detect the
   recurrence order from the prefix", which is a genuine, generalizable computation.

4. **No-routing consolidation instead of growth**: skip modular routing entirely and test whether a
   REPLAY-FREE consolidation (self-distill the A-model over A-style prefixes into the post-B model) retains
   A — i.e. attack interference directly rather than quarantine it. This is closer to the project's
   knowledge-INTO-shared-weights goal than module quarantine.

My plan unless you object: adopt (3) as the growth/retention testbed (arith phase A → quad phase B, prefix-
detectable order => legitimate prefix-inferred routing), run the fixed-capacity baseline there first
(does quad acquisition erase arith?), then a growth arm routed on the prefix-detected order, AND in
parallel a consolidation arm (4) as the shared-weights alternative — reporting instance retention, new
acquisition, added params, and active FLOPs. Keep (1) only as a control to show arbitrary-partition
routing is not what makes it work. Push back if you think the same-family A/B partition must be solved on
its own terms, or if delta-bucket routing (1) is a more honest first growth test than switching to the
order-structured split.
