## What I built (`run_keytie`, dispatch `keytie_<mode>`)

- Fixed-size top-GROW (no growth), scaffold-teacher answer loss (CE+KL, identical to `run_nswrite` "none" =
  `naive_fixed`) + the same base/neutral KL anchor. So the ONLY delta vs `naive_fixed` is the key-tie term.
- **Key-tie:** each step, pool the current model's `kstem(f)` rep and pull it toward that stem's
  **frozen-base** pooled rep. `anchor_mode`: `base` (real), `random` (base rep shuffled across facts —
  matched-compute mismatched-target control), `none` (== naive_fixed sanity).
- Rehearsal-free by your line: anchor for a fact = its OWN kstem + frozen base; no old prompts/answers/
  logits/acts/targets in later writes; single dense checkpoint; no inference key bank.
- Headline metric added to `agg`: `old_seen_final` / `old_para_final` over streams 0..R-2.

## Three calls I want your read on

1. **Cosine vs MSE for the tie.** I defaulted to **cosine** (`1 - cos(cur, base_kstem)`) because raw MSE on
   896-dim fp32 hidden states is scale-sensitive and lam is hard to set; cosine pins the key *direction*
   (retrieval identity) while letting magnitude float, and lam=1.0 is commensurate with the O(1) CE/KL terms.
   Concern: cosine ignores magnitude, and if the answer write mostly changes the rep's norm, cosine won't
   resist it. `BK_KT_METRIC=mse` is available. Which do you want as the primary arm?

2. **Which stems to tie.** You listed kstem(f), p_seen(f), p_para(f). I tie **kstem only** for the first cut
   — it's the pure retrieval key with no answer token, so anchoring it can't fight answer learning, giving
   the cleanest "anchor the key, learn only the value" test. Tying p_seen/p_para pooled would anchor more of
   the fact but risks fighting the write. I lean kstem-only first, add `BK_KT_STEMS=all` as a follow-up if it
   doesn't move retention. Agree, or do you want all-three from the start?

3. **Controls.** I have `keytie_random` (mismatched anchor, same compute) as the key control — if `base`
   beats `random`, the gain is real anchoring, not the extra loss/forward. Is that sufficient, or do you also
   want the explicit equal-token-budget *unanchored* arm you mentioned? I think `random` already matches
   compute AND forward-count exactly (same kstem forward, just wrong target), so it's a strictly better
   control than an unanchored-repetition arm. Push back if you disagree.
