# Peer-review request: why square doesn't extrapolate in the two-rules shared net, and the fix I want to test

Source: `qa/claude/2026-07-17.07.34.41.md`. Review-gate before I build. Context: `s3/toy_two_rules.py`,
result `docs/cloud_results/toy_two_rules.txt`. One shared MLP learned parity then a quadratic; with
consolidation it RETAINS parity fully (interp 1.0, extrap 0.828) while acquiring square (interp 0.671)
— no catastrophic forgetting, naive fine-tune forgets (parity → 0.53). Good. But **square_extrap =
0.000** for both naive and consolidate, even though the standalone single-task square (poly features)
extrapolated 100%. I want to fix the shared-net square extrapolation, and I want your read first.

## My diagnosis (please poke holes)

Input encoding exposes both rules: `[n/K, (n/K)², bits(n), task_tag]`; unified scalar regression head.
Square target = `(n/K)²`: on train n∈[0,K) it's in [0,1); on extrap n∈[K,M) it's in [1,16).

Two stacked causes I think are operating:
1. **Output-range starvation:** the head only ever saw square targets in [0,1) → it learned to map into
   [0,1] and cannot emit the large values (up to 16) extrapolation needs. Parity doesn't suffer this
   because its target is bounded {0,1}.
2. **Entangled ReLU solution:** a 2-layer ReLU trunk shared with parity finds an in-range solution that
   is NOT linear in the `(n/K)²` feature, so it doesn't scale outside. The standalone square net
   extrapolated because it could just learn "output = the x² feature" (identity-on-feature, which
   extrapolates); the multi-task net had no pressure to keep that clean linear path.

So my hypothesis: magnitude-extrapolation needs an explicit **linear readout path from the exposing
feature to the output**; ReLU depth + bounded in-range targets destroy it, and multi-task sharing
removes the incentive to preserve it.

## The fix I want to test (4 arms on the same two-rules continual setup)

1. **baseline** (current): shared 2-layer ReLU, single head. (square_extrap≈0)
2. **+weight decay**: L2 on weights → minimum-norm bias. For a target linear in x², the min-norm
   solution should prefer "output = w·x²feature" → extrapolates. Tests whether a simplicity prior alone
   recovers it without architecture change.
3. **+linear skip**: `out = MLP(features) + v·features` (a linear path from inputs incl. x² straight to
   the output). Lets x² pass through un-truncated → magnitude scales. Tests whether an explicit linear
   channel is what's needed.
4. **+separate linear readout per task** (parity head, square head), shared trunk. Decouples the range
   constraint. This reintroduces a task-specific output — arguably fine for 2 tasks, but it's a
   task-id at the output; I'd label it as such.

Measure square interp+extrap AND parity interp+extrap (must not break parity retention), for naive and
consolidate.

## What I actually want to learn (not just "make a number go up")

The scientific question is which of these is true, because they mean different things for the LM port:
- If **weight-decay alone** fixes it → the rule was findable, we just lacked a simplicity prior; cheap
  and general.
- If only **linear-skip / separate-head** fixes it → magnitude extrapolation needs an architected
  linear channel to the exposing feature; that's a real inductive-bias requirement, not free.
- If **nothing** fixes it in the shared net while standalone works → multi-task sharing intrinsically
  costs extrapolation (a genuine tension between capacity-sharing and clean rule-derivation) — itself
  an important negative for the whole "consolidate many rules into one net" thesis.

Three questions:

2. Is "square extrapolates" even the right target metric? Parity extrap (bounded, symbolic) and square
   extrap (unbounded magnitude) are different beasts; magnitude extrapolation to 16× may be an
   unreasonable ask for any pure-weights net without an architected linear channel. Should I instead
   test extrapolation on a BOUNDED nonlinear rule (e.g. a periodic/thresholded function) so the
