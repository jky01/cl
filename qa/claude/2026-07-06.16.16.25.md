# R36-A2 implemented (compact/precomputed replay target) — review before the run

Implemented your R36-A2 design in `s2/lifecycle_bakeoff.py`. Compiles. Posting for review-gate; a pod is

## What I built

`run_consolidate(..., replay_tgt=None)` + env `BK_REPLAY_TGT` + arms `ours_tgt_<mode>`:
- **snapshot** (default = current `ours`): live pre-round snapshot KL; keeps a resident teacher copy and
  does a snapshot forward **every replay step**.
- **answerid**: at each stream's commit, store the committed **argmax token** per (fact, view); replay =
  CE to it. **No snapshot model, no replay-time teacher forward.**
- **topk8 / topk16**: store committed **top-k (ids, logits)** per (fact, view); replay = top-k KL
  (target = softmax over stored top-k logits; student = gathered log-softmax at those ids).
- **current**: reuse the student's own argmax as a hard target — the **circular negative control**.

Footprint accounting returned per run: `replay_tgt`, `replay_teacher_forwards` (0 for precomputed modes),
`extra_bytes_per_fact` (snapshot 0 / answerid ~8 / topk8 ~96 / topk16 ~192, beyond the (key,relation)
tuple all modes already need), `uses_snapshot_teacher`. Commit-time capture is once per stream
(2·|S| forwards), not per step.

Planned single-process run (shared scaffolds, your launch guard applied):

## Two design choices I want you to sanity-check

1. **Frozen-at-commit vs pre-round snapshot.** The precomputed targets are captured **once, at the end of
   each fact's OWN stream round** (its best committed state), then frozen. The `snapshot` arm instead
   re-snapshots the model at the START of every later round, so its target **drifts** with the (slowly
   degrading) model. This gives the precomputed modes a *fresher* target than snapshot. I think that's the
   honest "store the good target once" design and a real advantage of precomputing — not a confound — but
   flagging it: do you want a `snapshot_frozen` control (snapshot captured once at commit, stored as full
   logits) to isolate "frozen-vs-drifting target" from "compact-vs-full"? I lean no (answerid/topk already
   test compactness; the frozen-ness is intrinsic to precomputing), but your call.

2. **Label hygiene.** answerid/topk targets are the **committed DENSE model's** answer/logits at commit
   time — a committed-teacher signal, NOT dataset gold. For correctly-consolidated counterfactuals the
   committed argmax equals the gold counterfactual value, so answerid is *gold-equivalent for learned
   facts* while remaining formally no-old-gold. I'll report it as "committed-teacher target (=gold for
   already-correct facts), not old-gold replay." `uses_snapshot_teacher=false` + `replay_tgt` disambiguate
   in JSON. Agree that's the right framing, or do you want an explicit `commit_answer_gold_equiv` flag?

## Interpretation I'll apply (your pass bar)

Win (cheaper replay-consolidation): a precomputed mode reaches `all_seen ≥ 0.84` (within ~0.04 of `ours`
0.875), `all_para ≥ 0.70`, `oldest_forget ≤ 0.06`, newest within 0.03, base-hop drop ≤ 0.03 — **with

per fact and drop the snapshot*. If only topk16 works, the win is smaller (more bytes). If none reach the
bar, snapshot self-distill is load-bearing → report and move to capstone.
