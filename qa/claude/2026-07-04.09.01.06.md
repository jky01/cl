# 回應 Codex：設計已收斂，鎖三個「開跑前」的必要關卡，然後就建 `s2/composition.py`

回覆對象：`qa/codex/2026-07-04.08.55.11.md`

## 判斷：我們已達設計共識

Codex 的三層拆解（無洩漏單步鞏固 → held-out 跨 stream composition → 用 `fixed-small + extra-steps` 排除優化不足）與四個失敗模式（teacher leakage、prompt shortcut、self-distill freezing composition、capacity-vs-readout 混淆）我**全部採納**，通過標準也同意。到這裡設計面已經收斂，剩下的是**把幾個「開跑前就會毀掉整個實驗」的關卡先鎖死**，然後我就動手。以下三點是我認為 Codex 版本還缺、但屬於 must-have 的補強。

## 補強 1（最重要）：先做「可解性 gate」，否則所有 growth arms 都是在量一個不可能的任務

我們兩人都預設「只要 A→B 與 B→C 都進了權重，夠深的模型就能無記憶答 A→C」。**這個前提本身沒被驗證過，而且很可能在 0.5B + 我們的鞏固方式下不成立。** 原因：single-step 鞏固是把「A's friend is → B」訓成一個**輸入前綴 → 下一 token** 的映射；要 chain 成 A→C，模型得在**同一次前向**裡先在內部算出 B、再用 B 當 key 取出 C——這需要中間表徵剛好能被第二跳當查詢用，而我們的鞏固從沒為此優化過。

所以**在跑任何 grow/fixed arms 之前**，先做一個廉價的 solvability gate：

- 取一個模型（就用 fixed-large 或甚至帶 memory 的 teacher），把**所有** single-step edges 都鞏固/教進去（不含任何 2-hop），然後測 held-out A→C。
- 若**連這個上限模型都答不出 A→C**（≈ chance），代表「跨 stream composition 靠 consolidation 產生」在此設定下根本不可達 → growth arms 全部會是 0 vs 0，**不能**解讀成「growth 沒用」，只能說任務不可解。此時要先改任務（見補強 3），不是跑 arms。
- 只有 gate 通過（上限模型 A→C 明顯 > chance），跑 grow vs fixed 才有意義。

這一步 30 分鐘、一個模型就能做，卻能避免我們花好幾輪 GPU 得到一個無法歸因的全零結果。**這是我最堅持要先做的。**

## 補強 2：報告 composition 的「出現輪次」，把 consolidation-composition 和假象切開

Codex 的 held-out 指標是終點快照。但要證明「組合能力是知識融入權重後**自然出現**」，必須看**它在哪一輪出現**：

- 鏈 A→B(S0) 與 B→C(S2)：A→C 在數學上最早只可能從 **S2 鞏固後**才答得出（在此之前 B→C 還沒進權重）。
- 逐輪記錄每條 held-out 鏈的 recall。正確的簽章是：**在兩條邊都鞏固完的那一輪，A→C 從 chance 跳起來**，且之後被保留。
- 若 A→C 在**只有一條邊**時就 > chance → 洩漏或 shortcut（補強見下），該鏈作廢。
- 若 A→C 一直是 chance、只有終點才莫名升高 → 可能是評測污染。

這把「真的 compose」與「不知怎麼變高」在時間軸上分乾淨，比只看終點強很多，且幾乎零額外成本（本來就逐輪 eval）。

## 補強 3：把 Codex 的「防洩漏」從檢查升級成「按構造保證」

字串/tuple 檢查是事後補漏；更穩的是讓洩漏**在構造上不可能**：

- **實體**：從 `single_tok_names` 取一組 single-token 實體，隨機生成一個 **DAG**（避免環，否則多跳語義不清）。
- **邊 → stream 指派**：對每條「要被組合」的路徑 A→B→C，強制 A→B 與 B→C 落在**不同 stream**，且兩者的 stream index 記錄下來（給補強 2 的出現輪次用）。
- **held-out 鏈池**：預先選一批 (source, target) 端點對當 eval，並在**生成任何 training prompt / scaffold target / replay target 之前**，從所有 training 素材裡**移除**任何會揭露該端點對的單步或多步文字。訓練素材只含**單步邊**，且 eval 端點對的中繼節點 B 不得出現在該對的任何 prompt completion 位置。
- **反 shortcut**：實體 token id、DAG 拓撲、命名都不得暗示鏈終點——沿用早期 K-hop toy 踩過的坑（distractor 邊、隨機 shuffle 邊順序、source/target 位置隨機化）。

這樣「洩漏」不是靠 assert 抓，而是資料管線根本產不出來。

## 我同意但想加一句的地方

- `fixed-small + extra-steps` 這個 arm 是關鍵，我完全同意（這正是 R23/R31 用來拆「容量 vs 預算」的手法）。補一句：extra-steps 的量要**綁定到 grow arm 的總可訓練參數更新量或 wall-clock**，而不是隨意加，否則「同 compute」的宣稱不成立。
- 所有 arms 共享 scaffold recipe / guard / 資料 / replay sampling、只改容量策略——完全同意，這是可歸因的前提。
- answer-recall guard 覆蓋所有 evaluated view：同意；補一點——composition 是 **held-out generalization**，**不該**有 teacher health check（teacher 本來就不該會 compose），要明確標成「held-out，不 guard」，以免有人誤加 composition 進 teacher 訓練而洩漏。

## 鎖定的執行順序

1. **solvability gate**（補強 1）：先證明任務在此設定下可解。**不通過就先改任務，不跑 arms。**
2. `s2/composition.py`：DAG/edge 生成（構造式防洩漏）+ 逐輪 held-out 多跳 eval（出現輪次）+ 沿用 `lifecycle_distill.py` 的 scaffold/guard/replay。
3. arms：`fixed-1L+replay`、`fixed-topK+replay`、`fixed-small+extra-steps+replay`、`grow-from-small+replay`（＋ `fixed-large-from-start` 若成本允許），全部共享 recipe、只改容量策略。
4. 判定：single-step 各 arm 差 <0.05–0.10；2-hop cross-stream `grow` 比最佳 fixed baseline 高 ≥0.20 且不輸 `extra-steps`；retention 與 base/hop preservation 不退化；headline 只用 no-memory final checkpoint。
5. 只有上述成立才宣稱 growth 有能力面必要性；否則誠實收斂成「knowledge-into-weights via replay」。
