# Peer review: single-process K-sweep refactor (shared scaffolds) — speedup with zero result-impact

User asked to make the sweep faster without breaking comparability to already-validated metrics. From
the running R36-A sweep log I found a concrete waste: **each per-K process recomputes the identical
scaffolds** (`scaffolds answer-recall=[1.0,0.98,0.85,...]` is byte-identical across all 8 jobs, since
`train_memory` is deterministic in `seed*100+r`). Scaffold training (`MEMSTEPS=800 × 6 streams × 2
seeds`) is ~redundant 7 of 8 times. Please review the fix before I use it.

File: `s2/lifecycle_bakeoff.py`. Compiles clean.

## The refactor (minimal, result-preserving)

`main()` already computes `streams` and `scaffolds` **once per seed** and loops `for arm in ARMS`, so
multiple arms in ONE process already share scaffolds. The only thing forcing 8 separate processes was
that `BK_REPLAY_K` is a single global env. Fix: make K a **per-arm** parameter via arm names `ours_k<K>`:

- `run_consolidate(seed, streams, kind, scaffolds, replay_k=None)` — `replay_k` overrides the env
  (`REPLAY_K = replay_k if replay_k is not None else int(os.environ.get("BK_REPLAY_K", -1))`).
- dispatch: `arm.startswith("ours_k")` → `run_consolidate(..., "ours", ..., replay_k=int(arm[6:]))`.
- `need_scaffold` and the `agg()` flags lookup fall back to the `"ours"` entry for `ours_k*`.

Now one process runs the whole sweep:
```
BK_ARMS=naive,oracle,ours_k0,ours_k1,ours_k2,ours_k4,ours_k8,ours_k16,ours_k40 \
LD_ROUNDS=6 LD_PER=40 LD_STEPS=1000 LD_SEEDS=2 PYTHONHASHSEED=0
```
Scaffolds train once; every `ours_k*` arm reuses them. Saves ~40–60 min/sweep.

**Why results are identical (please sanity-check my reasoning):**
- `streams` and `scaffolds` are seed-deterministic (`make_streams(seed)`, `train_memory(...,seed*100+r)`)
  — same values whether computed once or 8×.
- each `run_consolidate` call builds a **fresh** `random.Random(seed*13 + abs(hash("ours"))%97)`, so
  every `ours_k*` arm gets the same training RNG stream it would have gotten as a standalone process
  (given `PYTHONHASHSEED=0`). Arms run sequentially; no shared mutable RNG across arms.
- the nested fixed K-subset RNG (`seed*100003 + j*31 + 7`) is K-independent, so `ours_k4 ⊂ ours_k8 …`
  exactly as in the separate-process version.
So `ours_k40 == ours(full) == a_replayk_40.json`, `ours_k0 == naive-in-consolidate`, and every K
matches its separate-process counterpart bit-for-bit (modulo GPU nondeterminism already present).

I'll validate by re-running the tiny smoke (K=0/4/40 in one process) and checking it reproduces the
separate-process smoke numbers before trusting the full sweep.

## Speed levers — my comparability assessment (want your check)

**Safe (do NOT change the retention regime → past metrics unaffected; only cut sampling/redundancy):**
1. shared-scaffold single process (above) — zero result change.
2. 1-seed explore to locate the knee, then 2-seed confirm only at the knee ± one neighbor.
3. coarse K first ({0,4,16,40}) then refine around the knee.

fewer steps, smaller GROW. These reduce forgetting pressure and could make small-K look artificially
