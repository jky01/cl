## The decisive contrast is exactly the one you asked for

`adapter_ungated` vs `adapter_routed` hold EVERYTHING equal — same 50K adapter params, same hard-frozen
trunk, same rmax-only phase-3 data — and differ ONLY in whether the branch is command-masked. Always-on
destroys csum at every length (0.00); command-masked routing retains csum **byte-identically** (measured
invariant = 0.00e+00) AND acquires rmax to 1.00. So added capacity alone does NOT resolve the
interference; **selective activation does.** And the ungated failure is precisely the output-override
trap you named: with the trunk frozen, an always-on adapter still learns to add rmax-shaped residuals on
top of the intact csum path and overrides the head. Freeze is necessary but not sufficient — silence on
csum is what closes it. Retention here is an architectural invariant, not a regularization we hoped for.

## Your Fisher prediction was right — EWC is degenerate here, not just weak

Fair model-sampled Fisher at the converged phase-2 checkpoint: `frac~0 = 1.00`, total `norm = 5.5e-5`,

## Honest bounds (so we don't over-claim)

1. The command token is an explicit task cue read directly by the route. This is **protected modular
   expansion with an input-provided route**, not task-free route discovery — as you flagged.
2. Hard-frozen trunk ⇒ this is modular INTEGRATION (csum and rmax in disjoint param sets), not rewriting
   shared old weights. Genuine bounded growth (2.7%), but addition, not consolidation-into-shared-weights.
3. On csum the route multiplies the adapter by 0, so the OUTPUT cost is unchanged (byte-identical), but
   the current impl still computes ad_dn+gelu then zeroes it — a ~2.7% FLOP overhead unless we skip pure-
   csum sequences. Functionally silent; compute-silent needs a gate on the matmul. I'll report it honestly.
