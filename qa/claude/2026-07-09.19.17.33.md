# Design spec (red-team before I build): schema-compressibility experiment (R44)

Proceeding with the schema shot. This is a DESIGN review-gate: I want you to red-team the concrete
design below and the metric BEFORE I write ~300 lines of harness + spend a pod. I have resolved the
A/B ambiguity — please attack the resolution and the construction.

## Resolved claim (A, not B)
- **A (what we test):** consolidated schema knowledge in weights makes each NEW same-schema fact
  CHEAPER to write and MORE robust to retain (fewer committed-target reinforcements to reach a
  retention threshold; higher held-out paraphrase EM at matched budget).
- **B (what we DON'T test — impossible / R34-killed):** inferring the UNTRAINED answer of a same-schema
  instance. Arbitrary facts (fake capital of Ruritania) are not derivable from the schema; R34 already
  killed the derivable case. So "held-out same-schema improves" means faster/robuster BINDING of
  trained instances, NOT answer inference.
- **The sublinearity metric = the slope:** marginal committed-targets per RETAINED fact FALLS as the
  number of already-consolidated same-schema instances grows. Flat slope = item ledger (schema buys
  nothing); falling slope = reusable structure compresses (the whole reframe's load-bearing claim).

## Data construction (real base-known schemas, so this is existing-schema ACTIVATION not new-schema
## acquisition — the case you argued R32/R34 do NOT kill)
- Schemas = a handful of relation templates the pretrained base already has latent structure for:
  e.g. `capital-of(country)->city`, `born-year(person)->year`, `located-in(place)->region`,
  `symbol-of(element)->symbol`, `author-of(work)->person`. (Real relations, familiar surface.)
- Instances = (entity, answer) pairs where the base is closed-book WRONG (needs writing) but the
  relation is familiar. Two sources to compare:
  (a) REAL rare instances mined from SQuAD/wiki census (base-hard, RAG-answerable) — genuinely
      existing-schema; or
  (b) CONTROLLED instances: real template + invented entity+answer (fake capital). These isolate the
      schema-familiarity variable but drift toward new-fact binding. I lean (a) primary, (b) as a
      contrast to see if familiarity of the ENTITY matters vs familiarity of the SCHEMA.
- Each instance gets a held-out paraphrase (as in census) for the retention metric.

## The core measurement (fixed-budget binding-cost comparison — cleaner than steps-to-commit)
At a FIXED small consolidation budget, compare commit-rate + held-out paraphrase EM of:
- a new instance of an ESTABLISHED schema (model already consolidated N same-schema instances), vs
- a new instance of a NOVEL schema (first time the model sees that relation).
If established-schema instances bind better/cheaper at matched budget → schema-in-weights lowers
marginal cost. Sweep N (schema density) to get the slope.

## Arms (your R43/schema set, adapted)
| arm | purpose |
|---|---|
| `k0` | forgetting floor |
| `full_replay` | ceiling |
| `item_k_matched` | same #committed targets, schemas NOT concentrated (mixed) — the real baseline |
| `schema_commit` | instances grouped by schema, streams accumulate same-schema density |
| `deranged_schema` | same budget, template/answer-kind scrambled per instance (anti-"just more supervision"/leakage) |

## Pass / fail (yours, sharpened)
- PASS: marginal targets/retained-fact SLOPE falls with schema density AND schema_commit beats
  item_k_matched by >= +0.10-0.15 held-out same-schema paraphrase EM on BOTH seeds, single dense
  checkpoint, no inference memory, deranged does NOT pass.
- FAIL: item_k_matched ties schema_commit; gains only on supported instances not held-out; slope stays
  linear; deranged passes (=leakage/extra-supervision artifact). If FAIL cleanly → reframe immediately.

## Questions for you (attack these)
1. **Is the fixed-budget binding-cost comparison the right operationalization of "marginal cost falls",
   or do you want an explicit steps-to-commit curve** (train until retention threshold, count steps)?
   The latter is more direct but needs a new training loop; the former reuses the existing fixed-step
   consolidation. Which buys the cleaner slope?
2. **Real (a) vs controlled (b) instances:** if I use real base-hard census facts, the "schema" is
   entangled with entity familiarity and topic. If I use controlled fake-answer instances, I'm testing
   new-fact binding under a familiar template — which is closer to the actual continual-reading case but
   risks looking like R32/R34 synthetic. Which is the honest primary, and is the OTHER a needed control?
3. **Deranged control design:** scramble the template (wrong wh-word/relation) but keep entity+answer?
   Or scramble answer-KIND (ask for a date, answer is a name)? Which one actually isolates "schema
   structure helped" from "more gradient steps helped"?
4. **Slope statistics at our scale:** to see a falling slope I need several schema-density points ×
   enough instances/point × 2 seeds. Rough sizing: ~5 schemas × ~12 instances = 60, streams accumulate
   density. Is that enough to distinguish a real slope from noise, given R43's high seed variance?
5. **Does this even need growth?** Your reframe says growth is justified only if schema compression
   saturates. R44 as specified tests compression WITHOUT growth. Correct to keep growth OUT of R44 and
   make it a follow-up only if R44 passes and then saturates?
