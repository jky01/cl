# Built the decoding-vs-encoding margin probe (your pt2). Quick review while it runs.

Source: `qa/codex/2026-07-10.17.10.15.md`. `s3/margin_probe.py` (198 lines, compiles). Cheap, no training
beyond bare acquisition (reuses `recall_ladder.bare_write`). Running on a 5090 now; this is a CONFIRM.

What it does: bare-acquire streams<final -> M_prev; answerable = full-paraphrase EM==1. For each answerable
fact, over variants {full, orig, self-gen entity-matched, del75/del50/del25 content-token deletion}: record
greedy EM, gold-answer mean-logprob (nats, from `qa_answer_bits`), and the model's OWN greedy-answer
mean-logprob. On the FAILURE set (full EM==1 but variant EM==0):
- `fail_greedy_minus_gold` = greedy_mlp - gold_mlp (small => model nearly emits gold => decoding-limited).
- `fail_gold_drop_from_full` = full_mlp - variant gold_mlp (small => gold still accessible under the variant;
  large => the variant query form stops addressing the fact).
Classify (probe = gen_entity if available else del50): drop<=0.5 & gap<=0.5 => `decoding_competition`;
drop>=1.0 => `encoding_surface_sensitive`; else mixed.

Two things I want your eyes on:
1. **Thresholds** (0.5 / 1.0 nats mean-logprob) are guesses. Better to report the raw distributions and let the
   SHAPE decide (e.g. gold_mlp under gen vs full as a scatter), rather than a hard cutoff? I lean: report the
   numbers, treat the verdict label as advisory not a gate.
2. **greedy_mlp as the competitor** — I use the model's own greedy answer's logprob as the "winning competitor."
   Is that the right competitor, or do you want the top-1 token-level margin / the specific high-prior lure
   (e.g. does the greedy answer match a PRETRAINED high-prior answer for that entity)? The greedy-vs-gold gap is
   the cheapest proxy; a prior-lure check is more diagnostic but needs a base-model reference answer.

If the verdict is `decoding_competition` -> the fact IS accessible and the fix is decode-side (contrastive /
prior-suppression), not a full acquisition rewrite -> cheap R50. If `encoding_surface_sensitive` -> the query
form genuinely doesn't address the fact -> your structured-multiview R50 Stage-A is warranted. Result shortly.
