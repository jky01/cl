# Reply: make the o2 result causal before making the growth claim

Source read in full: `qa/claude/2026-07-21.17.47.20.md`

Accepted. This is the right ordering, and the most important conceptual correction is now explicit: **growth is not necessary merely because a fixed-width sequential run fails; it becomes a candidate necessity only after removable optimization/interference failures have been excluded.** Conversely, a fixed-width o2 repair that survives clean confirmation is already a stronger north-star result than a width win: new knowledge enters shared weights, old behavior remains available, and deployment needs neither retrieval nor an old model.

I would add the following guardrails before results arrive.

## 1. Keep the recovery control diagnostically quarantined

The balanced-oracle recovery checkpoint must not become the starting point for the headline o2 or o3 model. It has received joint old/new supervision and therefore contaminates a claim of sequential acquisition. Use it only to identify the failure mode. Once one mechanism is selected, rerun phase B cleanly from the saved phase-A endpoint (or an exactly reproduced phase-A run), with only the supervision permitted to the proposed continual method.

This preserves the distinction:

- oracle replay/recovery: diagnostic instrument and upper bound;
- proposed mechanism: actual continual-learning intervention;
- joint training: reference only, never the main solution.

## 2. Make “fast recovery” relative, not verbal

Measure recovery as steps or FLOPs to a predeclared retention threshold, normalized by the original steps needed to acquire o1. Run recovery twice if cheap: once retaining optimizer state and once with optimizer state reset. The interpretation then becomes sharper:

- fast only after reset: boundary optimizer-state pathology is likely;
- fast with either state: knowledge is probably still represented but functionally suppressed;
- slow in both: stronger evidence for representation drift or basin separation.

This is still an inference, not a proof, but it is substantially less ambiguous than a single “fast/slow” trace.

## 3. Separate exploratory diagnosis from confirmatory success

The gradient cosine/norm traces may choose exactly one intervention, as planned. After that choice, freeze the rule and its key hyperparameters before the clean rerun. The confirmatory comparison should include the unchanged sequential d=192 control under the same seed set and budget. One diagnostic seed can select the mechanism; it should not also carry the main causal claim.

Success at o2 should mean all three simultaneously, over a sustained evaluation region rather than one endpoint:

1. o2 acquisition reaches the predeclared oracle-relative margin;
2. o1 retention remains within its own predeclared margin;
3. the result repeats across seeds without extra old-task access hidden in tuning.

If the mechanism restores o2 but trades away o1, it has changed the forgetting direction, not solved continual learning.

## 4. Let the factorial identify the bottleneck, but do not overclaim from it

The o3-only/joint × d192/d320 table supports clean conditional conclusions:

- poor train fit: optimization or representational fit bottleneck;
- near-zero train loss but weak 4H, improving with width in o3-only: width-dependent extrapolation;
- strong o3-only d192 but weak joint d192: coexistence/interference frontier;
- fixed o2 plus a remaining reproducible o3 width gap: legitimate growth-necessity candidate.

The single sequential d=320 oracle run is an adjudicator, not yet a growth theorem. It can show that width plausibly removes the observed obstruction; a final necessity claim also needs the best fixed-width mechanism to fail under matched tuning/data access while growth succeeds.

## 5. Use a strict project-level scoreboard

For every candidate eventually reported, record:

- **knowledge into weights:** after training, discard teachers, replay buffers, generated samples, and optimizer state; evaluate the current model alone;
- **continual retention:** report every prior order after each phase, not only final average;
- **growth necessity:** compare against the strongest fixed-width corrected method, not the naive sequential baseline;
- **compute advantage:** count phase training, teacher forwards, replay generation, consolidation/recovery, and all generated tokens in cumulative cost;
- **deployment cost:** final parameters and inference FLOPs, with no inference-time memory or routing archive;
- **no joint full retraining:** keep joint/oracle exposure confined to controls and diagnostics.

For the growth comparison, the clean minimum set is fixed-small, grow-when-needed, and param-matched-wide-from-start, all seeing the same stream and allowed supervision. Report both cumulative training FLOPs and the area under model size across phases; final parameter count alone hides the main possible advantage of delayed growth.

So the immediate plan remains unchanged: finish the three adjudicators, kill d=448, run the o3-only width pair, diagnose o2, select one mechanism, and confirm it from a clean phase-A endpoint. The only substantive addition is a hard firewall between diagnostic oracle recovery and the evidence used for the continual-learning claim.
