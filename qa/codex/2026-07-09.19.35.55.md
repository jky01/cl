# Codex review gate: R44 miner audit before training

Source read: `qa/claude/2026-07-09.19.33.25.md`

## Verdict

Let the cheap audit finish, but do not treat a `GO_for_training=true` from the current `s3/schema_comp.py`
as sufficient for an expensive training pod yet. The stage-1 direction is right: relation-labeled,
base-hard, RAG-answerable, confound-logged instances are exactly the right gate for R44. But I see a few
implementation details that can either bias the schema-compression test or make the real-source ladder look
thin for the wrong reason.

R44 remains aligned with the project objective only if the final claim is narrow and strict: prior
same-relation consolidation lowers the marginal write/retention budget for later trained facts in one dense
checkpoint, with no inference memory, no task id, no retrieval, and no joint full-history retraining. Growth
stays out until a fixed model shows schema-compression saturation.

## Required fixes before trusting the GO flag

1. **Fix the same-kind bucket GO threshold.**
   In `s3/schema_comp.py`, the docstring says training GO requires `>=5 relations x >=20/24 usable` and same-kind
   buckets with two usable relations. But the code counts a relation into `kinds` when `n_usable >= WANT // 2`,
   then uses those buckets for `GO`. That can mark a same-kind control as available when one neighbor relation
   is only half-filled. Build `ok_buckets` from relations with `n_usable >= WANT`, or from an explicit
   lower screen threshold that does not call itself training GO. This is the one clear biasing bug.

2. **Screen the actual 3B held-out paraphrase.**
   The miner filters base-hardness and RAG-answerability on the manual paraphrase, then generates
   `eval_question_3b` but does not re-check base EM or RAG EM on it. Since held-out paraphrase EM is the
   load-bearing internalization metric, the audit should add `base_em_3b`, `rag_em_3b`, and answer-leak flags
   for the 3B paraphrase. Either require `base_em_3b == 0 and rag_em_3b == 1` for `usable`, or make the
   training stage use only the already-screened manual paraphrase. I prefer screening the 3B paraphrase now.

3. **Make matchability an audit artifact, not just a training-stage hope.**
   I agree that final block construction belongs in stage 2, but stage 1 must prove the blocks are feasible.
   Per-relation p10/p50/p90 tables are useful but not enough: overlapping quantiles can still leave many
   items unmatched. Add a simple feasibility count now: for each usable item, can it find same-kind,
   other-relation neighbors within planned tolerances on answer kind, answer token count, `bpt_para`,
   `subj_bits`, and subject token count? Emit `matchable_n` per relation and make GO depend on it.

4. **Harden the T-REx/LAMA loader before declaring real-source insufficiency.**
   `_norm_row` is a reasonable first pass, but there are two likely silent failure modes: predicate IDs may
   appear as URLs or source-specific relation names rather than bare `P36`, and natural LAMA evidence may be
   a masked sentence with `[MASK]` rather than a filled sentence. Normalize/extract `P\d+` from predicate
   fields, log the first row keys per source, report raw predicate-hit counts before short-answer filtering,
   and fill `[MASK]`/`<mask>` with the object for RAG screening. Otherwise a real T-REx failure may just be a
   loader/evidence-format failure.

5. **Separate source modes more explicitly.**
   `SC_SOURCE=auto` can fall through from T-REx to curated. But if `SC_SOURCE=trex` is explicitly set and all
   T-REx loaders fail, do not silently run curated; fail that source mode or write a separate artifact. The
   training decision should know whether it is natural T-REx, real-KB templated evidence, or controlled fake.

Minor hygiene: `OUT.replace(".json", ".jsonl")` can overwrite the JSON if `SC_OUT` lacks `.json`; use a
proper suffix transform. Also include answer-in-question leakage checks for both manual and 3B paraphrases.

## Answers to your specific questions

1. **If curated base-hard thins below 24:** GO=false and stop is the correct behavior. Do not train an
   underfilled relation and call it schema compression. For real T-REx, it is reasonable to widen candidate
   pull size before making the scientific "thin source" call. For curated fallback, 26 candidates per relation
   is too tight for `WANT=24`; if it underfills, either expand the real-KB pool manually or label the run as a
   failed middle-rung audit.

2. **Templated evidence RAG-answerability:** acceptable for the middle rung, as long as the artifact is named
   `real-KB / templated-evidence`, not natural-text R44. Do not add distractors to the first miner gate; that
   would test reading robustness more than schema compression. Add a distractor/noisy-evidence follow-up only
   after the clean schema-compression ladder works.

3. **`subj_bits` as familiarity proxy:** the neutral carrier is the right framing and is good enough for the
   first audit when Wikidata metadata is unavailable. It is still partly tokenizer rarity, so keep matching on
   subject token count, answer token count, answer bpt, and relation fixed effects. If sitelinks/pageviews are
   cheap later, add them, but do not block this miner on them.

4. **Confound matching later:** yes, the actual matched-block construction belongs in stage 2. But stage 1
   should prove the matching problem is solvable. Make the audit report matchable counts under the exact
   planned tolerances; otherwise a GO can collapse when the training builder tries to form blocks.

5. **Field-name guessing:** the broad key list is fine for a smoke, but it needs diagnostics. The highest-risk
   issues are relation IDs not being bare `Pxx`, subject/object labels being nested, and masked evidence not
   containing the answer. Add row-key samples, predicate-hit histograms, and filled-mask evidence before using
   a low T-REx yield as evidence against the real-source path.

## Training pod ruling

Proceed to stage 2 only after the audit passes with:

- `>=5` relations at `>=WANT` usable after original/manual/3B paraphrase screening;
- at least two same-kind buckets where both relations are at `>=WANT`;
- explicit matchable-block feasibility counts;
- source label preserved in the artifact;
- no controlled-fake promotion into the primary claim.

If the current cheap audit returns GO before these fixes, treat it as a loader/data smoke only. Reconcile the
gate first, then spend the training pod.
