# Ruling: control the instruct policy, but do not replace both acquirer and generator before R50-A

Source read: `qa/claude/2026-07-10.20.45.02.md`

## Bottom line

**The base-model confound is real enough to require one bounded control, but the proposed
Qwen2.5-1.5B-Instruct acquirer+self-generator rerun is not the clean first test.** It changes two causal axes at
once: the representation and optimization geometry that hold the acquired facts, and the policy used to propose
questions. A positive would not show that instruction following fixed self-addressing; a null could be blamed on
damaged chat behavior or an inappropriate raw-text acquisition interface.

Run the cheaper crossed control first: keep the **acquired Qwen2.5-1.5B base checkpoint as the sole knowledge
holder and answerer**, and give a frozen Qwen2.5-1.5B-Instruct model only the role of history-free question
proposer. It receives no old question, answer, entity, title, relation, qid, passage, embedding, or stream label.
The acquired base checkpoint answers every proposed question; hidden historical data is used only for the
offline proposition-equivalence audit. Match this arm to base L0+L1 on attempts, generated tokens, and reported
FLOPs.

This should be added as the strongest **no-shadow proposal-policy baseline inside R50-A Stage A**, with a quick
read before enabling shadow search. It kills the omitted instruct-policy control without spending a separate pod
on a second acquisition regime. `s3/scale_scout.py` currently deletes each acquired model without saving it, so
unless a checkpoint exists outside the recorded artifact, even this control requires replaying one acquisition;
evaluate the extra proposer before `del M` on that rerun.

My probability ordering is:

1. instruct tuning materially improves instruction compliance, parse rate, fluency, and question diversity;
2. it modestly improves coverage of familiar entity/relation question manifolds;
3. it still leaves correct coverage of obscure newly written tail propositions near zero;
4. it is less likely to make the acquired write itself create a reliable autonomous address.

So I reject both extremes. Reversal-curse-style directionality does **not** make the control a certain zero, but
instruction tuning is also unlikely to supply the missing information about *which* low-prior facts were written.
The right investment is one frozen-policy arm, not a full model-family campaign.

## Why the confound is real—but narrower than claimed

### Steelman: instruction tuning could matter

The current L0/L1 audit is unusually sensitive to output policy. `rl.gen_pool()` asks a raw causal LM to continue
few-shot text, then accepts only a continuation with an `Answer:` separator, a question ending in `?`, and other
format constraints. An instruct checkpoint used through its native chat template is trained to obey exactly this
kind of request. It may therefore produce many more valid, distinct questions instead of falling into a few
high-prior completion grooves.

That is a genuine uncontrolled baseline. The repository already contains a warning of the same class:
`s3/census.py` needed explicit examples and output-format repairs because an instruct generator copied literal
separators and omitted required punctuation. Output-interface mistakes can create false zeroes. Base Qwen did
produce many parsed high-prior QA pairs in R48, so formatting cannot explain the entire negative, but it can
still depress the effective diversity of the search distribution.

An instruct model could also possess a much broader pretrained *question prior*: even if it does not know the
new answer, it may know that a rare entity has an architect, headquarters, date, or creator worth asking about.
Once the written base checkpoint answers that question, passive replay has obtained a valid training target. That
would be operationally useful even though the address came from an external proposal policy rather than from the
holder's new write.

### Pushback: instruction tuning does not identify the new tail

The stronger claim—“instruct makes the holder self-address its own newly acquired facts”—requires more than
following a request. The checkpoint has no explicit variable for “facts learned in the last acquisition phase,”
and ordinary Q-to-A CE does not train a map from an unconditioned generation state to the corresponding question.
Instruction tuning can reshape the sampling policy, but it is not given the identity of the weight changes to
invert.

The reversal-curse analogy is useful but not exact. R48/R49a are not merely testing the literal inverse `A -> Q`;
they ask the model to select one proposition from a large mixture of pretrained and newly written functions with
no identifying cue. The more general obstruction is posterior selection under an overwhelmingly skewed prior.
An instruction policy can increase entropy and valid-question rate while still spending nearly all probability
mass on familiar propositions. This is consistent with the repository evidence: 1.5B acquired more addressed
facts than 0.5B (`38/29` versus `31/25`) yet both emitted zero correct propositions over roughly 32k generated
tokens per seed under the fixed policy.

The prompt “list facts you just learned about X” does not cleanly resolve this:

- with no `X`, “just learned” has no grounded episode boundary and is likely to elicit generic or hallucinated
  recency language;
- if `X` is an old entity, it supplies historical information and becomes an oracle-entity cue, close to R49a L3;
- if the full relation is also supplied, it approaches L4/L5 and no longer measures history-free addressing.

It is worth including the generic “facts recently learned” wording as a diagnostic prompt family, but it must not
be counted as a new mechanism unless the prompt contains no historical key. Any entity-conditioned result must
be reported separately as cued coverage.

## The decisive cheap control

The suggested “base acquirer, instruct generator” variant is the best first discriminator, with one conceptual
correction: the instruct model cannot inspect facts stored in the base model's weights. It is an **external query
proposer**, not a self-generator of the holder's knowledge. Its questions can elicit the holder's acquired facts,
but a positive establishes `generic instruct prior -> useful address`, not `new write -> self-address`.

That distinction is scientifically useful. It separates three possibilities:

1. **format/policy failure:** base and instruct propose similar propositions, but instruct yields more parseable
   candidates;
2. **prior-address failure:** instruct proposes more relevant entity/relation questions, but independently of the
   holder's acquired write;
3. **write-aware addressing:** proposal probability specifically changes because the proposer itself acquired the
   new facts—this cannot be shown by an external frozen proposer and requires the later instruct-holder test.

### Frozen arm contract

Use the exact R50-scale stream and the acquired 1.5B-base holder, but strengthen the screen so every evaluated
fact is failed by the frozen base holder **and** the frozen instruct proposer when directly asked the complete
question. This prevents the proposer's known answer from masquerading as a newly written target. Retain the
existing jointly base-hard result as a separately reported population so the stricter screen does not silently
change the original claim.

Compare, at minimum:

| Arm | Question proposer | Answerer | Meaning |
|---|---|---|---|
| base L0/L1 | acquired base holder | acquired base holder | existing passive self-generation |
| instruct-static | frozen instruct model, generic chat prompts | acquired base holder | output-policy/prior control |
| instruct-static + frozen answerer | same candidate pool | frozen pre-write base | acquired-lift control |
| R50-A real-shadow | frozen generic proposal seeds plus damage-guided search | acquired base holder | proposed tomography mechanism |
| R50-A wrong-shadow/no-damage | matched search controls | acquired base holder | causal mechanism controls |

The third arm is essential: a hit counts as knowledge-into-weights only if the acquired holder answers correctly
and its frozen pre-write counterpart does not. If the instruct proposer itself already answers the gold, exclude
that item from the write-specific result and report it as prior contamination.

The static instruct arm should not see the base model's hidden states, logits, answers, or write shadow. If an
iterative instruct agent is later allowed to observe base answers and mutate questions, call that **black-box
query search** and include it as another no-shadow search baseline. It is much closer to R50-A than to passive
self-replay.

### Interface and implementation corrections

“Same tokenizer” is not sufficient for an instruct comparison. In the current code, `wb.tok` is loaded once from
`WB_MODEL`, `scale_scout.load()` swaps only model weights, and `rl.gen_pool()` feeds raw strings rather than
`apply_chat_template()`. Reusing those helpers unchanged would test an instruct checkpoint through the wrong
interface. Give the instruct proposer its own tokenizer object and native chat template, while keeping the
semantic generation request and sampling budget frozen.

Also do not let the rigid QA parser decide the scientific result. Save every raw continuation and report:

- attempted, parseable, and unique natural-question counts;
- generated and prompt tokens, wall time, and estimated FLOPs;
- duplicate concentration and effective question diversity;
- proposition-equivalent question coverage, independent of whether the holder answered correctly;
- holder correctness conditional on an equivalent question;
- unique **correct** proposition coverage (`question equivalent AND acquired holder correct`);
- acquired lift over the frozen pre-write holder;
- answerable and threatened coverage separately;
- raw target error, high-prior contamination, and age distribution.

This decomposition is important because `surfaced_global()` already returns raw and correct sets, but
`scale_scout.py` discards the raw sets and all candidate rows. Instruct may raise raw proposition coverage while
leaving correct coverage flat, or raise parse rate while leaving proposition coverage flat. Those are different
outcomes.

Use the hardened R49a proposition-equivalence protocol rather than Jaccard alone for all putative hits and a
blinded sample of misses. The evaluator must not be told which proposer produced a question. Because the existing
3B judge is from the same Qwen instruct family, manually adjudicate all decision-driving hits and an enriched
near-match sample; otherwise generator/judge family agreement can inflate the instruct arm.

Match the existing budget of 400 L0 plus 400 L1 attempts and also cap/report approximately the existing 32k
generated tokens per seed. Chat prompts have different prompt-token cost, so attempts alone are not compute
matching. Do not increase the instruct budget after observing sparse hits.

### Pass/fail rules

`cov_ans > 0` is too weak. Eight hundred autoregressive draws from a small prompt bank are highly correlated, and
one lucky familiar relation would not reframe the mechanism. For the two-seed answerable scout, preregister a
**policy signal** only if, in each seed:

- at least four unique propositions are correctly recovered;
- correct answerable coverage is at least 0.15;
- at least 80% of admitted hits are proposition-equivalent;
- every counted hit has positive acquired lift over the frozen pre-write base;
- no single entity, relation template, or duplicate cluster supplies more than half the hits.

This is a trigger for the instruct-holder follow-up, not a retention success. The threatened sets in the current
scale artifact are only `2/1` on the shared population, so they cannot decide a retention mechanism. To displace
R50-A, passive instruct generation must later meet a powered threatened-fact coverage gate comparable to Stage A
(`>=25%`, target-precise in both seeds) **and** its replay must improve old held-out paraphrase retention under a
compute-matched future write. Nonzero answerable coverage alone does not moot tomography.

Interpret the quick arm mechanically:

- **Higher fluency/parse rate, same proposition coverage:** the interface confound is real but does not explain
  the wall. Proceed to R50-A unchanged.
- **More equivalent questions, but frozen and acquired holders answer them equally:** the proposer is surfacing
  prior knowledge, not newly written knowledge. Do not count it.
- **Positive acquired-lift coverage, but no threatened enrichment:** a frozen external question prior is a useful
  passive baseline; keep it in R50-A, but it has not solved retention targeting.
- **Material acquired-lift and threatened coverage:** run the instruct-holder factorial before broad R50 search.
- **One-seed or one-template hit:** treat as inconclusive and do not launch a family sweep.

## If the policy control passes: the clean instruct-holder experiment

Only after a material static-policy signal should the project pay for an instruct acquirer. Then generate
candidate pools from both acquired holders and cross them with both answerers:

| Candidate pool | Base answerer | Instruct answerer |
|---|---|---|
| acquired base proposer | B-proposal / B-access | B-proposal / I-access |
| acquired instruct proposer | I-proposal / B-access | I-proposal / I-access |

Both holders acquire the same jointly hard facts. This crossing separates a better proposal distribution from a
better knowledge representation or readout. Also generate from each proposer **before and after** acquisition.
A post-write rise in proposition-equivalent question probability is the evidence needed for write-aware
self-addressing; high coverage already present pre-write is a pretrained address prior.

There are two acquisition interfaces, and they answer different questions:

1. **strict objective-matched:** retain the raw `QT`/QA-span CE objective used by base, testing whether initial
   instruction tuning alone survives identical continual updates;
2. **chat-native capability:** use the checkpoint's chat template and assistant-token-only loss, testing the
   actual instruct interface.

Do not silently choose one and call it a clean base comparison. If the raw arm loses instruction following but
the chat-native arm works, the result is an acquisition-interface interaction, not evidence that generic
instruction tuning alone solved addressing. Report a small held-out instruction-following suite, neutral/base
capability, newest acquisition, and parameter drift. The current neutral KL anchor on raw neutral strings does
not guarantee preservation of chat policy.

The “more fluent but wrong proposition” failure must remain a hard fail. Audit proposition selection first,
holder answer second, and final retention third. A model that elegantly asks a different question about the right
entity has reproduced the R49a failure.

## Ordering versus R50-A and family scouts

My ordering is a slight refinement of both stated positions:

1. **Add and read one static Qwen2.5-Instruct proposal arm as R50-A's no-shadow policy baseline.** Run it first if
   convenient, but do not make it a separate full-acquisition pod.
2. **If it misses the frozen policy-signal gate, proceed immediately to bounded R50-A Stage A.** Do not try more
   instruct prompts or families.
3. **If it passes, run the crossed instruct-holder scout.** R50-A still remains necessary unless passive
   threatened coverage and retention pass; the instruct arm becomes a strong baseline and possibly a proposal
   source.
4. **Run Llama/Gemma family tests only after a Qwen instruct signal or a theory-specific reopen condition.** A
   family switch simultaneously changes tokenizer, pretraining corpus, architecture, size, chat tuning, and
   priors. At the current zero floor it is more likely to produce an uninterpretable family anecdote than a
   mechanism result.

Thus the instruct confound is worth controlling **before interpreting R50-A**, but it is not worth replacing
R50-A with a new pod-scale branch. The control and R50-A answer complementary questions: can a better generic
language policy enumerate useful addresses, and does future-write damage specifically locate the propositions
that need protection?

## Project-objective assessment

An acquired-base-holder/instruct-proposer positive would still satisfy knowledge-into-weights only when the
frozen pre-write base fails and the acquired holder succeeds. The external proposer is permissible as disposable
training-time compute, but it is not evidence of checkpoint-only self-addressing; it must be removed before final
closed-book inference. Its model size and proposal FLOPs belong in the lifetime-cost ledger.

If its questions are replayed into the holder and preserve old held-out behavior across future writes, the final
artifact remains one weights-only model with no inference memory and no task ID. This is aligned with the project
even though strict rehearsal-free learning remains unsolved. No arm needs joint full-history retraining: proposal,
answering, and consolidation operate on the current checkpoint, disposable probes, and generated targets.

Neither an instruct checkpoint nor a larger external proposer demonstrates justified growth. Native instruct
initialization and auxiliary generation compute are baselines. The small-to-large claim remains gated on a
measured fixed-model capability or lifetime-compute frontier, followed by function-preserving growth from the
same smaller checkpoint.

## Boundary-pushing, high-risk/high-reward brainstorming

### Make the weight update itself the episode key

Keep a disposable low-rank sketch of `M_t - M_{t-1}` during consolidation and train a small query decoder to map
update directions into natural self-tests. It receives no historical items—only the parameter delta and current
checkpoint—and is deleted after it generates replay questions. A real success would show coverage scaling with
newly acquired surprise rather than with generic trivia priors. The danger is that the delta mostly encodes
optimizer noise or surface tokens; require cross-seed question equivalence and wrong-delta controls.

### Train a symmetric self-questioning interface at write time

For each current-stream fact, train both ordinary question-to-answer behavior and a content-derived latent-code
to-question behavior, where codes come from a fixed public hash rather than a stored per-fact ledger. Sleep scans
the public code space to regenerate questions. Growth adds code capacity only when collision or scan cost crosses
a frozen threshold. This could put addresses into weights without inference memory, but it risks becoming an
item-per-slot memory; bytes, active scan FLOPs, collision rates, and retained surprise per slot must be audited.

### Distill a universal interrogator into the small model

If the external instruct proposer finds any acquired-lift questions, train the base checkpoint on the **policy of
asking**—not merely on the recovered old answers—using only generic transformations and current-stream examples.
Then test whether the next unseen stream becomes more self-addressable without the external model. Repeated
success would turn an auxiliary large model into a temporary teacher that improves the small model's in-weights
learning algorithm; failure would show that the proposer is merely carrying a fixed external prior.

### Contrast pre-write and post-write generative support directly

Instead of asking for “recent facts,” search for natural questions whose likelihood rises from `M_{t-1}` to
`M_t` while the correct answer is stable in `M_t` and absent in the frozen base. Intersect that write-salience
signal with future-shadow damage. The first delta says “this behavior was newly installed”; the second says “this
behavior is about to be lost.” Their intersection may provide a checkpoint-derived replay curriculum without an
old-item ledger. The major risk is optimizing adversarial likelihood artifacts, so paraphrase stability,
wrong-write deltas, and natural-question controls are mandatory.
