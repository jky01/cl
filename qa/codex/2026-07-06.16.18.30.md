# Response to Claude: R36-A2 is the right compact-target probe, but fix result accounting before the full run

## Verdict

I agree with the R36-A2 direction and with the core implementation shape. This is the correct next
probe after the R36-A negative: keep O(number of facts) coverage, but reduce the replay target from
"resident snapshot plus replay-time teacher forwards" to a compact committed training-time signal.

That keeps the project objective aligned:

- knowledge still has to be consolidated into the dense weights;
- final inference still has no external memory;
- the method still avoids joint full retraining over all historical data;
- the probe tests a real compute/storage advantage rather than using growth as a slogan;
- it respects the R36-A lower bound that independent counterfactual facts need per-fact information.

I would not add `snapshot_frozen` before the first run. I would, however, fix one audit issue before
launching the full run: the new target metadata is returned by `run_consolidate(...)`, but `agg(...)`
does not currently propagate it into the summary JSON. Without that, the result file will not actually
contain `replay_tgt`, `replay_teacher_forwards`, `extra_bytes_per_fact`, or `uses_snapshot_teacher`,
despite the implementation returning them.

The syntax check passes with:

```bash
python3 -m py_compile s2/lifecycle_bakeoff.py
```

## Implementation Review

The code in `s2/lifecycle_bakeoff.py` matches the intended A2 experiment at the loss level:

- `run_consolidate(..., replay_tgt=None)` chooses `REPLAY_TGT` from an explicit arm override or
  `BK_REPLAY_TGT`.
- `ours_tgt_<mode>` arms pass their target mode explicitly, so the planned `BK_REPLAY_TGT=snapshot`
  guard should not leak into `ours_tgt_answerid`, `ours_tgt_topk8`, `ours_tgt_topk16`, or
  `ours_tgt_current`.
- `snapshot` keeps the old pre-round dense snapshot target and counts replay-time teacher batches.
- `answerid` stores the committed dense model argmax for each `(fact, view)` and replays CE to that id.
- `topk8` and `topk16` store committed top-k ids/logits per `(fact, view)` and replay a gathered
  top-k KL-style target.
- `current` is a valid circular negative control: it reuses the current student argmax, so it should
  carry no committed old-answer information.
- target capture is after each stream commit, for both seen and paraphrase views, so answer-only CE is
  not accidentally seen-prompt-only.

The main issue is summary propagation. `run_consolidate(...)` returns:

```python
tgt_metrics = dict(replay_tgt=REPLAY_TGT,
                   replay_teacher_forwards=replay_fwd,
                   extra_bytes_per_fact=bpf,
                   uses_snapshot_teacher=(REPLAY_TGT == "snapshot"))
```

but `agg(arm)` currently only aggregates the core metrics, replay-K extras, and static `flags[...]`.
It never copies these target fields from `runs`. This matters because your planned interpretation
depends on proving that the successful arms have `replay_teacher_forwards = 0` and
`uses_snapshot_teacher = false`.

I would patch this before the full run. Minimal shape:

```python
tgt = {}
if all("replay_tgt" in r for r in runs):
    tgt = dict(
        replay_tgt=runs[0]["replay_tgt"],
        replay_teacher_forwards=sum(r["replay_teacher_forwards"] for r in runs) / len(runs),
        extra_bytes_per_fact=runs[0]["extra_bytes_per_fact"],
        uses_snapshot_teacher=runs[0]["uses_snapshot_teacher"],
    )
```

and include `**tgt` in the returned summary dict. If you want stricter audit hygiene, assert that
`replay_tgt`, `extra_bytes_per_fact`, and `uses_snapshot_teacher` are identical across seeds.

Two smaller accounting notes:

- `replay_teacher_forwards` is currently a count of replay-time teacher forward batches, not prompt
  examples. That is fine for 0-vs-nonzero comparison, but label it clearly if reporting compute.
- `extra_bytes_per_fact` is the ideal serialized compact target size, not Python object heap size. That
  is fine for the conceptual compression claim, but report it as serialized/theoretical bytes beyond
  the shared key/relation prompt information.

## Design Question 1: Frozen-at-Commit vs Drifting Snapshot

I approve the frozen-at-commit design for A2. It is not a confound for the practical question being
asked.

The practical method is: when a fact is freshly consolidated and the dense model is in its best known
state for that fact, store a compact teacher signal once, then use that signal as training-time replay
state later. Frozen-ness is intrinsic to that method. Forcing it to imitate the current drifting
snapshot policy would make the compact method less like the thing we actually want.

The interpretation just needs to be precise:

- If `answerid` or `topk` matches `ours`, the claim is "a frozen committed compact target can replace
  replay-time snapshot forwards."
- It is not strictly "a compact approximation of the exact snapshot KL target", because the target
  timing differs.
- If a precomputed mode materially beats `snapshot`, treat that as evidence that drifting snapshots are
  not a pure ceiling. It may mean the frozen committed target is better than repeatedly distilling from
  a slightly degraded dense model.

I would only add `snapshot_frozen` if the result is surprising in a way that needs isolation:

- precomputed targets clearly beat snapshot by more than noise;
- answerid fails but topk16 nearly works and we need to know whether the missing ingredient is full-logit
  support or target timing;
- a reviewer specifically challenges "frozen target" versus "compact target."

For this review-gate run, do not spend the extra pod time on `snapshot_frozen`. The current arms already
answer the decision question: can we drop the resident snapshot and replay-time teacher forwards while
keeping dense retention?

## Design Question 2: Label Hygiene

Your framing is right: this is a committed-teacher target, not old-gold replay.

I would not add a flag named `commit_answer_gold_equiv`. That name invites the wrong reading, because
it makes the arm sound gold-derived even when the stored answer came from the committed dense model.
Use source-oriented metadata instead:

- `target_source = "committed_dense_argmax"` for `answerid`;
- `target_source = "committed_dense_topk_logits"` for `topk8/topk16`;
- `uses_gold_old = false`;
- optionally `commit_target_acc_seen` and `commit_target_acc_para` as audit metrics, computed against
  gold only for reporting, not for training.

The honest wording is:

> The old replay target is the dense model's committed answer/logit sketch at the time the fact was
> learned. On facts that were correctly committed, the hard answer target is gold-equivalent, but the
> procedure does not read old gold labels during replay.

This distinction matters for the larger research goal. We are not proving that arbitrary facts can be
retained without per-fact information. We are testing whether the necessary per-fact information can be
stored as a compact training-time teacher signal and then integrated into weights with no inference
memory.

## Negative Control

`ours_tgt_current` is the right negative control, but interpret it carefully. It is not mathematically
a zero loss: CE to the current argmax sharpens whatever the model already predicts on old prompts. So it
may act like a weak confidence regularizer over old keys.

That is still useful. The expected behavior is:

- if `current` is near `naive`, the target information in `answerid/topk` is doing the work;
- if `current` is much better than `naive`, then old-prompt exposure and confidence sharpening are a
  larger part of the effect than expected, and the result needs a more cautious interpretation.

I would keep it in the full run.

## Run Gate

I would allow the tiny smoke immediately, especially to catch missing `committed[(f, vi)]` keys,
shape errors in the top-k tensors, and whether `current` behaves as a negative control.

For the full `6 x 40 x 1000 x 2` run, I would first fix the aggregation issue above. Otherwise the raw
stdout may show the mode labels, but the durable JSON will not carry the audit fields needed for the
paper trail.

The planned full command is appropriate:

```bash
BK_REPLAY_K=-1 BK_REPLAY_TGT=snapshot \
BK_ARMS=naive,oracle,ours,ours_tgt_answerid,ours_tgt_topk8,ours_tgt_topk16,ours_tgt_current \
LD_ROUNDS=6 LD_PER=40 LD_STEPS=1000 LD_SEEDS=2 PYTHONHASHSEED=0
```

I would also set a unique `BK_OUT`, for example:

```bash
BK_OUT=docs/cloud_results/r36a2_compact_targets.json
```

so the artifact does not overwrite a prior lifecycle bakeoff result.

## Pass/Fail Interpretation

Keep the pass bar you stated:

- `all_seen_final >= 0.84`, or within about 0.04 of `ours`;
- `all_para_final >= 0.70`;
- `oldest_S0_forgetting <= 0.06`;
- newest stream within 0.03 of `ours`;
- base-hop drop <= 0.03;
- `replay_teacher_forwards = 0` and `uses_snapshot_teacher = false` for the winning compact arm.

My preferred interpretation table:

| outcome | interpretation |
|---|---|
| `answerid` matches `ours` | Strong practical win: one committed token per view per fact is enough to replace replay-time snapshot distillation on this benchmark. |
| `topk8/topk16` match but `answerid` fails | Compact soft teacher signal is useful; answer-only CE loses calibration or paraphrase robustness. Still a compute win, smaller storage win. |
| all compact targets fail but `ours` succeeds | Snapshot self-distillation is load-bearing; A2 becomes a clean negative and the capstone should say compact target replay was insufficient here. |
| `current` approaches compact targets | The result is less about stored target information than expected; inspect old-prompt confidence regularization before claiming compression. |

## Bottom Line

Proceed with R36-A2, but do not run the full pod until target metadata is included in the JSON summary.
I agree on Q1: no `snapshot_frozen` for the first pass. I agree on Q2: call the target a committed dense
teacher signal, not old-gold replay; avoid a `gold_equiv` flag and use source-oriented target metadata
instead.

If the compact arms pass, the contribution is exactly aligned with the project goal: independent facts
still require per-fact training-time information, but that information can be compact and can be
consolidated into a single dense model with no inference memory and no full joint retraining.
