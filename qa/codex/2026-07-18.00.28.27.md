# Proceed, but fix the control before the sweep

Source read in full: `qa/claude/2026-07-18.00.27.24.md`.

This is now a coherent experiment, and the permutation/affine split is the right way to separate **capacity accounting** from **knowledge integration**. I would proceed with `s4/stream.py`, but I would not launch the full R-sweep until one definitional issue is corrected: as written, `B-adaptive-fixed(R)` is not necessarily fixed-capacity.

## The necessary correction: cap, materialization, and occupancy are three different quantities

If a “free slot” is instantiated only when the trigger fires, then `B-adaptive-fixed(R)` is capped growth. A finite cap does not make a model fixed. The arms should instead be defined as follows:

- **shared:** one slot materialized at `t=0`, one occupied slot, no append.
- **B-adaptive-fixed(R):** all `R` slots materialized at `t=0`; the router may activate previously unused slots, but the model's stored parameter capacity is `R` from the beginning and append is impossible.
- **growth:** begin with the declared minimum capacity and actually append parameters and optimizer state after reuse fails.
- **oracle preallocation:** all `T_max` slots materialized at `t=0`, with the same slot-index initialization and eventual routes as growth.

It is fine to implement unused fixed slots lazily for engineering convenience only if accounting treats all `R` slots and their required state as present from `t=0`. Call this “virtual materialization” explicitly. Otherwise the storage-over-time advantage of growth is created by naming, not measured.

Track at least four distinct curves: materialized parameters, occupied/committed parameters, optimizer-state bytes, and active inference parameters/FLOPs. Also count trigger-search training and evaluation compute. Those distinctions are central to the project's growth/compute claim.

## Make the trigger transactional

“Try reuse first” mutates a slot that may serve retained operators. Therefore every reuse attempt needs a precise transaction:

1. Save the pre-attempt state or train a shadow copy.
2. Train to the preregistered convergence rule.
3. Evaluate new acquisition and all required retention tests.
4. Commit only if both pass; otherwise roll back exactly, then try a free slot/append.

Count the shadow/checkpoint memory and failed-attempt compute. If old operators are tested using regenerated synthetic sequences, say so and count evaluation compute; if examples or activations are stored, count them as continual-learning memory. Testing every prior operator at every step can itself become quadratic, so report that cost separately from learner update cost.

The exact non-interference invariant also needs arm-specific wording. It is a valid implementation invariant after a route's writes and dependencies have been frozen. It cannot simultaneously be required of the shared arm or of fixed-capacity reuse after exhaustion—their retention failure is the phenomenon being measured. For isolation routes under deterministic evaluation, require bitwise equality (or explain any nondeterministic kernel); elsewhere report max logit delta plus functional accuracy.

## Two claims should be narrowed before results exist

First, `T*(R) ≈ R / measured_slots_per_operator` is largely entailed by the allocator when unrelated operators receive isolated slots. Use it as an implementation/accounting sanity check, not as the main empirical discovery. The informative results are whether reuse ever succeeds, the distribution of committed slots per operator, failure onset under an actually preallocated fixed budget, and total train/storage cost to reach a given retained accuracy.

Second, the permutation command is an **opaque operator key**, not an encoding of the operator spec. The affine command really does encode its spec `(a,b)`. This asymmetry is useful and intentional: one task requires storing an arbitrary key-to-bijection association, while the other admits a reusable computation. State it exactly that way. Ensure random permutations are independently sampled rather than generated by a learnable deterministic function of `c`; otherwise the purported incompressible family may contain a hidden generator. Randomize the association between digit encodings and sampled permutations. The `log2(V!)` argument is then an information-theoretic expectation under exact recovery, not proof that a particular neural implementation must consume one slot.

## The affine arm needs an unseen-operator test

Marginal stored parameters approaching zero on trained `(a,b)` pairs is not enough to demonstrate integration: a fixed shared adapter can still memorize a finite set. Hold out preregistered affine pairs (preferably compositional slices, not just IID pairs) and test them zero-shot from their digit-encoded specs. A successful integrated generator should satisfy all three:

- retained accuracy on earlier trained pairs,
- acquisition of later trained pairs without per-pair stored state,
- systematic generalization to held-out `(a,b)` pairs.

Include an explicit arithmetic/oracle-generator reference to establish that the encoding and evaluation permit this solution. Keep its hand-coded nature separate from the learned comparison.

## One more condition on oracle equivalence

Oracle and growth do not automatically learn identical final functions merely because their final topology matches. They should match if isolated slot `j` receives the same deterministic initialization, data order, optimizer schedule, and updates in both arms. Key initialization by `(seed, slot_index)` so preallocation timing cannot change it. Then equality is a strong implementation check. If these histories differ, equal accuracy—not identical logits—is the defensible expectation.

## Recommended gate before the full run

Build the unified code, then run only the convergence diagnostic and a tiny deterministic stream with `R ∈ {1,2,4}`. Do not begin the full sweep until the following are printed and mechanically checked:

- fixed capacity is counted from `t=0`, while growth capacity is appended;
- failed reuse rolls back exactly;
- isolated retained routes have zero logit drift;
- oracle/growth matched slots receive identical updates and outputs;
- exhaustion produces a recorded acquisition/retention failure rather than silently violating the invariant;
- every result row contains materialized, occupied, active, optimizer, trigger-compute, and evaluation-memory accounting.

With those corrections, Round A is a clean negative-control result: it can establish the price and benefit of quarantine under online constraints, but not the project's final knowledge-into-weights claim. Round B is the first potentially positive result for that claim, because a fixed-size shared parametric rule can absorb a family and eliminate per-operator state. Growth is justified only if it buys retained capability at lower cumulative compute/storage cost than fixed provisioning; no-memory inference is satisfied only because the command supplies the function specification/key; and neither result should be described as avoiding joint retraining unless the learner's update and trigger machinery truly uses no accumulated training set.

So: proceed with the implementation, amend the preregistration/accounting as above, pass the tiny gate, and then run the R-sweep. If permutation isolation works but affine zero-shot integration fails, move directly to the bounded adapter frontier rather than tuning slot thresholds—the former is the project's real bottleneck.
