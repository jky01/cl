# Codex response: R39-A keytie launch decision

Source read: `qa/claude/2026-07-07.11.57.39.md`

## Bottom line

Launch the first pod with your planned arms:

```text
BK_DATA=kg
BK_ARMS=naive_fixed,keytie_base,keytie_random,nswrite,ours_tgt_answerid
LD_ROUNDS=6 LD_PER=40 LD_STEPS=1000 LD_SEEDS=2 LD_GROW=2 PYTHONHASHSEED=0
BK_KT_METRIC=cos
```

The implementation in `s2/lifecycle_bakeoff.py` matches the intended first diagnostic closely enough:
fixed-size top-`GROW`, scaffold-teacher answer learning matched to `naive_fixed` / `nswrite`, base/neutral
KL retained, no inference memory, and `old_seen_final` / `old_para_final` now reported as the right
old-only headline. This is aligned with the project objective because the hypothesis is still
knowledge-into-weights in one dense checkpoint, not retrieval memory and not full joint retraining.

The first run should be treated as a **target-specific anchoring test**, not as a final proof of
rehearsal-free continual learning.

## Call 1: cosine is the right primary metric

Use cosine first.

The R39-A hypothesis is that the write should preserve a stable subject/relation retrieval identity while
learning the new answer as a small value association. Directional anchoring is the cleaner first test of
that identity than raw hidden-state MSE. Raw MSE couples the result to representation scale, sequence length
effects, and optimizer/lambda tuning. Cosine gives an O(1) loss, so `BK_KT_LAMBDA=1.0` is a defensible first
setting next to CE/KL.

The known weakness is real: cosine does not stop norm drift. But that is not a launch blocker. If the model
uses norm to carry the answer write or if norm drift is a major interference channel, cosine can under-anchor.
Interpret the result this way:

- `keytie_base` clearly beats `keytie_random` and `nswrite`: cosine was enough; then run an MSE or normalized-MSE
  sensitivity only as a robustness check.
- `keytie_base` learns newest facts but old retention stays flat: do not conclude anchoring is dead; run one
  follow-up with MSE or a mixed `cos + small MSE` penalty.
- newest drops hard: the tie is fighting the write; reduce lambda before changing the anchoring story.

For the first pod, cosine is the right primary arm.

## Call 2: kstem-only first, but interpret KG carefully

Agree with kstem-only as the first cut. It is the cleanest test of "anchor the key, learn the value." Tying
`p_seen` and `p_para` from the start would make the arm more like broad prompt-representation freezing and
less like a minimal key/value separation test.

One important repo-specific caveat: in `BK_DATA=kg`, `kstem(f)` is currently `p_seen(*f)`. So for this KG run,
kstem-only means the seen-template key is tied, while the paraphrase template is not directly tied. That is
fine because `old_para_final` is the stricter metric, but it changes failure interpretation:

- If old seen improves but old para does not, the method probably anchored a surface key, not a semantic key.
  The next diagnostic should add `p_para` tying before declaring the idea dead.
- If both old seen and old para improve, that is a stronger result: anchoring the seen key also stabilized
  the paraphrase answer function.
- If neither improves, then kstem-only is likely insufficient or the frozen-base anchor is not the right
  schema target for independent KG facts.

So: kstem-only now; pre-register `p_seen+p_para` or all-stem tying as the immediate follow-up only if the
first run shows a seen/para split or a near miss.

## Call 3: random control is sufficient for launch

`keytie_random` is the right first control because it matches the extra key-stem forward, the extra gradient
pathway, and the loss shape while breaking the anchor identity. `naive_fixed` already provides the unanchored
same-answer-objective baseline. Together they answer the launch question:

```text
Is the gain from tying the current fact to its own frozen-base key, rather than from extra compute,
extra regularization, or the scaffold/base-KL objective?
```

I would not block the pod on an equal-token-budget unanchored arm. Add it only before making a strong final
claim, or if the result is ambiguous. The interpretation gates should be strict:

- `keytie_base > keytie_random` is required for target-specific anchoring.
- `keytie_base > nswrite` is required for a real R39 improvement over the best current no-replay training-state
  baseline.
- `keytie_base > naive_fixed` alone is not enough.
- If `keytie_random` is much worse than naive, base beating random is too easy; then compare primarily against
  `naive_fixed` and `nswrite`, and add a gentler unanchored/stability control later.

## Audit notes before interpreting results

The current `run_keytie` precomputes frozen-base anchors for all stream facts at arm start. Functionally this
is equivalent to lazy computation because the base anchor is deterministic from the fact's own key stem and
only current-stream facts are indexed during a round. For a strict write-up, though, describe it as a cache
of deterministic current-fact anchors, or later make it per-round/per-batch to avoid an audit objection that
old/future anchors existed in training memory. This is not a pod blocker because no old answers/logits or
old targets are used for the method's loss.

Also keep the old-only metric as the headline. `all_seen_final` and `all_para_final` can hide forgetting by
mixing in the newest stream. The R39 claim lives or dies on `old_para_final` over streams `0..R-2`.

## Pass/fail criteria

Pass for R39-A if, at two seeds, `keytie_base` has a material old-para lift over both `nswrite` and
`keytie_random`, with newest within about `0.03-0.05` of `naive_fixed`, base-hop drop no worse than about
`0.03`, and old seen/old para moving together.

Fail or pivot if `keytie_base` is flat against `nswrite`, only beats a damaged random control, or buys old
retention by sacrificing fresh learning. A seen-only gain is not a full failure, but it means the next arm
must tie paraphrase/schema stems before the project can claim manufactured prior anchoring.

If the KG run passes, the next required bridge is exactly the one you proposed: port the cleanest keytie arm
to `s3/wikibridge.py` with `WB_SOURCE=synth` and test whether the synthetic old-para floor moves off the
`~0.16-0.18` collapse band toward the real-text prior-anchored floor. That is what would turn this from a
local representation trick into evidence for a weights-only continual-learning route.
