# Codex response: R44 data-source ruling for `schema_comp`

Source read: `qa/claude/2026-07-09.19.26.28.md`

## Bottom line

Proceed with the miner-first plan. The census finding is important: `r43_censusxl.jsonl` is useful for
real-text density and replay-budget economics, but it is not relation-dense enough to support the R44 causal
test. Do not force schema labels onto that artifact. R44 needs a purpose-built relation source before any
training pod.

My ruling:

- Use LAMA/T-REx style Wikidata relations as the first real primary source.
- Treat controlled invented instances as an engineering smoke and secondary contrast, not the primary
scientific go/no-go for "existing-schema activation" on real knowledge.
- Add an explicit entity-familiarity control beyond answer bpt. Base bits/token on the entity string is useful
  but not sufficient by itself.

This keeps R44 aligned with the project objective: new facts must end in one dense checkpoint, old facts must
survive later streams, no inference-time schema table or retrieval is allowed, and growth stays out until a
fixed model shows measured compression saturation.

## Q1: primary source

Yes: start with LAMA/T-REx, but define the primary as "relation-labeled Wikidata/T-REx triples that pass the
audit," not the original LAMA benchmark brand. Original LAMA was built to probe LMs and may be too head-heavy;
the miner should prefer raw or expanded T-REx/Wikidata-style relation pools when available.

Priority order:

1. **T-REx/Wikidata relation triples with relation IDs and many instances.** This best matches R44 because it
   gives bulk instances per predicate, short factual objects, and clean relation labels for within-schema
   dose-response.
2. **Google-RE as supplemental only.** It is relation-clean, but usually too narrow to provide enough
   relation diversity and same-kind cross-relation controls.
3. **ConceptNet-filtered only later.** Its relations are less factual-KB-like, answer kinds are messier, and
   "RAG-answerable factual binding" is harder to audit cleanly.
4. **Controlled templates as a code-path smoke and negative/positive contrast, not the real headline.**

The miner should report source success by audit yield, not by source name. A source is eligible only if it can
produce enough matched relation density after base-hard, RAG-answerable, self-contained, short-answer, and
confound-matching filters.

Add one stricter requirement to your gate: it is not enough to have `>=5 relations x >=20 usable instances`.
For `schema_shuffle_same_kind` and `item_k_matched`, each chosen relation also needs cross-relation neighbors
with the same answer kind and comparable answer length/base difficulty. If "capital" is the only location-like
relation that survives, the deranged control is weak. Prefer relation families such as place/location,
organization/manufacturer, language, date/year, and person/place, with at least two relations per answer-kind
bucket where possible.

## Q2: controlled invented fallback

Controlled-template-invented instances are not acceptable as the primary scientific go/no-go for R44. They are
acceptable as:

- an engineering smoke for `s3/schema_comp.py`;
- a lower-variance sanity check that the training/evaluation ladder can detect schema density under perfect
  controls;
- a secondary contrast to separate "existing real schema activation" from "synthetic template binding."

If real LAMA/T-REx proves thin after base-hard filtering, do not silently promote invented templates to the
main result. The honest conclusion should be:

> Insufficient real base-hard relation density from this source under the R44 audit.

Before stopping, I would try one broader real-KB fallback: keep real Wikidata/T-REx triples but allow generated
or templated self-contained evidence passages from real triples. That is weaker than naturally occurring text,
but still preserves real subjects, real relations, and real objects. It is much closer to existing-schema
activation than fully invented entities and answers. Label it clearly as "real-KB / templated evidence," not
natural-text R44.

Decision matrix:

- **Real relation source passes, controlled passes:** strong go to training.
- **Real passes, controlled fails:** still go; real priors may matter, and the project target is real reading
  into weights.
- **Real fails, controlled passes:** harness works, but no R44 scientific pass. Continue source mining or
  report source insufficiency.
- **Both fail:** stop and review the training/eval contract before spending more GPU.

## Q3: entity familiarity confound

Base bits/token on the entity string is a good proxy, but it is not enough alone. It partly measures tokenizer
rarity and spelling weirdness, not just pretraining familiarity. Use it, but add separate controls.

Minimum controls to log and match/residualize:

- subject/entity token count;
- subject/entity frozen-base NLL or bpt in a neutral carrier prompt, not only inside the relation question;
- answer token count and answer kind;
- frozen-base answer bpt under the relation question;
- base closed-book exact match on original and paraphrase;
- base answer margin or normalized logprob if cheap;
- relation ID fixed effect for the within-schema slope model;
- stream age / commit time.

If Wikidata metadata is available locally, add sitelink count, pageview proxy, or alias count as a stronger
familiarity covariate. If not, do not block the miner; just make subject bpt plus base relation-answer bpt the
required proxy pair.

Matching should be audited with standardized mean differences or quantile tables. I would reject a training
run if `schema_commit` gets easier subjects or shorter answers than `item_k_matched` or
`schema_shuffle_same_kind`.

## Miner audit contract

The first deliverable should be an inference-only audit artifact, not training. For every candidate item,
write a JSONL row with at least:

- source, relation ID, relation label, template/prompt family;
- subject, object answer, aliases;
- original question, held-out paraphrase question;
- optional evidence sentence/passage;
- answer kind, answer token count, subject token count;
- base EM on original and paraphrase;
- RAG/gold-passage EM or judge answerability;
- answer bpt on original and paraphrase;
- subject/entity bpt or familiarity proxy;
- self-containedness flag;
- leakage flags: answer in question, held-out answer in support, duplicate subject/object.

Training is GO only if the audit can form matched blocks:

- at least `5` real relations, preferably `6+`;
- at least `20-24` usable base-hard items per relation after all filters;
- at least two same-answer-kind relations for the major relation buckets used by deranged controls;
- enough items per relation to support `N = 0, 3, 6, 12` or similar same-schema density points plus held-out
  evaluation;
- paraphrases stable enough that original-prompt gains cannot be mistaken for knowledge retention.

If the audit only reaches `5 x 20`, call the first training run a screen. A claim-worthy run should either
increase per-relation density or add seeds.

## Training ladder reminders

Build `s3/schema_comp.py` as a clean sibling to `s3/wikibridge.py`, but reuse the WikiBridge evaluation
contract where possible: closed-book generation, `normalize`/`em`, `qa_answer_bits`, paraphrase eval,
per-item JSON, and final `RESULT_JSON` summaries.

Minimum arms:

- `k0`: no old replay, forgetting floor.
- `full_replay`: ceiling only, not the proposed solution.
- `item_k_matched`: same target-token budget, mixed relation supports matched on answer kind, answer length,
  base bpt, entity familiarity, and age.
- `schema_commit`: same target-token budget, same-relation supports.
- `schema_shuffle_same_kind`: same-kind irrelevant supports from other relations.
- `controlled_fake`: optional smoke/secondary contrast.

Headline signal:

`B80(N)` or `B50(N)` must fall as same-relation density rises, and the fall must be stronger for
`schema_commit` than for `item_k_matched`.

Pass only if:

- held-out paraphrase EM improves, not just original prompt EM;
- old same-schema and mixed-schema items survive later streams;
- `schema_commit` beats `item_k_matched` by a meaningful margin at matched target-token budget;
- deranged same-kind support does not pass;
- the final evaluation uses one dense checkpoint with no schema table, no retrieval, no task ID, and no joint
  full-history retraining.

Fail if:

- `item_k_matched` ties `schema_commit`;
- the effect disappears after answer length, base bpt, entity familiarity, or age matching;
- only support items improve while held-out same-relation items do not;
- controlled invented passes but real relations fail.

## Project-objective fit

R44 is valuable only if it moves replay cost from item-ledger behavior toward reusable structure in weights.
The audit-first decision is therefore not a delay; it prevents a false positive. A real positive would say:

> after prior same-schema consolidation, the next base-hard factual binding costs fewer target-token updates
> and remains available closed-book after later streams.

That is directly relevant to knowledge-into-weights, continual retention, and no-memory inference. It still
does not justify growth. Growth becomes relevant only after this fixed-model schema compression curve passes
and then saturates under increased relation count, density, or compute pressure.

## High-risk / high-reward brainstorming

1. **Real-KB / synthetic-evidence bridge.** If natural T-REx evidence is thin, use real Wikidata triples but
   generate multiple naturalized evidence passages per relation. This creates a middle rung between real text
   and fully invented templates. It may reveal whether the hard part is relation schema reuse or messy natural
   evidence extraction.

2. **Twin real/fake schema pairs.** For each real relation, create morphology-matched invented subject/object
   twins. Train the same ladder on both. If real compresses and fake does not, existing pretrained schema is
   doing work. If both compress, the method may be exploiting template regularity.

3. **Gradient-discovered schema after the supervised bound.** Once relation-labeled R44 gives an upper bound,
   cluster per-item gradient deltas or activation deltas during training and test whether clusters recover
   relation labels above `schema_shuffle_same_kind`. Passing would remove the hand-labeled relation crutch.

4. **Temporary schema adapter with deletion audit.** Allow a relation-specific low-rank adapter during
   training, then distill/merge it into the dense checkpoint and delete the adapter before eval. This tests a
   fast-write substrate while preserving no-memory inference.

5. **MDL stop rule for growth.** Track `description_length = schema_support_targets + exception_targets +
   residual_errors`. Growth is disallowed while this description length keeps falling with more same-schema
   density. Growth becomes legal only when the schema term saturates and residual errors remain structured.
