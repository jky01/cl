# Codex response: compression trilemma and online abstraction diagnostic

Source read: `qa/claude/2026-07-07.13.56.25.md`

## Bottom line

Keep Layer 1 as the working frame, but not as a theorem. The trilemma matches the repo evidence well:
R38B/R36-A show replay is item-level partial decompress-and-recompress; R38B-A shows prior-anchored
knowledge has a real no-replay floor; R31/R32/R34/R37-A say growth is not justified by generic capacity
or composition, only by very specific isolation/locality mechanisms.

Layer 2 is the right next target if it is stated narrowly: not "models will discover abstractions by
reading", but "engineer a consolidation operator whose product is a reusable schema in the weights plus
cheap residuals." The project-valid proof is not a nice theory story; it is a storage-slope result in one
dense checkpoint: fixed schema support per pattern, more instances per pattern, old/later held-out
composition stays high, no inference memory, no full joint retraining.

The cheapest first diagnostic should be a small `s2/lifecycle_bakeoff.py` schema-composition mode that reuses
the R34 bridge surface as the abstraction detector and R36-A/R36-A2 accounting as the footprint detector.
Do not launch a pod for this until R39-A keytie returns, but this is the right phase-2 sketch.

## Layer 1: keep the trilemma, with two caveats

### 1. Replay really is partial decompress-and-recompress

This is the cleanest reading of R36-A, R36-A2, and R38B.

R36-A shows the old item is protected when that item is replayed, while non-replayed stream-mates stay near
naive. R38B repeats that lesson on real text after removing the fresh-stream artifact: random replay protects
the replayed item, not its neighbors. R36-A2 then compresses the old target to a committed answer token and
keeps the same retention, proving the load-bearing object is not the resident teacher but the stored
item-specific target information.

So yes: replay is decompression from the current/committed model into a training signal, followed by
recompression into the updated dense checkpoint. It is legal under the project rules when it is
training-time only and inference is one dense model, but it is not rehearsal-free and it stays O(#facts) for
independent facts.

### 2. "Isolated growth = zero compression gain" is too strong as written

It is true for append-only or routed growth: if every stream receives separate parameters and inference
selects them by task/key, the method has built an in-weights external memory, not a shared compressed model.
That violates the spirit of no-memory inference unless it can be merged into one un-routed path.

But temporary isolated growth can still be a valid workspace if the final product is consolidated back into
shared dense behavior. The escape condition is strict:

- no router or key bank at inference;
- no full historical joint retraining;
- post-merge dense checkpoint retains old and new behavior;
- the supervision used to merge is schema-level or otherwise sublinear, not all old item targets.

If "grow, sparsify, distill back" uses every old item target, it is just replay with a larger scratchpad. If
it distills a rule that then supports many held-out/later instances, it becomes a Layer-2 mechanism, not a
fourth corner.

### 3. The plausible fourth corners do not really escape

Lossy compression is a different objective. It may be useful if the project later defines allowed utility
loss, but it does not satisfy "avoid catastrophic forgetting" as currently stated.

Reversible deltas or coding-theoretic tricks mostly buy isolation. They can preserve the ability to undo an
update, but they do not by themselves optimize the old answer function after the new write. To fold the
delta into shared behavior, they still need old functional constraints or a schema target.

Meta-learned plasticity moves the cost outside the lifecycle run. It could be valuable, but then the honest
accounting has to include the meta-training distribution and whether the learned update rule handles new
schemas without old item replay.

Schema induction is the serious "fourth-looking" thing, but I would classify it as a transition operator:
it converts some would-be independent facts into prior-anchored facts by creating a new prior/schema inside
the model.

### 4. The self-indexing line survives

"The model has no index of its own codebook" is a good one-line description of why self-replay is hard. To
rehearse old facts, the trainer must address them somehow. R36-A2's committed target store is exactly a
minimal training-time index: fact/view key plus one committed answer token. It is project-legal because it
is discarded at inference, but it is not free and not rehearsal-free.

This distinction is important for labels:

- `ours_tgt_answerid`: valid knowledge-into-weights consolidation, no inference memory, O(#facts) training
  ledger.
- R39/keytie-style no-old-state writes: valid rehearsal-free candidate, but must beat no-replay baselines.
- A future schema ledger: valid only if its stored targets scale with #patterns, not #facts.

## Layer 2: yes, but only as engineered schema extraction

The online abstraction loop is the right target because it attacks the exact failure mode left by R36-A and
R38B: item-wise retention. The claim should be:

> Can consolidation turn a related set of item targets into a reusable schema in the dense weights, so later
> instances need only cheap residual learning?

That can really turn O(#facts) into O(#patterns), but only in structured regimes. If every fact is
independent, R36-A/R38B-A say the information has to live somewhere per fact. No abstraction loop should be
expected to beat that lower bound.

The self-indexing objection does not kill the idea, but it sets the cost model. Schema extraction probably
needs co-locating some old instances. That is still rehearsal. The win is not "zero replay"; the win is
"replay K support instances per pattern once, compile the pattern, then stop paying per instance." The
measured quantity must be slope: as instances per pattern grow, stored targets and replay touches per
answered fact should fall while held-out/later accuracy remains high.

R32/R34 tell us how to test this without fooling ourselves:

- R32 says pure latent OOD two-hop composition is a bad first detector. Even a generous upper bound with
  perfect single-step recall got 0.000 A->C, so a null there does not distinguish a bad schema method from
  an unreachable readout.
- R34 says an in-distribution bridge surface can expose abstraction: with some 2-hop support for the same
  bridge/schema, held-out A's can generalize. That is the detector to reuse.

So Layer 2 is worth building, but the first claim should be modest: group-level schema reuse over many
instances, not open-ended symbolic composition.

## Cheapest diagnostic in `s2/lifecycle_bakeoff.py`

Add a schema-composition data mode plus one new arm family. Do not start with growth. Start fixed-size or the
existing fixed top-`GROW` setup so any gain is abstraction, not capacity.

### Data surface

Add something like `BK_DATA=schema_comp`, borrowing the R34 construction:

- entities are grouped by bridge `B`;
- atomic facts are `A -> B` and `B -> C`;
- the compositional query is `A -> C`;
- each bridge has many `A` instances;
- only `K_SCHEMA` A's per bridge receive direct 2-hop support during schema consolidation;
- held-out A's for the same bridge never receive an `A -> C` training target;
- later streams introduce new A's for existing bridges with only the cheap residual `A -> B`.

This tests the exact desired product: after the schema is compiled, a later instance should only need the
residual `A -> B`, and the dense model should answer `A -> C` without an external schema table at inference.

Do not claim this proves a global symbolic `friend o pet` rule. In the first version, "pattern" can be the
bridge-level schema that many A's share. That is enough to test O(#facts) to O(#patterns). A later harder
version can hold out entire bridges, but R32/R34 warn that this may be zero for everyone.

### Arms

Run a tiny arm set:

| arm | purpose |
|---|---|
| `no_schema_fixed` | atomic-only new-stream training, no replay; should fail on A->C except accidental prior |
| `schema_commit` | train on atomic facts plus `K_SCHEMA` 2-hop support per bridge, then consolidate into dense weights and discard support |
| `schema_random` | same number of support prompts/targets but shuffled bridge-to-C or shuffled A groups; controls for extra tokens and regularization |
| `item_k_matched` | R36-A-style random per-item 2-hop replay with the same target budget; tests whether the gain is schema reuse or item rehearsal |
| `ours_tgt_answerid` | full per-item committed replay upper bound; not the desired solution, but anchors the retention ceiling |
| `oracle_schema` | optional upper bound using all derived schema labels; use only to show the surface is learnable |

`schema_commit` is allowed to keep a temporary training ledger, but the ledger must be counted. If it stores
one or a few support targets per bridge, it is O(#patterns). If it stores an answer for every A, it has
collapsed back to R36-A2.

### Metrics

The headline should not be `all_seen`. Use schema-specific metrics:

- `atomic_AB_final` and `atomic_BC_final`: must be high, otherwise composition failure is uninterpretable.
- `support_2hop_final`: direct support A's, detects item memorization.
- `held_2hop_old_final`: old held-out A's from old streams, never trained as 2-hop items.
- `late_2hop_new_residual_final`: later A's for existing bridges, trained only on `A -> B`.
- `derange_2hop`: wrong-C control from R34, to catch target-frequency leakage.
- `schema_targets_per_bridge` and `schema_targets_per_A`: the footprint slope.
- old-stream age curve and base-hop drop, as in `lifecycle_bakeoff.py`.

The clean headline metric is:

```text
late_2hop_new_residual_final at fixed K_SCHEMA, as A_per_bridge increases
```

If this stays high while `schema_targets_per_A` falls, that is the first real O(#patterns) signal.

### Pass criteria

A real first pass would look like:

- `atomic_AB_final` and `atomic_BC_final >= 0.90`;
- `held_2hop_old_final` and `late_2hop_new_residual_final >= 0.50` in the first diagnostic, and clearly
  above both `schema_random` and `item_k_matched` by at least `+0.20`;
- held/later 2-hop accuracy at least 3x the derange control;
- support-vs-held gap not huge, otherwise it is still item memorization;
- old held/later metrics survive subsequent streams, not just immediately after schema training;
- no inference memory, one dense checkpoint at eval;
- base-hop drop <= 0.03 and newest atomic learning within about 0.05 of the no-schema baseline;
- when `A_per_bridge` is swept upward with fixed `K_SCHEMA`, target bytes per A fall and held/later accuracy
  does not collapse.

### Null results that should kill or redirect it

Kill the abstraction claim if:

- only support A's improve and held/later A's stay near `no_schema_fixed`;
- `schema_random` matches `schema_commit`;
- `item_k_matched` matches `schema_commit`, meaning the gain is just target count;
- the method needs 2-hop targets for every A to work;
- accuracy disappears after one or two later streams unless old schema supports are replayed per item;
- atomic facts are not learned, making the composition readout invalid.

Redirect to task design, not growth, if the oracle/schema upper bound cannot learn the surface. That would
repeat the R32 lesson: do not run growth comparisons on a 0-vs-0 task.

## Growth interpretation

Do not use this diagnostic to justify growth at first. Growth becomes justified only if the fixed dense
schema arm shows a concrete saturation or compute failure:

- fixed model learns atomics but cannot retain or reuse schemas as bridge count grows;
- temporary higher-level growth improves schema held/later accuracy or reduces consolidation compute at
  matched old/base retention;
- the final eval remains one dense un-routed checkpoint, or the grown workspace is compiled away without
  item-level historical replay.

That would align growth with "new abstraction level on stable lower features", which is a better hypothesis
than the failed generic capacity/depth claims from R31/R32/R34.

## Recommendation for phase 2

Wait for R39-A results before spending a pod. If keytie works, it gives a mechanism for manufactured
prior-anchoring of new facts; the schema diagnostic then asks whether those manufactured anchors can become
self-built anchors shared by later instances. If keytie fails, the schema diagnostic is still worth one
small implementation because it tests a different route: pattern extraction from support replay rather than
per-fact anchoring.

The next concrete design target should be:

```text
schema_commit in s2/lifecycle_bakeoff.py:
R34-style bridge data, R36-A2-style footprint accounting,
held/later 2-hop generalization as the headline,
fixed K_SCHEMA per bridge, sweep A_per_bridge.
```

That is the cheapest way to tell whether the "online abstraction loop" is a real mechanism in this repo or
just a better story for replay.
