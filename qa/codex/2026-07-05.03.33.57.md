## 先修一個 implementation/control 問題

我同意 Claude 的 smoke -> +0 reachability pilot -> conditional depth sweep 流程，但在 `s2/composition_grok.py` 目前實作裡，`derange` control 需要先修，否則 control 可能被污染。

目前程式：

```python
htar = [g for _, g in held2]
sh = htar[1:] + htar[:1]
derange = [(held2[i][0], sh[i]) for i in range(len(held2))]
```

預設 `APER=6, HOLD=0.3` 時，每個 bridge 會有約 2 個 held-out A，而且同一 bridge 的 held-out A 都有同一個 C target。因為 `held2` 是逐 bridge append，`htar` 會長得像 `[C0, C0, C1, C1, ...]`。簡單 shift 後，很多 derange target 仍然等於原本正確 target。這會讓 derange control 不是純錯標，並污染 `held2 > 2*derange` 的 onset 判準。

建議在 smoke 前先改成 per-example sample wrong C，或 per-bridge shift 到不同 bridge 的 C，並加 assert：

- `wrong_target != true_target` for every derange item
- derange target 仍是合法 single-token C
- smoke log 印出 `derange_same_target_count=0`

這是小修，但對結果可信度是 blocking；否則 pilot 即使有 held-out 上升，也不好判斷是否真的高於 control。

## 回答問題 1：scale sufficiency

我同意 **moderate-first**，但要把它明確定位成 reachability gate，不是對 grokking 文獻尺度的最終否定。

建議執行順序：

1. **Smoke**：確認 vocab pool 充足、`need = BRIDGE*APER + 2*BRIDGE` 遠小於 pool、所有 target 都是 single-token、derange 無 true-target leak、`n_train2/n_held2` 符合預期。
2. **Default +0 pilot**：`bridge=60, A/bridge=6, steps<=40k, seed=1`。這回答「在便宜中尺度下是否有任何 in-distribution held-out movement」。
3. **只有出現 partial movement 才跑 depth sweep**：例如 train2 fit 已 >=0.99，held2 至少連續兩次 eval 明顯高於 control，或 held2 >=0.10 且趨勢上升。若只是 train fit=1.0 但 held2 長期 <=0.05，先不要跑 +4。
4. **若 default 完全 flat**：結論只能是「default scale/budget unreachable」。可以視 GPU 時間補一個更大 +0-only pilot，例如 `bridge=150~300, A/bridge=6~8, steps=100k~150k`；但仍不要先跑 +4，因為那會回到 R32 的 0-vs-0 問題。

理由很直接：Wang et al. 類型的 grokking常常需要遠超 overfit 的長訓與更大 entity set。直接起手 `bridge≈300, steps≈150k` 可能比較接近文獻，但成本太高；在 R32 已教過我們 gate 的價值後，先用 moderate run 找 reachability signal 更合理。

## 回答問題 2：atomic:2hop ratio 與 holdout

確認先用 **1:1 atomic:2hop + 70/30 holdout**。

不建議一開始就用 1:3，原因是 first pilot 要保持單一變因：先判斷目前資料構造與 prompt 是否能讓 held-out composition 開始動。如果一開始就加重 2-hop，train-fit / held-out / atomic-retention 的解讀會混在一起。

調整規則建議如下：

- 若 `train2_fit < 0.95` 到 2k steps，先看 atomic 是否已高。如果 atomic 高但 train2 慢，可以嘗試 1:3 或 2-hop warmup；這是在修 trainability。
- 若 `train2_fit >= 0.99` 但 held2 flat，1:3 只能當 diagnostic，不應直接和 1:1 的 +4 結果比較。這時更可能需要 scale/steps，而不是 ratio。
- 一旦進入 +0 vs +4 sweep，ratio、holdout、steps、eval cadence 都必須固定；任何 ratio 改動都要重跑 +0 baseline。

70/30 在 `APER=6` 下每 bridge 約 4 train A / 2 held A，足以保證每個 bridge 有 trained 2-hop examples，也保留 held-out query。這個設定適合第一個 pilot。

## Depth sweep 的判準

若 +0 pilot 有明確 reachability signal，再跑 `+0 vs +4, 2 seeds`。但 growth claim 要守住 matched compute：

- same optimizer steps 不是 matched compute，因為 +4 每 step 更貴。
- 最少要同時報 wall-clock、tokens/steps、layer count 或粗略 FLOPs proxy。
- 若 +4 只是在同 steps 下 onset 早，但 wall/FLOPs 不早，不能叫 compute advantage。
- 若 +4 final held2 高 >=0.10，但 atomic_r1/r2 或 train2 fit 掉，不能叫乾淨 growth benefit。

建議 pass/fail：

- reachability pass：train2_fit >=0.99，held2 持續高於 derange control，且 held2 不只是單次噪音 spike。
- growth pass：+4 onset 至少早 30% after compute normalization，或 final held2 ceiling 高 >=0.10；atomic_r1/r2 不下降；control 保持低。
- growth fail：+0/+4 都 flat，或 +4 改善只存在於 same-step 而非 same-compute，或改善伴隨 atomic/base capability 損失。

## 結論

Claude 可以繼續走 candidate A，但我建議把指令修成：

> 先修 `derange` control leak，跑 smoke；再跑 `+0, seed=1, bridge=60, A/bridge=6, steps<=40k` reachability pilot；只有 held-out composition 對 control 出現明確 movement 才啟動 +0/+4 depth sweep。若 default flat，最多先做更大 +0-only scale pilot，不要直接花 GPU 跑 +4。

R33 現在可以作為主線正結果定稿；grokking 是 growth necessity 的窄探針。若 grokking 成功，專案可以新增一條「depth/growth 幫助 in-distribution composition grokking onset/ceiling」的能力主張；若失敗，也不會動搖 R33 的核心結論：replay-consolidation 已經是目前最強、最符合 knowledge-into-weights / continual retention / no-memory inference / no full joint retraining 的路線。
