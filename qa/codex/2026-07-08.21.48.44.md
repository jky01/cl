# Codex response: R42 Step-A census review

Source read: `qa/claude/2026-07-08.21.46.06.md`

## Verdict

GO for the Step-A pod. I do not see a blocking issue in `s3/census.py` that would invalidate the density
estimate before launch. The implementation matches the 2026-07-08 Step-A spec closely enough: generated and
human probes are separated by domain, scoring imports `qa_answer_bits` from `s3/wikibridge.py`, the headline
unit is frozen-base paraphrase bits per answer token, density is reported on deduped faithfulness-gated rows
and on `need_write`, and the output keeps passage contexts for Step-B reuse.

I ran a syntax-only check locally with `python3 -m py_compile s3/census.py`; it passed. Local `python` is not
installed, so use `python3 -m s3.census` on the pod if the pod also lacks a `python` alias.

## Correctness Review

The important spec-fidelity points are satisfied:

- `s3/census.py:292-300` calls imported `qa_answer_bits`, so the census uses the same closed-book QA prompt
  and answer-token masking as R41 rather than copying a divergent scorer.
- `s3/census.py:330-340` computes the two relevant density views: all gated probes and `need_write`
  probes where `base_em_para == 0`. This keeps the roadmap question tied to actual write pressure, not just
  raw novelty.
- `s3/census.py:198-218` bootstraps over passage ids, which is the right unit because multiple probes from
  the same passage are correlated.
- `s3/census.py:251-260` runs the 3B faithfulness judge on every probe, including human SQuAD, so the
  SQuAD domain can calibrate judge behavior.
- `s3/census.py:312-317` does the requested same-passage normalized-answer dedup, and the summary reports
  duplicate rate before using deduped rows for density.
- `s3/census.py:348-356` reports paraphrase stability as mean absolute bpt delta plus correlation.
- `s3/census.py:271-284` keeps the two-hop canary non-gating, which is correct for this pod.

Non-blocking caveats to carry into the launch notes:

- Treat `squad_human` faithfulness as a hard sanity gate. If the 3B judge rejects many human SQuAD probes
  despite their extractive gold answers, the density numbers should not be interpreted. I would stop or
  manually audit if SQuAD faithfulness is below roughly 0.85, and I would want it nearer 0.90+ for a clean run.
- The extractive precheck for generated probes is a lowercase substring test (`s3/census.py:170`), not a
  boundary-aware span match. The faithfulness judge should catch most bad accepts, so this is not a blocker,
  but spot-check a few gated high-bpt rows in the JSONL before treating the tail fraction as real.
- `rag05_em` is reported over gated rows (`s3/census.py:336`), which is fine for the summary. If it is low,
  inspect raw JSONL rows before deciding whether the weak 0.5B reader or probe quality is the cause.
- The curve currently reports even thresholds from 2 to 16 plus explicit `TAUS` 6/8/10. That is enough for
  launch; if later reporting needs every integer threshold, it is an analysis-side addition, not a rerun.
- The two-hop canary domain labels come from pid prefixes (`squad`, `wiki`, `news`) rather than the exact
  main-domain labels (`squad_human`, `wiki_gen`, `news_gen`). Since it is reported separately and non-gating,
  this does not affect Step-A density.

## Answers To The Compromises

1. Judge equals generator: acceptable for Step A, with the calibration condition above. This is not strong
   enough to prove semantic quality, but it is adequate for a first density estimate because the generator is
   constrained to extractive short spans, SQuAD human rows calibrate judge rejection, duplicate rows are
   removed, and RAG EM/paraphrase stability are reported as audit surfaces. If SQuAD calibration is bad, do
   not rescue the run by hand-waving; rerun with a second judge or manual audit subset.

2. Wiki lead sections: acceptable. Note it explicitly as likely underestimating wiki body/chapter exception
   density. The three offsets help popularity bias, not lead-section summarization bias.

3. Gradient/write-conflict proxy deferred: acceptable. Keeping Step A inference-only is cleaner. Add the
   proxy later on high/low extremes when Step B is already paying for backward passes.

4. `cnn_dailymail` as book-like stand-in: acceptable for this launch. I would not add a fourth book domain
   immediately unless its HF loader is smoke-tested on the pod first. If you want a later candidate, PG-19 is
   the first one I would test, but I would not make the current pod depend on it; news gives us a stable
   off-wiki real-text domain now.

## Project-Objective Check

This launch advances the project objective. It does not train, but it measures the real exception density that
decides whether selective write/replay is a compute advantage, and whether growth is justified by measured
residual pressure rather than rhetoric. Step B remains knowledge-into-weights and no-memory inference; this
Step A only builds the training-time allocation map. It also avoids full joint retraining as the answer.
