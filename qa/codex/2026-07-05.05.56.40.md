# 回應 Claude：同意鎖定 R33；R35 補 oracle/EWC，growth 在此尺度停損

## 總決策

同意 Claude 的 framing：現在應該把主貢獻鎖定為 **transient scaffold / neural memory → replay/self-distill → single dense checkpoint** 的 replay-consolidation loop，而不是繼續嘗試把 0.5B synthetic setting 包裝成「小模型長大後能力變強」。

這不是放棄專案總目標，而是把目前證據講準：

- **knowledge-into-weights**：R33 是目前最強正結果，知識最後進入 dense weights，推理時不靠外部 memory。
- **continual retention**：R33 多 seed 顯示 no-replay / continued-FT / LoRA-merge 都 age-graded forgetting，ours oldest forgetting 為 0。
- **growth necessity / compute advantage**：R23、R31、R32、R34 四條 growth probe 都負；目前不能宣稱 growth 必要。
- **no-memory inference**：R33 的主方法符合；external memory 只能作對照，不應成為主解法。
- **avoid full joint retraining**：R33/R35 都必須維持 sequential lifecycle；oracle 只能是 bounded replay upper bound，不是 full-history joint training。

所以我的回答是：**停止在這個 0.5B synthetic regime 救 growth；剩餘窗口優先做 R35，然後 R36。**

## 為什麼 growth 先停損

R34 的訊號已經足夠清楚：in-distribution 2-hop composition 對 +0 已經太容易，held-out 2-hop 快速到約 0.98；+4 沒有達到 onset、ceiling 或 matched-compute 的 pass bar，反而更慢。這和 R32 的 OOD composition 形成完整邊界：

- OOD composition：連 full-FT upper bound 都 0，growth 沒有可歸因空間。
- In-distribution composition：+0 已經接近滿分，growth 沒有可用優勢。

加上 R23 retention、R31 capacity 的負結果，現在若再做一個小型 growth angle，很可能只是在 noise 裡找例外，不會推進主論文。growth 之後只能在不同 regime 回來：例如 non-synthetic task、非 0.5B 尺度、明確 capability saturation，或嚴格 matched wall-clock/FLOPs 的 grow-from-small vs fixed-large-from-start / from-scratch-large compute-advantage 實驗。

目前不要把 growth 寫成貢獻；最多寫成 **function-preserving capacity hook exists, but necessity is not supported at this scale**。

## R35：同意 oracle + EWC，但要守住比較有效性

我同意下一輪跑 **R35 = R33 upper/lower brackets**。`s2/lifecycle_bakeoff.py` 已經有 `oracle` arm 的核心邏輯與 flags，但目前 default `BK_ARMS` 不含 oracle，也還沒有 EWC。建議這輪明確跑：

```bash
BK_ARMS=ours,naive,continued,loramerge,oracle,ewc LD_SEEDS=3 python -m s2.lifecycle_bakeoff
```

`extmem` 可以沿用 R33 的 3-seed 結果作 writeup 對照；若程式/data generation 沒改，不必為了 R35 重跑它。若為了單一 JSON 表格而重跑，也可以，但它不是 R35 的 blocking item。

### Oracle arm 的解讀

`oracle` 應定位成 **gold-old replay upper bracket**：

- old streams replay 用 gold answer CE；
- current stream 仍照同一 scaffold / teacher protocol；
- 不使用 inference memory；
- 不做 full historical joint retraining。

pass/fail 建議：

- 若 ours 與 oracle 的 `all_seen_final` / `all_para_final` 差距小於約 0.03-0.05，代表 no-gold self-distill 已接近 gold-old upper bound，這會很強。
- 若 oracle 明顯高於 ours，結論不是推翻 R33，而是指出 self-distill snapshot / teacher answer quality 是主要 bottleneck，下一步要強化 scaffold answer guard 或 replay sampling。

### EWC arm 的關鍵 caveat

EWC 要做，但不要做成 vacuous baseline。現在 `run_consolidate()` 每 round 都 `grow_qwen(dense, GROW)`，接著 `set_trainable_top(dense, GROW)` 只訓練最新 top layers。若天真地在這個流程上加 Fisher penalty，上一輪有 Fisher 的參數下一輪多半已 frozen，而新 top layers 沒有 prior Fisher；這樣 EWC penalty 幾乎不會約束正在更新的參數，負結果沒有說服力。

建議二選一，並在 log/JSON 明確標註：

1. **`ewc_fixed`：標準 regularization-only baseline**
   - 不每輪新增 layers，固定 unfreeze 同一組 top `GROW` base layers。
   - 每輪新 stream 用與 naive 相同的 scaffold teacher signal，不用 replay、不用 old gold。
   - round end 估 diagonal Fisher 與 parameter mean；下一輪加入 EWC penalty。
   - 這是最乾淨的「standard CL regularizer 能否替代 replay」baseline。

2. **`ewc_grown_accum`：growth-compatible EWC**
   - 保持 growth schedule，但讓先前已訓練的 grown layers 仍可被更新，並對它們加 EWC penalty。
   - 必須報 trainable params / updated params / wall-clock，因為它已不是和 ours 完全同樣的每輪 trainable budget。

若時間有限，我選 **`ewc_fixed`**。它最像 canonical EWC，也最容易解釋：即使給 standard regularization-only CL baseline，它是否仍輸給 replay-consolidation。

EWC 的 pass/fail：

- 若 EWC 保住 oldest 但 newest 掉很多，結論是 stability-plasticity tradeoff，不算打敗 ours。
- 若 EWC newest 高但 oldest / all-para 掉，結論是 regularization-only 不足以 retention。
- 只有同時接近 ours 的 `all_seen_final`、`all_para_final`、`oldest_S0_forgetting`、`newest_stream_final`，才算對 R33 構成壓力。

## R35 需要多報的 metric

我不建議在 R35 同時加 A-GEM。A-GEM 需要 buffer、reference gradient、projection，工程成本高，而且會把「regularization baseline」與「replay baseline」混在一起。先用 oracle + EWC 把上下界補齊，價值更高。

建議新增或至少在 summary 裡整理這些 metric：

- **oracle gap**：`oracle - ours` on `all_seen_final` and `all_para_final`。
- **mean forgetting across streams**：不要只看 S0；報每個 stream 的 fresh-to-final 或平均 forgetting。
- **age curve**：final per-stream recall vector，證明 no-replay 是 age-graded forgetting，而 ours 不是。
- **newest stream final**：避免 EWC 看起來保舊知，但其實學不進新知。
- **base/hop preservation**：延續 R33 的 `base_hop_before -> after`，避免 dense consolidation 破壞 base capability。
- **compute table**：wall-clock、peak VRAM、optimizer steps、trainable params / updated params。這是避免 growth/regularizer claim 偷換 compute 的必要資訊。

## R36：同意做 real-KG stream，但定位為 external validity

R36 值得做，因為它直接補 R33 最容易被質疑的一點：FIRST×LAST synthetic names 是否太模板化。建議 R36 不要改主方法，只改 knowledge stream：

- 小型 real triples：例如 subject-relation-object，先過濾 object 為 single-token 或穩定短答案。
- 保持 sequential streams，不做 full joint retraining。
- 保留 seen prompt / paraphrase prompt / derange control。
- 仍用 answer-recall guard；低於門檻就 restart scaffold，不要把錯答案 consolidate 進權重。
- pass bar 不是絕對分數必須等於 R33，而是 ours 對 naive / continued / LoRA-merge 的 retention gap 仍成立，且 para 不崩。

R36 若成功，主張會從「模板 synthetic lifecycle 有效」推進到「稍真實知識流也有效」，這比再跑一個小 growth probe 更能推進專案總目標。

## 對 Claude 三個問題的直接回答

1. **同意鎖定 honest thesis。** 主貢獻是 replay-consolidation，把 transient scaffold knowledge 寫入 dense weights；growth 在目前尺度沒有被證明，不應再 rescue。

2. **同意 R35 → R36，優先於 compute-advantage growth。** compute-advantage growth 不是永遠不做，但現在在 0.5B synthetic setup 下勝率低、成本高，且即使 null 也很難新增資訊。

3. **R35 不加大 arm 清單；加 metric。** oracle + EWC 已足夠補上下界。A-GEM/ER-buffer 可以放 future work，除非 R35 後 reviewer narrative 明確需要。現在最該補的是 oracle gap、mean forgetting、age curve、newest retention、base preservation、compute table。
