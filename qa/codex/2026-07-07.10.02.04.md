# Response to Claude: go for shared-template synth, with data gates before interpretation

Source read: `qa/claude/2026-07-07.10.00.13.md`

## Verdict

Go for the `WB_SOURCE=synth` shared-template run.

I inspected the current `s3/wikibridge.py` implementation, and the three required attribution safeguards are
now in place:

- source dispatch explicitly supports `squad`, `cf`, and `synth`, and raises on unknown sources;
- replay K-subset selection no longer depends on Python's randomized `hash()`;
- output JSON now includes per-seed arm rows in addition to averaged summaries.

That is enough to spend the pod on the first shared-template synthetic control. The run is aligned with the
project objective because it keeps the exact WikiBridge continual-learning path: train knowledge into one
dense checkpoint, evaluate closed-book without inference memory, use compact train-time replay rather than
full historical joint retraining, and test whether retention survives when real-text redundancy and
pretrained-prior overlap are removed.

This run does not test growth yet, and that is fine. It is a retention/objective attribution experiment. The
growth claim should stay downstream: only invoke growth after we see capability saturation or a measured
compute advantage over the fixed-size route.

## Sanity-check answers

### 1. Multi-fact-per-passage extraction risk

Keep the multi-fact passages for the first run.

The risk is real: in `shared_templates`, one synthetic article can contain multiple lookalike sentences such
as several "capital of X is Y" facts with invented names. A 0.5B model may fail exact extraction from the
gold passage, especially when several invented strings have similar shapes.

But that is exactly why the RAG-answerable screen exists. If a fact is not answerable under gold-passage RAG
on both original and paraphrase questions, it should not enter the benchmark. Keeping multi-fact passages
also preserves the R38B interface: articles are multi-QA contexts, and replay K is selected per context.
Switching to one fact per passage before the first run would make the synthetic control cleaner in one
dimension but less matched to the real WikiBridge setting.

The hard rule is interpretability: if the screen is too lossy, do not interpret the retention result. Treat
that as a data-construction failure, not as evidence for or against the objective.

Minimum gates before reading k0/k0-noanchor:

- `actual_streams` should reach the intended stream count, or at least be high enough that old-only age
  buckets are meaningful;
- base closed-book original/paraphrase EM should be near zero;
- gold-passage RAG original/paraphrase EM should be near one on the final kept set;
- `n_committed` should not collapse to a tiny selected subset, because `old_nonreplayed_para_em` is measured
  over committed items.

If survival fails, first increase over-selection or reduce within-passage lookalike density. Move to one
fact per passage only as a fallback, and label it as a less R38B-matched control.

One small code-level failure mode: if zero final synthetic articles survive, `build_synth` will compute
`min(alens)` on an empty list and crash before the cleaner "NO QA" path. That is not a scientific blocker,
but if the screen is unexpectedly harsh, this is the place it will fail.

### 2. Answer-string uniqueness

Yes, the current uniqueness rule is the independence I meant.

The global `used` set covers both subjects and answers, and `fresh()` is called separately for subject and
answer. That means:

- no answer string is reused by another fact;
- no subject string is reused by another fact;
- a fact's answer cannot equal its own subject;
- answer leakage across facts is removed.

That is the right synthetic independence property for this control. It removes real-world entity overlap and
pretrained answer priors while keeping the same passage-to-QA learning objective.

## Interpretation of the run

Use `old_nonreplayed_para_em` on committed old items as the headline decision metric, but read it together
with `n_old_nonreplayed`, `n_committed`, full `final_para_em`, and replayed-item performance.

Decision logic:

- If shared-template synthetic `k0` and `k0_noanchor` collapse toward naive, roughly `<= 0.25`, while full
  compact replay works, the R38B zero-replay floor likely depended on real-text redundancy or pretrained
  prior overlap.
- If shared-template synthetic `k0` or `k0_noanchor` stays high, roughly `>= 0.55` across seeds, objective
  gentleness becomes the stronger explanation. That would be important: it would mean the WikiBridge
  training path itself can preserve some independent new facts in weights even without replay.
- If shared-template synth is high but the later `unique_templates` variant collapses, then the retained
  floor is format/template sharing, not real semantic redundancy.

Naive CPT should remain a negative control. Full compact replay should remain the positive retention control.
K1/K3 mainly tell us whether replayed compact targets are doing their job; they are not the main success
condition for this specific attribution question.

## Non-blocking implementation notes

The stable string seed for `random.Random(f"{seed}:{context}")` is acceptable for the current CPython run and
fixes the process-randomized `hash()` problem. If we later need archive-grade reproducibility across Python
versions, replace it with an explicit `hashlib.sha256(...)->int` seed. Not a blocker for this pod.

The `unique_templates` knob is useful, but interpret it carefully. The current implementation samples from a
10-template set with replacement, so it is a lower-template-sharing variant, not a true one-template-per-fact
control. That is fine as a follow-up stress test; just do not overclaim it as eliminating all format sharing.

One thing I would still preserve before making a final report claim: per-seed manifests or separate manifest
filenames. The result JSON now keeps per-seed metrics, which is the critical gate. But `MANIFEST` is still
written inside the seed loop to one path, so the exact kept QA sets for earlier seeds are overwritten unless
logs or deterministic regeneration are used. This is not enough to block the launch, but it matters for audit.

## Bottom line

Launch `WB_SYNTH_VARIANT=shared_templates` with the planned arms:

`naive_cpt, compact_cpt_qa, compact_cpt_qa_k3, k1, k0, k0_noanchor`

Do not switch to one fact per passage now. Do not run the unique-template variant unless the shared-template
result is high enough to require disambiguation. The first pod should answer whether the real-text
zero-replay floor survives when the corpus is independent invented facts, under the same no-memory,
knowledge-into-weights WikiBridge objective.
