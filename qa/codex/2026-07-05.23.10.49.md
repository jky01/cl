## How to judge the three runs

Use the 12-stream `nswrite` baseline as the immediate comparator:

```text
baseline final age curve:
[0.25, 0.45, 0.28, 0.38, 0.28, 0.57, 0.45, 0.35, 0.40, 0.65, 0.78, 0.85]
baseline all-seen: 0.474
baseline final newest: 0.85
baseline final eff-grad: 0.237
```

The pass bar should stay strict:

- `all-seen >= 0.55` is the minimum interesting result; `>= 0.57` is the cleaner `+0.10` win.
- Final newest must remain near the baseline and preferably match the full `fresh_diagonal`, not only stream 11.
- S0-S5 must improve materially. A run that only improves the last few streams is just shorter forgetting exposure.
- Base/hop and all-para should not degrade, because the project objective is not narrow seen-prompt memorization.
- Any run with lower fresh learning should be labeled "underwrite" rather than "retention win."

One nuance: compare fresh to each stream's scaffold ceiling, not only to a flat `0.90` target. The seed-0 scaffold answer-recall in the pilot varies by stream (`0.80`, `0.78`, `0.73`, etc. appear in these lifecycles), so a fair adaptive target should be "near teacher/scaffold capability" rather than an absolute recall threshold for every stream.

## What each fixed-budget outcome means

If `LD_STEPS=300, BK_NS_LR=1.5e-4` improves old retention while fresh stays matched, the simplest interpretation is that the default `1000` steps are overwriting after the new stream is already installed. Move immediately to adaptive write budgeting.

If `LD_STEPS=100, BK_NS_LR=1.5e-4` improves retention but fresh drops, that is not a win. It only establishes the underfit boundary.

If `LD_STEPS=300, BK_NS_LR=7.5e-5` beats the 300-step full-LR run at matched fresh, then per-step optimizer displacement matters, not just total step count. The next adaptive rule should tune both step count and LR/trust-region size.

If all three are flat at matched fresh, the residual is not mainly fixed-budget drift magnitude. Then the next method should change the update primitive, not continue sweeping steps.

## Adaptive write budget if drift helps

The clean follow-up is an early-stop writer:

```text
for each stream:
  train nswrite in small chunks
  evaluate new-stream seen + para recall
  stop when recall reaches min(scaffold_answer_recall - tolerance, target_cap)
  enforce max steps so bad scaffolds do not overtrain forever
```

Suggested first policy:

- evaluate every `50` or `100` steps;
- require both seen and para to be within about `0.05` of the scaffold's answer recall when possible;
- cap at `1000` steps;
- log actual steps used per stream, fresh diagonal, age curve, all-para, hop, and `eff-grad`.

This stays aligned with the project objective: new knowledge goes into dense weights, old knowledge is protected better, no old prompts are replayed in the online loss, and inference remains memory-free. It also gives a compute advantage if many streams stop early.

Only after the adaptive 12-stream result clears the pass bar should it be run at 24 streams. If the 24-stream run preserves the gain, then add another seed before making a claim.

## If drift is flat

Then I agree with the locked branch: move to rank-bounded functional editing before slotwrite.

The reason is that gradient projection constrains the step direction, while the observed failure is old-function movement after many nonlinear optimizer steps. Functional editing should constrain realized local behavior:

```text
min_Delta ||Delta W X_new - R_new||^2 + lambda ||Delta W||^2
subject to ||Delta W X_old||^2 <= epsilon
```

For this repo, the first implementation should reuse the existing hook machinery:

- store compressed old input sketches per target Linear at commit time, analogous to `Umap`;
- additionally store local old outputs or projected output statistics, so preservation is about `W X_old`, not just input directions;
- solve a rank-bounded update for each target Linear after a new-stream write proposal;
- discard raw prompts and keep only the compressed training state;
- evaluate exactly like `nswrite`: fresh diagonal, final age curve, all-seen, all-para, hop, and no inference memory.

This is still not joint full retraining, and it is closer to the desired endpoint than permanent per-stream slots: one dense checkpoint with knowledge incorporated into weights.

## Slotwrite remains diagnostic

Slotwrite is useful, but not as the next project claim. Its role should be to separate bottlenecks:

- If slotwrite retains old streams before consolidation but fails after consolidation, the consolidation operator is the problem.
- If slotwrite retains and consolidates successfully into one dense or learned-routed grown model, then growth may become evidence-backed.
- If slotwrite only works by keeping history-proportional per-stream modules active forever, it risks becoming parameterized external memory unless the compute/parameter advantage is explicit.

So the current ordering is right: drift sweep, adaptive budget if positive, functional editing if flat, slotwrite as an interference-isolation oracle, and growth only after saturation or compute advantage is demonstrated.
