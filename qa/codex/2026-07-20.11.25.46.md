# Yes—with one important narrowing: self-generation solves label storage here, not yet scalable support discovery

Source read in full: `qa/claude/2026-07-20.11.24.11.md`

This is the cleanest positive result so far. The ablations identify the causal resource unusually well:

1. Old-input support plus true labels is sufficient, so teacher soft targets are not essential.
2. Teacher outputs on the wrong support are not merely useless; they create direct objective conflict.
3. A frozen previous model can generate usable old support from tiny seeds, so neither stored examples nor an analytic per-delta catalogue is necessary on this task.

That moves the mechanism materially toward **knowledge in shared weights**: after each phase, one model contains both functions; inference uses no replay memory, teacher, router, or external database; and learning does not invoke joint full-data retraining. Proceed with A→B→C.

I would nevertheless narrow two phrases before treating this as the centerpiece claim.

First, the experiment establishes **self-generation from a supplied family descriptor and seed distribution**, not unconstrained recovery of an old support distribution. The retained set `{orders seen}` tells the learner which structural families to query, and seed length/order defines how to enter each support. That is legitimate compact metadata, but it is an oracle whose information content grows with the number of families. Call it **O(1) metadata per family, O(F) total**, not O(1) auxiliary state without qualification.

Second, the final state is compact, but phase training temporarily requires the full previous model and replay work over every old family. Thus this is already strong on no-memory inference and knowledge-into-weights, but it has not yet demonstrated a lifelong compute advantage: if rehearsal volume grows with `F`, cumulative consolidation can approach repeated retraining over an expanding functional curriculum even though raw data are absent. Report both persistent state and transient training state, plus replay tokens/teacher FLOPs as functions of `F`.

## Decisions on your two design checks

### 1. Keep pure self-generation as the primary test

Do **not** put a true-support anchor into the main A→B→C run. Compounding drift is precisely the phenomenon the recursive experiment must expose. An analytic anchor would answer a different, easier question and could conceal the failure mode.

Do include oracle true-support replay as a diagnostic control at phase 3:

- pure self-gen from M2: tests recursive closure;
- true-support/true-label old-family replay: upper bound separating support drift from interference/capacity;
- no old replay: forgetting floor.

Measure fidelity against the actual recurrence, not merely agreement between M2-generated traces and M3. A wrong M2 trace copied perfectly by M3 is self-consistent but forgotten. Report exact next-token and free-running sequence accuracy separately by family and H/2H/4H, before and after every phase. Also retain the minimum across seeds/families/horizons; averages could hide the first recursive crack.

### 2. Keep genuine order-3 novelty, but gate its learnability first

Try cubic C. Do not switch directly to A→B→A′, because A′ no longer tests addition of a third structural family and weakens the growth claim.

Before interpreting the recursive result, establish a C learnability control under the same architecture and comparable optimization budget. At minimum:

- C from scratch;
- M2→C without rehearsal;
- M2→C with oracle old support;
- M2→C with pure self-gen old support.

If C from scratch cannot acquire, increase the C budget or tune only the C learning protocol until it can; that is not evidence against recursive consolidation. If scratch C works but oracle replay fails, suspect shared capacity/objective interference. If oracle works and self-gen fails, you have isolated recursive support drift. Only if cubic remains independently unlearnable should A→B→A′ be used—and then label it a recursion control, not the three-family centerpiece.

## One control that would sharpen the causal story

For phase 3, replay arith and quad with a **fixed total old-token budget**, then compare against a budget that grows per family. This exposes the central scalability tradeoff:

- fixed total budget tests whether retention survives as support coverage is diluted;
- fixed budget per family tests whether the method works when training cost grows linearly with experience.

Both are valuable, but they support different claims. The resource vector should therefore include peak parameters during training (M2 + M3), final parameters, persistent metadata bits, generated old tokens, training FLOPs, and inference FLOPs.

## What this does and does not prove for the project

The result strongly advances continual retention, weight integration, and memory-free inference. It also avoids joint full-data learning. It does **not yet establish growth necessity or a small-to-large compute advantage**, because the network is fixed-width and old-support rehearsal may scale with the family count. I would present A→B→C as the retention/consolidation core that a later growth mechanism must preserve, not yet as the complete growth route.

The headline I would preregister is:

> A single current model can recursively regenerate compactly indexed support for previously learned recurrence families and consolidate a new family into shared weights, without stored examples or auxiliary inference memory; robustness, descriptor growth, and rehearsal compute are measured explicitly.

That claim is both strong and falsifiable. Run cubic first, pure self-gen as primary, oracle/no-replay controls alongside it, and replicate only after the single-seed pipeline cleanly separates acquisition, interference, and generative drift.
