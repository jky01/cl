# Yes: pivot to support search—but treat it as an oracle and a diagnostic, not yet the final learning mechanism

Source read in full: `qa/claude/2026-07-17.09.41.24.md`.

I agree with the pivot. The enumeration is decisive for the question it actually tests:

- within the declared 91 singleton supports,
- under the current fit/complexity objective,
- on the current ID distribution,

`x*x` is both the unique best fit and the intended extrapolating mechanism. The graphL0 failure therefore cannot be blamed on a missing edge-code term. It is an optimization failure: the relaxed parameterization found the right *number* of units without finding the right internal support.

So I would drop edge-MDL as the headline. I would not spend a full branch on it. At most, run one cheap, explicitly labeled negative control if the implementation is already nearly free: charge edges, show that the relaxed gates still fail to recover the enumerated optimum, and close that branch. If it requires meaningful engineering, skip it—the enumeration already answers the scientific question more cleanly.

## Which search first

For this toy, use **exhaustive support enumeration**, not greedy, beam, OMP, or ILP. Ninety-one candidates are small enough that an approximate search would introduce a second optimizer before we have validated the protocol. The minimal selector should be:

1. Declare the operator library and exact structural code before looking at OOD.
2. Enumerate every allowed support.
3. Refit each candidate with the same deterministic procedure and equal restart budget.
4. Rank using ID/prequential evidence plus the preregistered structural cost only.
5. Commit to one candidate, then open sealed OOD once.
6. Insert/consolidate the selected module in the continual learner and measure both new-task recovery and old-task retention.

This gives an exact oracle result for the toy and separates three questions that should not be conflated:

- **Objective adequacy:** does the score rank the intended mechanism first?
- **Search adequacy:** can the discrete procedure find that ranked mechanism?
- **Continual integration:** can it be added without damaging previously encoded knowledge?

Only after that should search itself be made approximate. My first scalable version would be best-first or beam search over supports, with the exhaustive toy answer used as a unit test. OMP is less diagnostic here because defining `x*x` as a ready-made basis atom partly gives away the compositional discovery problem. An ILP also seems premature unless the refit-and-score objective can be expressed exactly rather than hidden behind a nonlinear inner solve.

## The decoy should be the very next experiment

Yes. In fact, it is more important than another gate experiment.

If `d = x` on every ID observation and `d` diverges only OOD, then `x*x` and `d*d` have identical ID predictions, identical one-coordinate support size, and—under a symmetric code—identical description length. Ordinary prequential scoring on prefixes from that same environment cannot help: every prefix preserves the equivalence. A selector that returns `x*x` in this setting has used an undocumented asymmetry, a tie-break rule, or luck; it has not identified the mechanism from evidence.

That makes the decoy a clean impossibility/control result, not merely a harder benchmark. I would preregister the expected outcome:

- single-environment ID + symmetric MDL: **non-identifiable; chance/tie behavior is correct**;
- multiple environments in which the `d=x` correlation changes while the `y=x^2` mechanism remains invariant: **`x*x` should become identifiable**;
- prequential ordering alone, with no environment shift or intervention: **should remain non-identifying**.

The important next principle is therefore not vaguely “more than description length.” It is **evidence that breaks observational equivalence**, paired with an invariance bias. Multi-environment data, interventions, or deliberately varied curricula can supply that evidence. A causal prior without such evidence can choose a candidate, but it cannot claim the choice was learned from the stream.

I would structure the immediate sequence as:

1. **S3-search-oracle:** exhaustive selection recovers `x*x`; sealed OOD succeeds.
2. **S3-continual:** select and integrate after parity; verify parity retention and square recovery without joint full retraining.
3. **S3-decoy-impossibility:** matched `x`/`d` code lengths in one environment; verify non-identifiability rather than rewarding lucky tie-breaking.
4. **S3-decoy-environments:** introduce the smallest environment change that breaks the tie; test whether invariant support selection now recovers `x*x`.
5. **S3-search-distillation:** use the exact search result as supervision for a differentiable support proposer, then test whether the proposer reduces search compute without changing the selected mechanism.

## Relation to the actual continual-learning goal

Search is a good **outer-loop teacher**, but it is not yet the destination. By itself it does not show that a small model can grow into a larger one efficiently: exhaustive search can simply move the combinatorial cost outside SGD. The decisive continual protocol must therefore report:

- **knowledge into weights:** the selected mechanism is consolidated into model parameters, not retained as an external episodic lookup table;
- **continual retention:** parity remains intact after square is integrated, including after any consolidation/refit step;
- **growth necessity and compute advantage:** added capacity and search cost are compared against a fixed-capacity baseline and against prohibited joint full retraining, with cumulative compute reported;
- **no-memory inference:** inference uses only the resulting weights/modules, with no replay buffer or search over past examples at test time;
- **no joint full retraining:** old raw data are not pooled back in as the main solution.

One subtlety: “support search + refit” is compatible with the goal only if refitting is local—new module, sparse adapters, or a bounded consolidation step. If each task triggers a global refit over all historical data, the method has merely disguised joint training as model selection.

My bottom line: **make exact support search the oracle mechanism now, make the decoy the next falsification test, and treat differentiable gates as a later amortization problem.** The enumeration rescued the objective on the plain toy; the decoy will tell us precisely where that objective stops being sufficient.
