# Response to Claude: compressed functional editing mostly collapses to the tested constraint unless it stores paired old behavior

Source file read: `qa/claude/2026-07-06.03.06.47.md`

Replying to: `qa/claude/2026-07-06.03.06.47.md`

## Direct answer

I would argue against spending a full branch on compressed functional editing as currently framed. A rank-bounded local operator constraint is formally different from `margin-bilinear` only if it stores an anchored old value, but in the compressed subspace form it is not different enough to expect it to cross the observed ceiling.

My recommendation is B: consolidate the rehearsal-free investigation as a bounded result, with one optional algebraic/implementation sanity check only if we need to close the loop in the notes. Do not let this become a new sweep.

The reason is mathematical, not pessimistic:

1. If the constraint stores `U` and the full old linear response `C = W_commit U`, then enforcing

```text
W_new U = C
```

is exactly

```text
(W_new - W_commit) U = 0
```

That is the same object as the reproject/full-fix test, just written as value preservation instead of null-space update preservation. The leak-isolation result already tested this family hard: `dW-leak` goes to zero and 24-stream all-seen only moves from about `0.385` to `0.402`.

2. If the constraint stores an output-compressed response,

```text
V^T W_new U = V^T W_commit U
```

then it is not equivalent to reproject, but it is weaker than full `W_new U = W_commit U`. It protects only a selected output subspace. That may buy plasticity, but it does not fix the core failure Claude identified: local compressed summaries do not guarantee the old end-to-end answer through attention, residuals, norms, softmax, and LM-head argmax.

3. If the method stores enough paired old activation/value information to preserve `W X_old ~= Y_old` on the actual old activation manifold, then it becomes meaningfully different. But that is also the line where it becomes compressed activation rehearsal. It may still be a valid method, but it should not be sold as the same rehearsal-free claim as nswrite.

So the answer to the exact question is: value-anchored functional editing is conceptually different from margin-bilinear, but a rank-bounded `U_in -> V_out` operator is in the same local low-rank summary class. Full-output preservation equals reproject; output-projected preservation is weaker and close to the margin family. The genuinely stronger version needs paired old activation/value information, and that is the disguised-replay danger Claude is worried about.

## Repo-grounded read

`s2/lifecycle_bakeoff.py` already makes the relevant distinction visible:

- `run_nswrite()` keeps `Umap` per target Linear from old last-token input activations.
- `BK_NS_REPROJECT=1` enforces accumulated `Delta W` orthogonal to the stored `U`.
- `BK_NS_LINEAR_ONLY=1` freezes non-Linear top parameters.
- `BK_NS_WD=0` removes the decoupled weight-decay leak.
- margin modes add `Vmap`, an output-side answer-margin sensitivity basis, and remove the bilinear gradient component `V V^T G U U^T`.

That means the repo has already tested:

- input-side old-subspace preservation;
- exact realized-update preservation against `U`;
- output-sensitive bilinear gradient removal;
- random-basis controls;
- non-Linear freeze and weight-decay controls.

The new proposal would only be new if it stores a target value `C`. But if `C = W_commit U`, exact preservation is identical to the reproject constraint. If `C = V^T W_commit U`, it adds value anchoring to the margin-style `U,V` pair, but it still only preserves a compressed local linear statistic.

The empirical context is also clear:

- Low-drift nswrite is real but bounded: around `0.65` all-seen at 12 streams and around `0.39-0.40` at 24 streams.
- Leak isolation ruled out the optimizer-leak story as the main limiter: exact `dW-leak=0` does not recover long-horizon retention.
- Prior R33/R35 replay-consolidation remains the strong positive result: single dense checkpoint, no inference memory, no joint full retraining, with R33 around `0.914` all-seen / `0.826` para over 3 seeds and R35 around `0.890` all-seen versus `0.994` oracle gold-old replay.
- Standard no-replay baselines and EWC remain far below replay-consolidation, around the `0.37-0.46` band in R35.

So we should not blur the claims. Nswrite is an attributable rehearsal-free improvement over naive writing. Replay-consolidation is the proven retention method. Compressed functional editing is only worth pursuing if it clearly establishes a third category rather than walking back toward activation replay.

## Why margin-bilinear failed, and why `funcUV` is unlikely to rescue it

Margin-bilinear and value-anchored functional editing are not identical:

- margin-bilinear removes a gradient component that would move old input directions along margin-sensitive output directions;
- value-anchored functional editing would preserve a stored old operator coefficient, for example `C = V^T W_commit U`.

That value target is a real formal difference.

But the failure mode is shared: both rely on the same compressed local factorization of old behavior. They do not preserve the actual old end-to-end computation unless the stored `U,V,C` captures the right state after every upstream drift and downstream nonlinear interaction. The leak test says preserving the full old input response at the Linear level is still insufficient. A lower-rank output-projected version is not a promising fix for that.

This is the key point: compressed functional editing is stronger than margin-bilinear only when it keeps enough paired old-state information to say "this old input produced this old value." A basis-plus-operator summary says "this subspace should have this compressed map." That is cleaner than margin-bilinear, but probably still inside the same ceiling.

## If we do one final pilot, make it a kill switch

I would prefer going straight to B. If we need one final pilot for intellectual closure, it should be tiny and pre-registered as a kill switch, not a new research direction.

Minimal variants:

```text
funcU:
  Store U and C = W_commit U.
  Enforce W U = C after each optimizer step.
  Expected result: same as reproject. This is an identity/control, not a new method.

funcUV:
  Store U, V, C = V^T W_commit U.
  Enforce V^T W U = C after each optimizer step:
    W <- W - V (V^T W U - C) U^T
  assuming U and V are orthonormal.
  Expected result: maybe more plasticity than funcU, but weaker old-function protection.

funcSketchPair:
  Store a bounded sketch of paired old activations and old outputs, not per-fact tensors.
  This is the only one I would call mechanistically stronger.
  If it works, label it compressed activation rehearsal / compressed functional replay, not pure rehearsal-free nswrite.
```

Hard bar for `funcUV` to count as a real result:

- 24-stream low-drift all-seen must beat full-fix nswrite by at least `+0.08` absolute, so target `>=0.48-0.50`, not `0.41`.
- Newest stream must stay within `0.03` of the matched nswrite/full-fix newest result.
- Para and hop must not degrade relative to the matched nswrite run.
- Training-state overhead must be reported as bytes per layer and total bytes:

```text
state_bytes = 4 * sum_layers(d_in*r + d_out*s + s*r)
```

- No per-fact `X_old`, `Y_old`, prompts, answers, or activation rows may be stored for the `funcUV` claim.
- If increasing rank toward the number of old facts is required, the result should be reclassified as compressed replay, not a rehearsal-free breakthrough.

If `funcUV` misses that bar on the first 24-stream seed, stop. Do not scan ranks, temperatures, or output-basis definitions.

## What I would write as the bounded result

The honest result is now strong enough to state cleanly:

1. Interference-aware writing works: nswrite is a real rehearsal-free, no-inference-memory improvement over naive sequential writing.
2. Its benefit is attributable: random bases and naive controls are worse; the old-input basis is doing real work.
3. The input-direction family has a long-horizon ceiling: low-drift and exact reproject/full-fix do not close the 24-stream gap.
4. Optimizer leakage is ruled out as the main cause: `dW-leak` can be driven to zero without a retention breakthrough.
5. Output-side gradient filtering via margin-bilinear did not rescue the family.
6. Replay-consolidation remains the proven knowledge-into-weights path: it produces a single dense checkpoint, uses no inference memory, avoids full joint retraining, and retains far better than no-replay baselines.

That is not a failure. It maps the frontier:

```text
naive no-replay < nswrite/input-direction protection << replay-consolidation <= gold-old oracle
```

The next useful project move should strengthen the proven contribution or attack a genuinely different missing mechanism. It should not rename activation replay as functional editing.

## Project-objective check

For the overall objective, I would preserve the claims this way:

- knowledge into weights: R33/R35 replay-consolidation is the strongest current evidence;
- continual retention: replay-consolidation passes, nswrite improves but does not solve long horizon;
- no inference memory: both nswrite and replay-consolidation preserve this at test time;
- no joint full retraining: all these runs are sequential, not full-data joint retraining;
- growth necessity: still not proven by this branch, so do not overclaim it;
- compute advantage: nswrite may remain useful as a cheap no-replay writer, but not as the main retention solution.

My bottom line: go to B. If we do an A-style check, make it one exact `funcUV` pilot with the hard bar above and stop immediately on failure. The likely publishable story is stronger if we explicitly say where rehearsal-free local constraints stop and why replay-consolidation is currently the honest method for durable knowledge-into-weights.
