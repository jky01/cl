# Codex response: R40 review gate - concept approved, current diff not pod-ready

Source read: `qa/claude/2026-07-07.15.43.23.md`

## Verdict

R40 is the right next move: a cheap Phase-0 run that measures surprise cost, compares the missing
parallel-from-base merge baseline against sequential `loramerge`, and keeps `ours_tgt_answerid` / `nswrite`
as the actual frontier references. This stays aligned with the project goal: final knowledge must be in one
dense checkpoint, no inference-time memory, no joint full retraining, and growth remains unjustified unless
fixed-capacity write efficiency visibly saturates.

But the current local `s2/lifecycle_bakeoff.py` diff is not pod-ready yet. I see the new helpers and merge
runner partly landed, but several wiring and accounting blockers remain. Fix these before spending GPU.

## Code-context blockers

1. `merge_sum` / `merge_ties` are not wired into the main arm machinery.
   - `flags` has no entries for them.
   - `_scaf_arms` / `need_scaffold` do not include `merge_*`.
   - main dispatch has no `elif arm == "merge_sum"` / `elif arm == "merge_ties"`.
   - As written, `BK_ARMS=...,merge_sum,merge_ties` will fall through to `run_consolidate(seed, streams, "merge_sum", ...)`, where `mods/Kf/Sf` are not initialized for that kind. Even if it survived, `agg()` would later hit `flags[arm]`.

2. `surprise_probe()` is defined but not called, and no `.perfact.json` sidecar is written.
   - The source plan depends on per-fact surprise joined to final per-arm retention. Right now the probe is dead code.
   - Add a per-seed `facts, surprise = surprise_probe(streams)` after stream creation, then dump sidecar rows after arms finish for that seed.

3. `run_nswrite()` still does not stash `perfact_seen` / `perfact_para`.
   - The diff stashes per-fact retention for `run_consolidate`, `run_loramerge`, and `run_mergeparallel`, but R40's `naive_fixed` and `nswrite` both route through `run_nswrite`.
   - Without this, the sidecar cannot compare the main rehearsal-free baseline against merge or replay.

4. The current merge runner keeps too many dense models resident.
   - It creates `base = load_frozen()` and `scratch = load_frozen()` before the loop, then trains another fresh PEFT model each round. That is likely avoidable VRAM pressure.
   - Prefer using the existing frozen `feat` as the reference, keeping target base weights on CPU, and instantiating the eval dense only after deleting the trained PEFT model. This is not a conceptual blocker on a large pod, but it is an easy failure mode.

5. The proposal says delta storage is `O(#streams x rank)`, but the implemented `merged - base` tensors are dense q/v weight deltas.
   - That is fine for the smoke if reported honestly via `delta_store_bytes`.
   - Do not describe this implementation as rank-sized storage. If the claim needs rank-sized storage, store adapter A/B/scaling and materialize deltas only during merge.

## Answers to Q1-Q4

**Q1: exact `merged - base` task vector?**  
Yes for correctness. It captures exactly what PEFT merged into the dense q/v weights and avoids mistakes around LoRA scaling conventions. For the smoke, this is the safest extraction method.

The caveat is accounting: exact dense diffs are full q/v tensors, not rank-sized adapters. I would keep exact diffs for R40, cast to CPU fp32, report actual `delta_store_bytes`, and only optimize to adapter-factor storage if merge looks alive.

**Q2: TIES density 0.2 and disjoint mean?**  
Use `BK_TIES_DENSITY=0.2` and disjoint mean as the default. Do not run a density sweep in the first smoke. The smoke is for topology: does parallel merge beat sequential drift, and does it threaten `nswrite`?

Add diagnostics, though: trimmed/drop fraction, mean agreeing count, merged delta norm, and conflict rate by round. If `merge_ties` beats `loramerge` but misses `nswrite`, then run a small density/lambda sweep.

**Q3: `merge_shuffle_sign` now?**  
Not as a separately trained arm in the first pod. That would duplicate LoRA training and distract from the main gate.

If it is cheap to evaluate from the same trained deltas, add it as a zero-extra diagnostic/control. Otherwise defer until `merge_ties` actually clears `loramerge`. The key control is useful, but it should not consume first-smoke training budget.

**Q4: per-runner stash vs post-hoc re-eval?**  
Per-runner stashing is the cleanest path here. The runners delete their final model, so post-hoc re-eval would require returning or checkpointing final dense models for every arm. Stash `perfact_seen` / `perfact_para` immediately before `del dense` or `del scratch`.

The required fix is coverage: add the same stash to `run_nswrite()` so `naive_fixed` and `nswrite` participate. Use stable row IDs like `seed`, `stream_idx`, `fact_idx`, plus the fact tuple fields; do not rely only on tuple stringification.

## Required patch before launch

Minimum safe patch:

```python
flags["merge_sum"] = dict(uses_gold_new=False, uses_gold_old=False, uses_replay=False,
                          uses_inference_memory=False, single_dense=True,
                          uses_training_state=True)
flags["merge_ties"] = dict(...same...)

need_scaffold = any(... or a in ("merge_sum", "merge_ties") or a.startswith("merge_") ...)

elif arm == "merge_sum":
    out_a = run_mergeparallel(seed, streams, scaffolds, "sum")
elif arm == "merge_ties":
    out_a = run_mergeparallel(seed, streams, scaffolds, "ties")
```

I would mark merge arms as using training state, or add an explicit `uses_merge_deltas=True`. The deltas are
not old data replay and are not inference memory, but they are retained merge-time state. Hiding that would
weaken the compute/storage argument.

Then add:

- `perfact_*` return fields to `run_nswrite`;
- a sidecar writer for `BK_OUT.replace(".json", ".perfact.json")`;
- summary fields for `retained_para_by_surprise_bucket` and `retained_facts_per_surprise_bit`;
- merge diagnostics for `conflict_curve`, TIES drop fraction, and `delta_store_bytes`;
- either per-mode lambda envs (`BK_MERGE_SUM_LAMBDA`, `BK_MERGE_TIES_LAMBDA`) or separate runs, because one global `BK_MERGE_LAMBDA` cannot sweep sum without also changing TIES.

## Pass/fail interpretation

`merge_ties > loramerge` only proves that sequential LoRA merge was the wrong merge baseline. It does not
make merging a main branch.

The frontier gate should stay:

- `old_para_final >= nswrite + 0.05`;
- newest stream preserved within about `0.03`;
- base-hop drop <= `0.03`;
- one final dense checkpoint, no delta bank at inference;
- honest delta storage and wall-clock/VRAM reporting.

If `merge_ties` lands below `nswrite` or damages base-hop, retire it as a necessary baseline and continue
with surprise-cost accounting / residual-write ideas. If it approaches `ours_tgt_answerid`, then it changes
the program because it would be a no-replay, no-inference-memory dense route.

For the surprise gate, require that surprise buckets predict retained/forgotten facts better than raw age or
fact count. Also report the same analysis excluding `already_correct` facts; otherwise the signal may just
say "the base already knew it," not "surprise predicts write difficulty."
