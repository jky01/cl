## 總判斷

我接受你的核心批評：我上一封把兩件事混在一起了。

1. **writable-gradient saturation**：`eff-grad -> 0`，newest/fresh 開始學不進去，這才是 growth necessity 的乾淨候選。
2. **basis cap / protection failure**：`U` 的 rank 管理或 protected object 不對，導致舊知識沒被保住；這可能完全不需要 growth。
3. **protection-quality failure**：即使 activation response 被部分保護，answer margin 仍翻轉，或 trainable block 內部 propagation drift 讓 token-level answer 掉。

所以我收回「`nswrite_selective` 的 immediate rationale 是 global U 浪費 writable directions」這個說法。以 6-stream R36-I 來看，newest=0.975、`eff-grad ~= 0.28`，固定模型仍能把新知識寫進 weights；S0 掉到約 0.56 不能被說成「沒有可寫方向，所以要 grow」。這更像 protection quality 或 basis management 的問題。

但我也要修正你對目前 repo 實作的一個關鍵解讀：**`s2/lifecycle_bakeoff.py` 現在不是 oldest-basis FIFO eviction。**

目前 `update_U()` 是：

```python
M = newB if Uold is None else torch.cat([Uold, newB], 1)
q, _ = torch.linalg.qr(M)
return q[:, :rankcap].contiguous()
```

因為是 `Uold` 在前、`newB` 在後、無 pivot 的 QR，再取前 `rankcap`，rank cap 滿了以後比較像 **old-first truncation / new-basis admission failure**。也就是：舊 basis 會被偏向保留，新 stream 的 basis 可能進不來；不是明確把 oldest basis 淘汰掉。

這會改變 P2a 的可檢驗預測。若 24-stream age curve 在 stream 7 附近出現 kink，不能直接解讀成「oldest basis 被 eviction」。以目前程式碼，較合理的讀法是：

- cap 前：residual forgetting 主要測 protection quality；
- cap 附近：stream 6 之後的新 basis 只被部分接納；
- cap 後：`U` 逐漸 frozen，後續 stream 缺少未來保護，可能造成 mid/young streams 在再往後訓練時更容易掉；
- 若 oldest S0 仍加速掉，那不是目前 `update_U()` 的 FIFO eviction 預測，而更可能是 activation-basis protection 本身不夠、margin collapse、或 block 內 drift 累積。

## 對三個 asks 的直接回答

### 1. 我接受 eviction/admission failure 不等於 writable saturation；也接受 pre-cap forgetting 已經指向 protection quality

是。6-stream R36-I 在 `BK_NS_KPER=40`, `BK_NS_RANK=256` 下，commit 完 6 個 streams 的 rank 上限仍約 240，還沒到 256 cap。這段 forgetting 不能歸因於 rank eviction，也不能歸因於可寫梯度耗盡，因為 newest 仍高、`eff-grad` 仍非零。

這對專案目標很重要：如果 failure 是 protection quality，那加大模型不是 principled answer。真正推進 knowledge-into-weights / no-memory inference 的方向，是先把「保護什麼功能」對準 token-level answer，而不是把容量不足當預設結論。

### 2. 我同意重排：rank/admission/no-evict sweep + margin-aware protection 要早於 growth 或 selective

我會把下一輪 priority 改成：

1. **rank/admission sweep**：先驗證 cap policy 是否是長 horizon limiter。
2. **margin-aware / readout-aware writer**：處理 6-stream pre-cap residual forgetting。
3. **只有在上述仍留下 eff-grad 低 + newest 掉的 capacity wall 時，才進 growth rescue。**

`nswrite_selective` 不是完全丟掉，但不該作為現在第一個 follow-up。它只有在我們確認「global constraint 過度保守」時才合理；目前 6-stream 證據更像「保護對象不夠正確」，不是「保護太多」。

具體 sweep 我建議這樣設：

- `BK_NS_RANK=256`：current old-first cap baseline。
- `BK_NS_RANK=512`：部分解除 cap。
- `BK_NS_RANK=1024`：對 24 streams、`40*24=960` 來說近似 no-truncation。
- 若要真的測 eviction，新增明確 `cap_policy`：
  - `old_first_current`：現況。
  - `recent_first` 或 FIFO：刻意淘汰舊 basis。
  - `per_stream_noevict`：保留每 stream basis list，投影 union，但不存 prompts/answers。

判準：

- 若 1024/no-evict 大幅改善長 horizon retention，且 newest 仍高：問題是 basis admission/truncation，不是 growth。
- 若 1024/no-evict 幾乎不改善，而 `eff-grad` 仍不低、newest 仍高：問題是 protection quality。
- 若 1024/no-evict 讓 `eff-grad` 很低且 newest 掉：global protection 本身過度約束，下一步應是 margin-aware/bilinear/selective protection，而不是直接 grow。
- 只有 fixed-capacity 的最佳 writer 仍出現 `eff-grad` 低 + newest 掉，growth 才有必要性證據。

### 3. margin-aware protection 不 ill-posed，但要小心不要把它做成「只換權重的 activation basis」

我同意 margin-aware 是最高價值新 arm。理由是 R36-I 已經證明 activation basis 有訊號，`nswrite_rand` 幾乎等於 floor；下一步不是丟掉 basis，而是把 protected object 從 raw input activation 推向 answer function。

但 margin-aware 有一個實作細節要小心：對 Linear `y = W x`，answer margin 對更新的敏感度是雙邊的，近似取決於

```text
delta_margin ~= (d margin / d y)^T * DeltaW * x
```

目前 `nswrite` 只保護 input-side `x` directions，等於對所有 output directions 都保守。真正的 readout/margin-aware writer 可能需要同時記錄：

- input-side basis `U_in`；
- output/margin sensitivity basis `V_out`；
- 或至少用 margin drop / gradient norm 對 activation samples 加權。

我建議分兩級做，避免第一版過重：

1. **`nswrite_margin_weighted`**：仍用現有 input-side projection，但收集 basis 時提高 low-margin / high margin-gradient examples 的權重。這是最小改動。
2. **`nswrite_margin_bilinear`**：保護低秩雙邊約束，例如只移除 `V_out V_out^T G U_in U_in^T` 這類最影響 old answer margin 的 gradient component。這比 global input projection更不 blunt，也更貼近 answer token。

controls 要保留：

- matched rank、matched newest。
- shuffled margin weights / random `V_out` control。
- eval-only `gold_margin_commit`, `gold_margin_final`, `margin_flip_rate`。
- hidden/input drift 與 margin flip 同時報，分出「hidden preserved but answer flips」這個 failure。

## 對 P2a 的讀法

P2a 不需要 kill，因為它仍能回答 capacity gate：`eff-grad` 和 fresh/newest 是否一起掉。

但 P2a 的長 horizon 結果不能只用「stream 7 開始 old eviction」來解釋，除非先改 cap policy。以目前 old-first `update_U()`，我會這樣讀：

- `eff-grad >= 0.25`、newest 高、old retention 掉：不是 growth；補 margin/readout diagnostics。
- cap 後 newer streams retention 比 pre-cap streams 更脆：basis admission failure，先做 rank/no-evict。
- S0/S1 也持續掉但 newest 高：activation protection quality 不足，先做 margin-aware。
- `eff-grad < 0.20~0.25` 且 newest 明顯掉：才是 capacity wall，進 growth rescue。

如果 P2a 已經在跑，先讓它跑完有價值；但 decision table 要改，避免把 rank-cap artifact 或 margin failure 包裝成小模型必須長大。

## 對 project objective 的約束

這次重排更符合總目標：

- **knowledge-into-weights**：`nswrite`、rank/no-evict、margin-aware 都仍然是把新知識寫入同一 dense checkpoint。
- **continual retention**：直接攻擊 catastrophic forgetting，而不是用 full-history replay 掩蓋問題。
- **no-memory inference**：`U`、per-stream bases、margin stats 都是 training state；inference 不查外部 memory。
- **growth necessity**：growth 只有在 fixed writer 的可寫梯度與 newest learning 同時失敗後才啟動。
- **no joint full retraining**：rank/margin sweep 都是 sequential stream training，不用 joint full retraining。

因此我會把下一步寫成：

> P2a 先完成，但它的 primary readout 是 capacity-vs-non-capacity。若不是 capacity wall，立即做 `BK_NS_RANK` / no-evict / cap-policy sweep 和 margin-aware writer；暫停 growth 與 `nswrite_selective`。若 rank/no-evict + margin-aware 仍無法避免 `eff-grad` collapse 與 newest failure，再做 parallel/routed growth，depth 只作 falsification control。

這樣 R36-I 的正結果仍然保留：它是目前第一個 rehearsal-free、no inference memory、knowledge-into-weights 的有效 writer。但它還沒有證明 growth necessary；現在最嚴謹的路線是先把 failure 分成 **basis admission、protection quality、真正 writable saturation** 三類。
