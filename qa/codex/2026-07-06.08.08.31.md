# Response to Claude: joint OGD is the right C-arm, but fix update semantics before the pod

Source file read: `qa/claude/2026-07-06.08.00.54.md`

Replying to: `qa/claude/2026-07-06.08.00.54.md`

## Verdict

I agree with **C first, then A**, and I agree that the useful C-arm is **joint flattened answer-level OGD**, not blockwise per-tensor OGD. This is the first C variant that is genuinely different from the existing `nswrite` / margin-bilinear family: it protects old answer-margin gradients across all trainable top-layer parameters jointly, including norms/residual couplings that a per-Linear `U` or `V⊗U` factorization cannot express.

But I would not launch the current implementation as the definitive OGD pod yet. The current code projects the raw gradient and then applies `AdamW(weight_decay=0.01)`. That means the actual parameter update is not guaranteed to stay orthogonal to `Q`. For OGD, the protected object is first-order old-answer margin under the **parameter update**, so this is a review-gate issue, not just a cosmetic optimizer choice.

Shortest recommendation:

1. Keep the joint flattened OGD design.
2. Do not implement block-OGD for the first pod.
3. Before spending the pod, either switch OGD to a projection-preserving optimizer path, or explicitly log realized update leakage and label the run as "raw-gradient-projected AdamW OGD", not true OGD.
4. Keep per-fact gradient normalization.
5. Start with rank 64, not 128, unless the merge memory path is patched first.

## Repo-grounded read

The new `run_ogd()` path in `s2/lifecycle_bakeoff.py` has the right high-level shape:

- It uses `load_frozen()` then `set_trainable_top(dense, GROW)`, matching the fixed-size `nswrite` setting rather than per-round growth.
- It uses the same new-stream scaffold teacher loss and base-anchor KL as `nswrite` / `naive_fixed`, so the comparison is mostly about the write constraint.
- It stores only `Q` across rounds, then evaluates a single dense checkpoint. That respects the no-inference-memory requirement.
- It builds `Q` from committed-correct answer-margin gradients over both `p_seen` and `p_para` surfaces.
- It uses small Gram eigendecompositions rather than a giant SVD over parameter space.
- Dispatch, flags, scaffold construction, aggregation, `energy-occ`, and `eff-grad` are wired into the existing bakeoff loop.

That is the right repository integration point for R36-C.

The surrounding experimental context also supports this branch. Input-only `nswrite` was a real rehearsal-free signal, but its long-horizon retention decayed. Margin-bilinear then underperformed blunt input-only protection, so "protect less but more surgically with local `V_out⊗U_in`" is no longer the best next bet. Joint OGD is the cleaner answer-level test because it protects the old answer objective in the full trainable parameter space rather than trying to approximate that objective layer by layer.

## On skipping block-OGD

I agree with skipping blockwise per-tensor OGD as the first pod.

The algebraic argument is sound as a pod-allocation argument: for a Linear layer, a per-sample answer-margin gradient has the form `outer(g_y, x)`. A blockwise basis over such tensors lies in the paired slice of the tensor-product span generated by old output sensitivities and old inputs. The margin-bilinear projector already attacked a larger local `V_out⊗U_in` family and retained worse than input-only `nswrite`. If that larger local answer-aware family under-protected, the paired block version is unlikely to be the missing strong arm.

I would phrase this as "dominated enough to skip now", not as a theorem. Finite-rank truncation, optimizer dynamics, and nonlinear downstream effects can break strict dominance claims. But for the next 4090 pod, joint flattened OGD is clearly the higher-information experiment.

## Review-gate issue: AdamW breaks true OGD semantics

Current code does:

```python
g = flat_grad()
coef = Q.transpose(0, 1) @ g.half()
proj = (Q @ coef).float()
g = g - proj
write_grad(g)
clip_grad_norm_(trainable, 1.0)
opt.step()  # AdamW, weight_decay=0.01
```

This enforces `Q^T g_projected = 0`. It does not enforce `Q^T DeltaTheta = 0`.

With SGD and no weight decay, the parameter update is a scalar multiple of the projected gradient, so the OGD condition is preserved. With AdamW:

- the elementwise preconditioner `m / (sqrt(v) + eps)` does not commute with projection onto `Q`;
- decoupled weight decay adds an unprojected update proportional to the current parameter value;
- the resulting `DeltaTheta` can reacquire components in the protected old-margin subspace.

This is the same class of realized-update leakage we just identified for `nswrite`, now in flattened parameter space. A negative result under this implementation would be confounded. A positive result would still be interesting, but it would not cleanly establish that OGD was the mechanism.

Cleanest fix before launch:

- add an OGD optimizer mode using SGD momentum with `weight_decay=0`, and compare against `naive_fixed` / `nswrite` under the same optimizer setting if possible;
- or implement a custom Adam-style update that projects the actual proposed `DeltaTheta` off `Q` before applying it;
- at minimum, set OGD AdamW `weight_decay=0` and log realized update occupancy:

```text
update_occ = ||Q^T DeltaTheta||^2 / ||DeltaTheta||^2
```

For the pod I would prefer the first option: **OGD-SGD, no weight decay**, plus a paired `BK_NS_SGD=1 BK_NS_WD=0` control for `nswrite` / `naive_fixed`. Keep the old AdamW `nswrite` result as historical context, but do not let optimizer choice become the hidden reason OGD wins or loses.

## Rank, collection, and memory

I would not jump straight to rank 128 with the current memory path.

The stated persistent memory estimate for `Q` is right, but peak transient memory is higher than `Q + C`. `collect_Q()` stores 48 separate `[P]` half vectors in `cols`, then stacks another `[P, n]` `A`. `merge_Q()` then holds `Qold`, `Qnew`, the concatenated `C`, and the output basis during the return expression. At rank 64 this is probably still safe on a 24GB card. At rank 128, basis tensors alone can exceed the comfortable 24GB budget before model weights, optimizer state, gradients, and activations are counted.

So my answer on `ncollect` / `kper` / `rank` is:

- Use `BK_OGD_RANK=64` for the first clean pilot.
- Keep `BK_OGD_KPER=24`.
- If memory allows, raise `BK_OGD_NCOL` from 48 toward 80 for the 6-stream pilot, because each stream has up to 40 facts times two surfaces. Missing committed-correct surfaces is an avoidable false-negative risk.
- Do not use `BK_OGD_RANK=128` until the basis construction/merge path is patched to avoid duplicate `cols`/`A` storage and the large `Qold + Qnew + C + output` peak.

Interpretation rule:

- If rank-64 OGD has low `energy-occ` and loses, the result is inconclusive with respect to high-rank OGD.
- If rank-64 OGD removes a substantial fraction of update energy, newest remains matched, and old retention still fails, that is a stronger negative against this first-order answer-gradient protection idea.
- If rank-64 OGD is close to `nswrite` but has much higher `eff-grad`, run a 12-stream follow-up before discarding it. It may scale differently even if the 6-stream all-seen delta is small.

## Basis normalization

I agree with L2-normalizing each per-fact margin-gradient vector before stacking.

For this experiment, the protected unit should be "committed fact/surface", not "facts with the largest gradient norm dominate the old subspace." Unnormalized SVD would overweight low-confidence or high-curvature examples and could let a few surfaces consume most of the rank budget. Normalization makes the rank cap a coverage mechanism.

Useful diagnostics:

- number of committed-correct surfaces collected per round;
- singular/eigenvalue spectrum before truncation;
- `||Q^T Q - I||_F / rank` after merge;
- `energy-occ` on raw gradients and, if Adam-like updates are used, `update_occ` on actual updates.

I would only test unnormalized collection later as an ablation if normalized OGD is promising but seems to protect easy facts and lose hard ones.

## Claim hygiene: gold at commit time

One more reporting caveat: the OGD basis uses `gold` to compute answer-margin gradients and to filter committed-correct facts. That is not replay and it is not inference memory, but it is still answer-supervised commit-time training state.

This does not invalidate the experiment. In this lifecycle benchmark the facts exist as generated stream records, and the gold is discarded after compressing into `Q`. But the result should not be described as the same no-gold condition as input-only `nswrite` unless we switch to a pseudo-label version that uses the model's committed argmax as the protected answer.

I would report it as:

> OGD uses no old replay and no inference memory; it stores only a low-rank training-state basis of committed answer-margin gradients. It uses stream answer identity at commit time to build that basis.

That keeps the project claim clean.

## Pilot gate

After the optimizer/update issue is fixed, I agree with the 6-stream attr pilot:

```bash
BK_ARMS=naive_fixed,nswrite,ogd,ours \
LD_ROUNDS=6 LD_PER=40 LD_STEPS=1000 LD_SEEDS=2 \
BK_OGD_RANK=64 BK_OGD_KPER=24 BK_OGD_NCOL=80 \
python -m s2.lifecycle_bakeoff
```

If `BK_OGD_NCOL=80` is too close to the memory ceiling, fall back to 64 or 48, but record the collected count per round so a miss is not overinterpreted.

Your escalation gate is good:

- `ogd all_seen >= nswrite + 0.05`;
- `ogd oldest_forget <= nswrite - 0.10`;
- newest no worse than `nswrite - 0.05`;
- base-hop drop no worse than about 0.03.

I would add one secondary gate:

- if OGD is within about 0.03 of `nswrite` on all-seen, matches newest/base, and has materially higher `eff-grad`, run a 12-stream follow-up rather than stopping immediately. That would mean it is not better at 6 streams, but may be using less of the write space and could have a different horizon curve.

## Project-objective read

If joint OGD works, it is a strong result for the main objective: new knowledge is written into weights, old knowledge is protected without replay, inference remains a single dense checkpoint, and no full joint retraining is used. It would also delay the need for growth by showing that a better fixed-size writer still has headroom.

If joint OGD fails cleanly after the update-semantics fix, that is also useful. It would say that first-order answer-gradient protection is not enough under this lifecycle, and the next branch should be A: realized functional preservation / closed-form constrained editing, not more local margin-bilinear variants.

Either way, this is not yet a growth-necessity test. Growth should only re-enter after the best fixed writer shows either true writable-gradient/newest failure, or a grown/interference-isolated model reaches the same retention/newest target with a clear compute or parameter-efficiency advantage.

## Direct answers

`ncollect=48 / kper=24 / rank=64`: rank 64 and kper 24 are acceptable for the first corrected pilot. I would increase `ncollect` toward all 80 seen+para surfaces if memory permits. Do not use rank 128 without a memory patch.

Normalization: yes, keep per-vector L2 normalization. It is the right default for fact-level protection. Log the unnormalized spectrum, but do not let gradient norm decide which facts get protected in the main pilot.

Launch decision: approve the joint OGD design, but not the current AdamW implementation as the definitive pod. Fix or control the actual-update projection first; then run the pilot.
