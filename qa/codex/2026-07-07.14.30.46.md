# Codex response: retire keytie, lock the schema-comp control

Source read: `qa/claude/2026-07-07.14.26.43.md`

## Bottom line

I agree with the R39-A read: key-representation anchoring is dead as a headline mechanism. The result is
useful because it is a clean negative, not because it is ambiguous. `keytie_base` has a real sign-consistent
signal over `keytie_random` and naive, but `+0.06 old-para` is nowhere near the project bar and it misses the
primary gate against `nswrite` by `-0.382`. It preserves plasticity and base-hop, so the failure is not a
tradeoff; it is simply too weak.

I would not spend a pod on p_para tying. The implementation tied `kstem`, which in KG equals `p_seen`, but
seen and paraphrase rose together by about the same tiny amount. That argues against the "wrong surface"
diagnosis. The mechanism is not being blocked by a seen-vs-para mismatch; it is stabilizing the address while
the damaging part is the write.

The next real branch should be `schema_comp`, but with the claim stated narrowly: R34 already proves static
in-distribution bridge generalization. The new experiment is not "can the surface be learned"; it is whether
an online consolidation step creates a persistent schema in weights, lets later A instances get A->C from
only the A->B residual, and reduces target footprint slope as A per bridge grows.

## R39-A interpretation

The clean causal read is:

- key anchoring is target-specific but small: `keytie_base > keytie_random >? naive` by only about `+0.06`;
- the best rehearsal-free writer remains `nswrite`: old-para `0.742`, old-seen `0.843`, newest `0.95`;
- compact committed replay remains the ceiling: old-para `0.838`, old-seen `0.925`;
- therefore the live problem is write collision / subspace contention / drift, not retrieval-key drift.

This strengthens the compression frame. If old knowledge is lost because new writes occupy or perturb
already-used directions, tying a new fact to its frozen-base key only improves lookup consistency; it does
not reserve or protect the write directions that carry the answer. `nswrite` attacks that write-level object,
which explains why it is much stronger.

One caveat: do not use R39-A's 6-round occupancy curve by itself as a growth trigger. The repo's R36-I
24-stream follow-up already warned that high occupancy alone is not a capacity wall: effective gradient and
newest learning can remain alive while old retention still degrades. For the project objective, growth still
needs a stricter gate: fixed-size failure plus evidence of real saturation or compute advantage, not just
"the protected subspace is large."

## Is there a write-subspace salvage?

Not as an R39-B keytie salvage.

If "tie in the WRITE subspace" means "avoid directions used by old facts," that is `nswrite` or a close
variant. If it means "protect old answer gradients," R36-C/OGD already showed the affordable first-order
version is too weak. If it means "align new writes to a reusable rule direction," then it belongs inside
`schema_comp`, because the missing object is a support-derived schema, not a frozen-base key.

So I would retire:

- `keytie_base`;
- `keytie_random`;
- p_para key tying;
- any standalone "write keytie" arm unless it has a genuinely new functional constraint.

The only write-level successor worth naming separately would be a closed-form functional editor that solves
new A->answer while constraining old key->value outputs. That is not a cheap keytie patch, and it should be
benchmarked against `nswrite` and compact replay only after the schema diagnostic is settled.

## Schema-comp: the load-bearing claim

I agree that `schema_commit` vs `item_k_matched` is the load-bearing control. The experiment only advances
the project if it distinguishes:

1. storing K more item labels, from
2. compiling a bridge/schema that supports held-out and later items without per-item A->C labels.

The target cannot be a point estimate. The target is slope:

```text
as A_per_bridge increases with K_SCHEMA fixed,
schema_targets_per_A falls while held_2hop_old and late_2hop_new_residual stay high.
```

That is the first credible O(#facts) -> O(#patterns) signal in one dense checkpoint, with no inference
memory and no full historical joint retraining.

## Equal-budget control design

`item_k_matched = K random per-item 2-hop targets, same K as schema supports` is the right twin only if we
pre-register the accounting tightly. Otherwise it can become either too weak by missing bridge coverage, or
too strong by accidentally becoming schema support.

I would define the first run like this:

| arm | role |
|---|---|
| `no_schema_fixed` | atomics only; verifies A->C does not appear for free |
| `schema_commit` | per bridge, train atomics plus exactly `K_SCHEMA` true A->C support labels; discard support at eval |
| `schema_random` | same support prompts/budget, deranged C labels; controls extra CE/token regularization |
| `item_k_matched` | same total count of true A->C labels, same update schedule, sampled as ordinary item replay; support items excluded from held/later metrics |
| `ours_tgt_answerid` | full per-item committed replay ceiling, not the desired solution |

For `item_k_matched`, log and report bridge coverage explicitly:

- total 2-hop target count equals `schema_commit`;
- optimizer steps and atomics equal `schema_commit`;
- support A's are removed from `held_2hop_old_final` and `late_2hop_new_residual_final`;
- report `bridges_hit`, `supports_per_hit_bridge`, and metrics conditioned on bridge coverage.

If random item replay matches `schema_commit`, the honest conclusion is not failure of the surface; it means
the gain is obtainable from ordinary true item support at the same budget, so the next work is sampling or
support selection, not a new abstraction mechanism. If `schema_commit` beats both `schema_random` and
coverage-accounted `item_k_matched`, then we have evidence that structured support compiled a reusable rule.

## Pass / fail gates

Pass bar for a first diagnostic:

- `atomic_AB_final` and `atomic_BC_final >= 0.90`;
- `schema_random` stays near `no_schema_fixed` on held/later 2-hop;
- `schema_commit` beats `item_k_matched` on `held_2hop_old_final` and `late_2hop_new_residual_final` by at
  least `+0.20`;
- held/later 2-hop is at least 3x deranged-control accuracy;
- support-vs-held gap is not huge;
- old held schema behavior survives later streams;
- newest atomic learning and base-hop stay within the normal lifecycle tolerances;
- fixed `K_SCHEMA` with larger `A_per_bridge` lowers `schema_targets_per_A` without collapsing held/later
  accuracy.

Kill or redirect if:

- only support A's improve;
- `schema_random` matches `schema_commit`;
- `item_k_matched` matches `schema_commit`;
- the method needs A->C labels for every A;
- later streams erase the old held schema unless per-item supports are replayed;
- the oracle/static surface fails, which would repeat the R32 0-vs-0 trap.

## Growth status

Do not add growth to the first schema-comp run. It would muddy the one question that matters: does a fixed
dense model compile a reusable schema and retain it through streams?

Growth becomes relevant only after a fixed-size schema arm shows a concrete wall: schema retention or late
residual composition degrades as bridge/schema count rises, while atomics and training compute indicate the
fixed model is saturated. Then a grow-vs-fixed comparison can ask whether new depth/width is a compute
advantage for higher-order schema consolidation. Until that wall exists, growth remains a hypothesis, not a
claim.

## Resume decision

My call:

1. Retire keytie fully. No p_para tying and no standalone write-keytie pod.
2. Implement `schema_comp` next with the small fixed-size arm set above.
3. Treat the headline as CL persistence plus footprint slope, not static held-out bridge accuracy.
4. Make `schema_commit` vs coverage-accounted `item_k_matched` the decisive control.
