## 回答問題 2：R33 backfill 的 arm 優先順序

如果時間只能容納一件事，優先順序應是：

1. **scaffold-sharing refactor + core arms 3 seeds + para/JSON**
2. **replay-with-gold oracle**
3. **EWC / diagonal-Fisher**

也就是說，若只能在「3rd seed + para」和「extra arms」二選一，我選 **3rd seed + para**。原因很直接：R33 的主結論已靠 core arms 成立，現在最大弱點是完整性與可審查性，不是缺另一個 baseline 名字。

### 必做：scaffold-sharing refactor

`s2/lifecycle_bakeoff.py` 建議改成每個 `(seed, stream)` 只訓一次 scaffold：

- 在每個 seed 開始時先建立 `stream_scaffolds[r] = train_memory(feat, streams[r], seed*100+r)`。
- `ours`、`naive`、`loramerge` 都讀同一個 per-stream scaffold。
- `continued` 不用 scaffold，維持 gold new-stream baseline。
- `extmem` 的 cumulative persistent bank 不是同一種物件，可以維持每輪 cumulative 訓練；但要在 flags 中清楚標為 `uses_inference_memory=True`、`single_dense=False`。

這樣可減少重複 `train_memory()`，也讓 arm 差異更乾淨：不是「哪個 arm 的 scaffold 運氣比較好」，而是同一個 teacher 下比較 consolidation / replay / LoRA merge / no replay。

### 第二優先：replay-with-gold oracle

這個 arm 很值得加，但它應被標為 oracle upper bound：

- sequential lifecycle，不做 full joint retraining。
- current stream 可維持同一 scaffold teacher，old replay 改用 gold answer CE；或明確定義成 `uses_gold_old=True` 的 bounded replay oracle。
- 報告時重點不是把它當主方法，而是問：ours no-gold self-distill replay 是否接近 gold-old replay upper bound？

若 ours 接近 oracle，會強化主張：不需要歷史 gold labels，也能把舊知保留在 dense weights 裡。

### 第三優先：EWC

EWC 是合理 baseline，但不要讓它阻塞本輪核心結果。它的風險是：

- diagonal Fisher 實作容易引入額外資料條件差異。
- lambda 掃描會吃時間。
- 在這個 synthetic fact lifecycle 中，EWC 很可能只證明「權重被鎖住後新知學不好」，需要同時看 newest stream 與 all-seen，否則解讀會偏。

若時間夠，建議簡化成：

- 同一 trainable top layers。
- `lambda in {10,100,1000}`。
- 明確 flags：是否使用 old prompts 估 Fisher、是否使用 gold、是否 replay。
- pass/fail：EWC 若 oldest-S0 保住但 newest 明顯下降，不能算優於 ours；若 all-seen 與 para 都落後 ours，結論是 regularization-only 不足以替代 replay-consolidation。

若時間不足，只跑 oracle，不跑 EWC；不要為了 EWC 犧牲 3-seed core summary。

## 回答問題 3：grokking later 的資料設計

我確認 Claude 提的修正方向：**large single-token vocab pool + 2-relation `r1∘r2` in-distribution holdout** 是下一輪 grokking 的必要前置。

R32 的失敗已經說明：在目前 cross-stream held-out 2-hop 設定下，即使 Gate A single-step 全部 1.000、Gate B direct 2-hop train-fit 1.000，held-out A->C 仍是 0.000。這不適合直接拿來做 grow-vs-fixed，因為會得到不可歸因的 0-vs-0。

下一輪 grokking 應改成：

- 從 tokenizer vocab 直接收集大量 all-alpha single-token entity ids，不再受 `single_tok_names` 約 44 個答案池限制。
- 建兩個 relation：`r1(A)=B`、`r2(B)=C`。
- atomic facts 全進訓練，確保 A、B、C 節點都 seen。
- 2-hop query 只 hold out 部分 `(A,C)`，但 holdout 必須是同一圖分佈中的 query holdout，不是新 entity / 新 relation path。
- 加 deranged/control labels，避免把 memorized lexical shortcut 誤讀成 grokking。

grokking 的硬停損條件沿用上一輪，但需要更嚴格落地：

- train 2-hop fit 在 2k steps 內不到 0.95：停，先修資料或 prompt。
- train fit >= 0.99 後再訓 5k steps，held-out 仍 <= 0.05 且不高於 derange/control：停。
- 兩個 seeds 都沒有 held-out 上升：停，不繼續掃 depth。
- growth claim 門檻：grow 在 matched compute 下 onset 提早至少 30%，或 final held-out ceiling 提高至少 0.10；同時 atomic recall、old-stream retention、base hop 不得明顯下降。
