## Data design

Use the same lifecycle shape first:

```text
6 streams x 40 facts, 2-3 seeds
same model, same train/eval budget, same answer-recall restart guard
```

The data should satisfy these constraints:

- subject can be multi-token;
- relation should be a real relation label with at least two natural prompt templates;
- object must be a single Qwen token for the primary exact-match run;
- facts should be screened so the frozen base does not already know them;
- if true KG triples are too base-known or too ambiguous, use KG-shaped counterfactual triples and label them honestly as counterfactual/KG-shaped, not real factual KG.

The base-knowledge screen matters. If Qwen already answers many triples before training, the experiment stops measuring new knowledge entering weights. I would require frozen-base seen accuracy <= 0.15 on the selected facts before accepting a stream set.

## Pass/fail criteria

Minimum pass for the external-validity claim:

- `ours` beats `naive` and `ewc` by at least +0.25 all-seen at final.
- oldest-stream forgetting for `ours` remains <= +0.10, or at least far below the no-replay arms.
- final `ours` all-seen >= 0.75 on seen prompts and all-para >= 0.60 on paraphrase prompts.
- base hop/capability drop stays <= 0.03 absolute.
- teacher answer-recall per stream is logged and guarded, ideally >= 0.80 after restarts.
- `oracle - ours` gap is reported. A gap around the R35 scale is acceptable; a much larger gap points to self-distill/scaffold signal quality, not a replay-consolidation refutation.
- final artifact remains a single dense checkpoint with no inference memory.
- no joint full retraining over all historical data is used; replay remains sequential training-time consolidation.

Failure should be classified, not hand-waved:

- high frozen-base recall: bad benchmark, not evidence of consolidation.
- low teacher answer-recall: scaffold/data issue, not dense retention.
- strong oracle but weak `ours`: no-gold self-distill signal is the bottleneck.
- weak oracle and weak `ours`: prompt/tokenization/object ambiguity or training budget problem.
- `naive` close to `ours`: either data are too easy/base-known or the stream does not create real interference.

## Why slotwrite should wait

`slotwrite` is more genuinely different than `funcUV`, but it opens a bigger and less controlled question:

- if slots grow with streams, the method risks becoming history-proportional parameter storage;
- if slots are later consolidated, consolidation may re-import the same interference problem;
- if it uses routing at inference, it violates the no-memory/no-router inference goal unless merged away;
- if it grows parameters, the growth claim needs a saturation or compute-advantage trigger, not just novelty.

So I would not start slotwrite until after the replay-consolidation result is stress-tested on real-KG/KG-shaped facts. The project currently has one robust positive contribution. Strengthening that first is higher value than opening another open-ended mechanism search.
