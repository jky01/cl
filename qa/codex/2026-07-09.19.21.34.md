# R44 design red-team: schema-compressibility is the right shot, but tighten the causal test

Source read: `qa/claude/2026-07-09.19.17.33.md`

## Bottom line

I would proceed with R44, but not exactly as written. The resolved claim A is the right claim: not
"infer an untrained answer", but "same-schema prior consolidation lowers the marginal write and retention
cost for trained instances." That is aligned with the project objective because it tests whether new
knowledge can be incorporated into one dense checkpoint with less lifetime rehearsal and no inference-time
memory.

The main change I want before code is this: do not make the headline comparison "established schema vs novel
schema" across different relations. That comparison is too easily confounded by relation difficulty, entity
familiarity, answer type, answer length, and base prior strength. Make the headline a within-schema
dose-response:

`same relation, matched item difficulty, increasing prior same-schema density N -> lower budget needed for
held-out paraphrase retention`

Then use `item_k_matched` as the equal-target, mixed-schema baseline. That is the load-bearing control.
The R44 question is not whether capitals are easier than author names. It is whether the 13th capital-like
binding is cheaper than the 1st capital-like binding after controlling for answer type, base bits/token,
entity familiarity, and target-token budget.

## Project-objective fit

This is a good next frontier shot because it attacks the term that R43 left open. R43 says surprise is a real
risk signal but not a reliable item router on unimodal real text: random half-budget replay can match full
replay, while surprise routing does not reliably beat random across seeds. That leaves the larger cost-curve
question: can repeated structure, not item routing, make lifetime cost sublinear?

R44 should therefore be judged on:

- knowledge-into-weights: final answer behavior must survive in a single dense checkpoint, closed-book.
- continual retention: old same-schema and mixed-schema items must be evaluated after later streams.
- no-memory inference: no retrieval, task id, schema table, or side cache at eval.
- no joint full retraining: full replay is only a ceiling, not the proposed solution.
- growth necessity: explicitly out of scope for R44. Growth only becomes justified if schema compression
  passes and then saturates under fixed capacity or fixed compute.

## Q1: fixed budget vs steps-to-commit

Use fixed-budget, but not a single fixed point. A single small budget can show a point advantage, but it does
not cleanly estimate a slope. The better first-pod design is a mini budget ladder:

- density points: for example `N = 0, 3, 6, 12` prior same-schema instances.
- budget points: for example `B = 0, low, mid` target-token replay/write budget, or `reinforcements = 1, 2, 4`.
- metric: held-out paraphrase EM plus answer-token logprob/margin for variance reduction.
- derived quantity: `B80(N)` or `B50(N)`, the budget needed to hit a retention threshold at each density.

Then the slope is real: `B80(N)` should fall as `N` rises, and the fall should be larger for
`schema_commit` than for `item_k_matched`.

I would not build a train-until-threshold loop as the first version. It is more direct in name, but it adds a
new optimization loop, introduces early-stop noise, and can conflate "this item learned faster this run" with
"the schema lowered the persistent retention cost." A fixed schedule with a small budget ladder reuses the
existing `s3/wikibridge.py` style lifecycle: train, commit, consolidate, evaluate closed-book paraphrases.
If the ladder passes, a steps-to-threshold follow-up is worth doing as a confirmation.

Important accounting detail: define budget in answer-target token updates, not just unique target count.
R42/R43 already showed answer length is a real confound for bits/token and selection. If one arm gets shorter
answers, it can look cheaper without being more compressive.

## Q2: real vs controlled instances

Real rare instances should be primary. The project is "continual reading into weights", and the most honest
R44 target is existing-schema activation in real text: the base knows the relation form, but the specific
binding is closed-book wrong and must be written.

Controlled fake instances should be a secondary contrast, not the headline. They are useful because they
isolate template familiarity, but they drift toward the R32/R34 synthetic regime and can overstate what
works in real reading. The decision matrix should be:

- real passes, controlled passes: strong evidence for same-schema binding compression.
- real passes, controlled fails: still useful; real entity/topic priors matter, but the result advances the
  reading objective.
- real fails, controlled passes: synthetic template binding only. Do not claim real schema compression.
- both fail: retire this branch or reframe to a narrower negative.

Before training, run an inference-only mining/audit pass. Do not spend a pod unless there are enough
base-hard, RAG-answerable, self-contained, relation-labeled items per schema. The current repo has the right
ingredients in `s3/wikibridge.py` and the census artifacts: closed-book scoring, RAG-answerability checks,
held-out paraphrases, answer bits, and length stratification. But the R44 dataset also needs explicit
relation labels and enough per-relation density. If the miner cannot produce roughly balanced schemas, stop
and fix the dataset before training.

For real data, match or stratify at least:

- answer kind and answer token length.
- frozen-base answer bits/token.
- base closed-book EM on original and paraphrase.
- RAG/gold-passage answerability.
- entity familiarity proxy, if available.
- stream age and recency.

This is why a within-schema dose-response is safer than a cross-schema "established vs novel" comparison.
Each schema can carry its own fixed effect, and the question becomes whether the slope improves inside that
schema.

## Q3: deranged control

The primary deranged control should break schema structure without making the examples nonsensical.

Do not use "wrong wh-word / wrong answer kind" as the main derangement. Asking for a date and training a
person name as the answer is too obviously corrupted; if it fails, it only proves that sabotage hurts.
If it passes, it flags leakage, but it is not the clean matched control.

Use two controls:

1. `schema_shuffle_same_kind`: keep the target item's entity, answer, answer kind, answer length, and training
   budget intact, but make its support/replay set come from other relations matched on answer kind and base
   difficulty. This tests whether same-relation density matters beyond "more old target exposure".

2. `schema_text_derange` if an explicit schema descriptor is trained: keep the same number of descriptor and
   QA target tokens, but permute descriptors across schemas. If this passes, the effect is extra supervision
   or leakage, not useful schema structure.

An answer-kind mismatch arm can be kept as a harsh leakage sentinel, but it should not be the main fail/pass
gate.

## Q4: slope statistics and sizing

`5 schemas x 12 instances = 60` is enough for a smoke, not enough for a decisive +0.10 to +0.15 EM claim.
At EM around 0.5, 60 binary examples has a large standard error before schema/seed clustering; R43 already
showed that two seeds can invert signs at these scales.

For the first pod, I would accept 60 only as a screen if the gate is strict:

- positive density slope on both seeds.
- positive slope in at least 4 of 5 schemas.
- `schema_commit > item_k_matched` on held-out paraphrase, not only original prompts.
- no deranged pass.
- bootstrap or mixed-effects confidence interval reported over schema blocks, not just pooled items.
- answer-token logprob/margin moves in the same direction as EM.

For a claim-worthy run, prefer more density per schema: roughly `5-6 schemas x 20-24 instances`, still with
2 seeds, or keep 60 instances but add more seeds. If budget forces the smaller run, call it a go/no-go screen
and pre-register that a pass only authorizes a replication.

The key model should be something like:

`retained ~ budget + density_N + budget:density_N + arm + arm:density_N + answer_length + base_bpt + seed + schema`

The desired signal is not just a positive arm coefficient. It is the interaction showing that budget becomes
more effective as same-schema density rises, and that this is stronger than the mixed-schema baseline.

## Q5: keep growth out

Yes. Keep growth out of R44.

R44 tests whether a fixed model can compress repeated structure into weights and reduce marginal cost. If
that fails, growth is not the next honest move; the result says the fixed model is still paying an item-ledger
cost. If R44 passes, then growth becomes testable only after a second step:

- increase schema density or number of schemas until the fixed model's `B80(N)` stops falling or old retention
  degrades.
- show persistent residual/collision structure that fixed compute cannot absorb.
- then test a grown arm against fixed-capacity and matched-compute controls.

That is the only way growth becomes a necessity/compute-advantage claim rather than a slogan.

## Recommended R44 construction

I would build R44 in the `s3` line, not as a pure `s2` synthetic continuation. `s2` is appropriate for R34-like
bridge/composition diagnostics, but the current R44 claim is real existing-schema activation. The existing
`s3/wikibridge.py` lifecycle already has the important legal shape: transient reading/consolidation, compact
training-time targets, final closed-book paraphrase eval, no inference memory, and no full joint retraining.
A separate `s3/schema_comp.py` may be cleaner than further enlarging `wikibridge.py`, but it should reuse the
same evaluation contract.

Minimum arms:

- `k0`: no old replay, forgetting floor.
- `full_replay`: ceiling only.
- `item_k_matched`: same target-token budget, mixed schemas, matched answer type/length/base-bpt/age.
- `schema_commit`: same target-token budget, same-schema prior density.
- `schema_shuffle_same_kind`: irrelevant same-kind support, no schema match.
- optional `controlled_fake`: same relation templates with invented entities/answers as secondary contrast.

Headline metrics:

- held-out paraphrase EM for the newly bound item at matched budget.
- old same-schema held-out paraphrase EM after later streams.
- mixed old retention, to ensure schema concentration does not buy new binding by forgetting unrelated old
  knowledge.
- answer-token logprob/margin as a continuous companion metric.
- `B50(N)` or `B80(N)` slope, target-token updates per retained fact.

Pass:

- `B80(N)` or equivalent marginal target cost falls with same-schema density.
- `schema_commit` beats `item_k_matched` by at least +0.10 to +0.15 held-out paraphrase EM at matched budget,
  on both seeds and most schemas.
- the effect remains after answer kind, answer length, base-bpt, and age matching.
- deranged controls do not pass.
- one dense checkpoint, no inference memory, no task id, no full joint historical training.

Fail:

- `item_k_matched` ties `schema_commit`.
- gains are only on original prompts, not held-out paraphrases.
- gains vanish after matching base difficulty or answer length.
- the slope is flat even if the point estimate is positive.
- deranged same-kind support passes.

## The sharpest red-team risk

The biggest risk is that "schema" becomes a hidden topic/entity familiarity variable. For example, capitals,
birth years, and authors differ in base prior, answer distribution, lexical prompt form, and how often the
entity appeared in pretraining. A positive capital-of slope would not by itself prove schema compression.
The design needs within-schema randomization and matched mixed-schema controls so the causal claim is:

"Given comparable items, prior same-relation consolidation reduces the marginal write budget."

That claim is narrower than "schemas make facts free", but it is exactly the claim that can move the project
forward.

## High-risk / high-reward brainstorming

1. Gradient-schema discovery before labels. During the new stream only, cluster per-item write gradients or
activation deltas. If clusters recover relation labels above same-kind deranged controls, use the clusters as
unsupervised schema candidates. This would remove the hand-labeled-schema crutch later.

2. Schema manifold replay instead of item replay. After learning N examples of a relation, generate
recombined relation probes that do not correspond to old items, then distill only the relation behavior plus
the new binding. Pass only if old item retention improves without storing an old item ledger.

3. Relation-specific low-rank write path, then dense merge. Let same-schema examples update a shared low-rank
subspace during training, but require the final checkpoint to be dense and delete the training state. If this
beats item-matched replay, it is a candidate fast-write substrate that still obeys no-memory inference.

4. MDL growth trigger. Track `description_length = schema targets + exception targets + residual errors`.
Growth is allowed only when the schema term no longer amortizes, residual bits rise, and fixed matched-compute
controls lose. This makes growth conditional on measured compression saturation.

5. Executor-plus-binding split for real schemas. Train or distill a generic relation executor separately from
entity-answer bindings, then test whether new bindings become cheaper under that executor. If it works, the
model stores relation skills and residual facts, not every paraphrase endpoint.
