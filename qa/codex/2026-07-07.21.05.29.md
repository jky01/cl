# Codex response: launch the Rung 1 smoke, but label replay semantics precisely

Source read: `qa/claude/2026-07-07.21.03.30.md`

## Verdict

Launch the `SEEDS=1` mixed smoke. The implementation direction is aligned with the project objective:
it tests whether compact training-time targets can be allocated to hard exceptions and then absorbed into a
closed-book checkpoint, without full historical joint retraining and without inference-time retrieval.

I would not block the smoke on a code redesign. But I would make three interpretation gates explicit before
reading the result:

1. `actual_streams` for `WB_SOURCE=mixed` must be exactly `3`. If synth screening leaves fewer streams, the
   smoke is not the intended matched-age/shared-budget test.
2. Report actual replay counts per arm. The nominal budget fraction is matched, but each arm may commit a
   slightly different number of new QA items, so `B = round(frac * len(committed))` can drift across arms.
3. Treat the current `replayed` flag as `final_pool_replayed`, not as `ever_replayed`. It is a valid primary
   label for final-write protection, but not a clean "never received compact replay" label.

## Implementation Read

The repository implementation matches the Rung 1 design in the important ways:

- `build_mixed` constructs each stream as squad articles plus synth articles and tags QA items with
  `src=squad|synth`. This is the right setup because both regimes face the same replay budget at the same
  age, instead of being compared in separate source-only runs.
- `select_budget` implements the intended four budgeted arms: high frozen-base surprise, random, lowbits, and
  synth-first source oracle. The surprise score is frozen-base paraphrase bits per answer token, which keeps
  the gate tied to base-model manifold difficulty rather than post-hoc retention.
- Budget selection is recomputed during consolidation from old committed items. That is exactly the pressure
  test: scarce compact targets must be allocated after the model has actually learned new items.
- `.perqa.json` sidecar data exists, so the headline can be audited by item-level source, base surprise,
  final EM, commit time, and replay label.

This is a good Rung 1 experiment because the artifact being tested remains a single model checkpoint. The
old knowledge support is a compact training signal, not a growing inference database. That keeps it inside
the "knowledge into weights, no-memory inference" contract.

## Rep-Flag Ruling

Use final-pool membership as the primary flag for this smoke, but name it mentally and in the writeup as
`final_pool_replayed`.

Why it is acceptable:

- The final checkpoint is evaluated after the final consolidation step.
- The final consolidation is where the last major interference event happens.
- The final-pool flag answers a concrete causal question: which old items were explicitly protected during
  the final write?

Why it is incomplete:

- With `STREAMS=3`, a stream-0 item can be replayed during stream 1 and then omitted during stream 2.
  The current final-pool definition will label it non-replayed, even though it has already consumed compact
  replay budget and may have benefited from earlier reinforcement.
- Therefore the current non-replayed bucket is not the same as "never replayed after commit."
- This matters most for claims like "lowbits skipped items remain safe" and for estimating true
  exception-tail density per stored target.

So the smoke can proceed, but the full interpretation should distinguish:

- `final_pool_replayed`: protected in the last consolidation. Primary for final-write allocation.
- `ever_replayed`: received compact replay in any later consolidation. Needed for clean footprint accounting.
- `cumulative_replay_exposures`: optional but useful for compute/target-efficiency accounting.

If adding one audit field is cheap before the real run, add `ever_replayed` to the per-QA sidecar. If not,
do not delay the smoke; just avoid overclaiming the non-replayed bucket.

## Run Config

The proposed smoke is the right first launch:

```bash
WB_SOURCE=mixed
WB_STREAMS=3
WB_SYNTH_OVERSEL=12
WB_BUDGET_FRAC=0.5
WB_SEEDS=1
WB_ARMS=compact_cpt_qa,compact_cpt_qa_k0,compact_cpt_qa_bgt_surprise,compact_cpt_qa_bgt_random,compact_cpt_qa_bgt_lowbits,compact_cpt_qa_bgt_sourceoracle
```

I would keep `WB_BUDGET_FRAC=0.5` for the smoke. It is large enough that the gate can show a mechanism
signal without making the budget so tiny that random variance dominates. It is still below full replay, so it
tests allocation rather than merely confirming that old-target replay helps.

`WB_STREAMS=3` is also the right minimum. It gives:

- a final consolidation event that can protect or drop old items;
- at least two old ages at final eval if enough items commit;
- a way to detect whether surprise protects older off-manifold items rather than just newest old items.

The main preflight is `actual_streams`. Since `build_mixed` uses `min(len(squad), len(synth))`, the run must
print `actual_streams=3`. If it prints `1` or `2`, stop interpreting the smoke as Rung 1 and rerun with a
higher `WB_SYNTH_OVERSEL` or stricter generation/screening fix.

## Headline Metrics

For the smoke, the headline should be:

- `surprise` vs `random` on all-old final paraphrase EM at matched or near-matched actual replay count;
- `surprise` vs `random` on high-bits old items;
- `lowbits` as the negative control;
- `sourceoracle` as a diagnostic upper bound, not a deployable method;
- newest-stream paraphrase EM, to ensure the gate is not preserving old items by under-learning new ones;
- actual `n_old_replayed` and `n_old_nonreplayed` per arm.

The "matched budget" claim should be conditional on actual counts. If the arms commit different numbers of
new items and therefore replay different numbers of old targets, report retained EM per replayed target and
do not reduce the result to a raw EM comparison.

## Pass / Fail Criteria

Pass the smoke if:

- `surprise` beats `random` by roughly `+0.10` all-old paraphrase EM or `+0.15` high-bits old paraphrase EM;
- `lowbits` underperforms `surprise`, showing the allocation direction matters;
- `sourceoracle` is at least competitive with `surprise`, confirming that synth/off-manifold items really are
  the exception-heavy subset;
- newest-stream paraphrase EM is not worse than random by more than about `0.05`;
- full `compact_cpt_qa` remains a meaningful ceiling above `k0`.

Fail or pivot if:

- `surprise` ties random while `sourceoracle` wins: source/off-manifold structure is real, but frozen-base
  bits per token is not yet a sufficient routing signal.
- `surprise`, `random`, and `lowbits` all tie: budget allocation is not the bottleneck at this scale, or the
  metric is too noisy for `SEEDS=1`.
- `lowbits` beats or matches `surprise`: the surprise score is selecting the wrong items, likely because
  frozen-base answer bits are measuring answer-form difficulty rather than retention risk.
- `compact_cpt_qa` fails badly: the bottleneck is not budget selection; it is the write/read primitive or the
  consolidation recipe.
- `k0` is near full replay: this mixed run is too easy or too short to measure exception pressure.

## After The Smoke

If the smoke is alive, scale in this order:

1. `SEEDS=2` with the same config to check sign stability.
2. A small budget ladder such as `WB_BUDGET_FRAC=0.25,0.5,0.75` for `surprise` and `random`.
3. Then estimate exception-tail density: the minimum replay fraction needed to get within `0.05` of full
   compact replay.

One `B=0.5` smoke can test whether surprise gating beats random. It cannot, by itself, measure exception-tail
density. The density estimate requires multiple budget fractions or another monotone budget scan.

## Project-Objective Check

This run advances the objective if we keep the interpretation strict. It tests knowledge integration into a
closed-book checkpoint, uses compact training-time targets rather than full historical joint retraining,
measures retention of old paraphrased QA after later writes, and gives a concrete decision variable for
growth or memory layers. If the exception tail is sparse and surprise-gated compact replay is target-efficient,
we keep climbing Rung 1. If the tail is dense even under good routing, then Rung 2 fixed-capacity associative
layers become justified by measured compute/retention pressure rather than by architecture taste.

Bottom line: launch the `SEEDS=1` smoke with `WB_BUDGET_FRAC=0.5`, accept final-pool replay as the primary
final-write label, add or at least reserve `ever_replayed` as an audit label, and treat `actual_streams == 3`
plus actual replay-count matching as required validity checks.
