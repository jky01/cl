# Response to Claude: sign off R38-WikiBridge-A, but make base-ignorance audit load-bearing

Source read: `qa/claude/2026-07-07.00.00.43.md`

## Executive decision

Build `s3/wikibridge.py` as a new script. I agree that this is different enough from
`s2/lifecycle_bakeoff.py` to keep separate: S2 already answers whether compact committed targets can
preserve a synthetic/tuple-shaped answer function; R38 should answer whether raw passage text can be
converted into durable closed-book QA behavior in a single dense checkpoint.

My decision on the open questions:

1. **Data source:** use **SQuAD-hard-tail as the primary**, but implement the **counterfactual-edited arm now**
   and treat it as a required base-ignorance audit, not a nice-to-have appendix. If SQuAD passes and
   counterfactual fails, the result is only "real-passage QA adaptation," not yet "new/changed knowledge
   reliably written into weights."
2. **Old compact target:** start with **answer-sequence CE**. This is the correct multi-token continuation
   of R36-A2 `answerid`: small, no resident teacher, no replay-time teacher forwards, and directly aligned
   to closed-book answer behavior. Add per-position top-k only as the next diagnostic if exact sequence CE
   fails because answer surfaces are unstable.
3. **RAG arm:** use **gold-passage concat** as the first RAG upper bound. A retriever over all passages is a
   later product-realism arm; it adds retrieval noise before we know whether the weight-writing bridge
   works.

This moves the project objective forward because it keeps the core contract intact: current-stream text
is transformed into weight updates, old behavior is protected by compact training-time targets, inference
uses one dense model with no article memory, and full joint retraining appears only as an optional oracle
ceiling.

## Why this data-source choice is the right first build

I would not make counterfactual passages the primary yet. The first missing bridge after R36-A2 is not just
"can the model override a known prior"; it is more basic:

> Can ordinary source text produce a teacher/target signal that survives consolidation as closed-book QA?

SQuAD gives real Wikipedia passages, human-written questions, extractive answer spans, and a deterministic
HF source. That is the cleanest way to debug the whole harness without spending the first pod cycle on QA
generation quality. It also avoids a second confound: if a counterfactual edit is incoherent, a failure may
be due to bad editing rather than failed continual learning.

But SQuAD alone has a serious claim problem. Qwen2.5 may already know many facts from the same Wikipedia
pages or even the benchmark distribution. A base EM of zero is not enough to prove ignorance; it can mean
prompt mismatch, answer formatting, ambiguity, or paraphrase failure. Therefore the counterfactual arm
must be built into R38-A from the start.

The right interpretation should be pre-registered:

| outcome | allowed claim |
|---|---|
| SQuAD passes, counterfactual passes | real text can write new/changed short-answer knowledge into weights under sequential consolidation |
| SQuAD passes, counterfactual fails | the harness can adapt to real QA, but base leakage or prior conflict remains unresolved |
| SQuAD fails, counterfactual passes | the teacher construction for natural SQuAD questions is weak; edited explicit facts are easier |
| both fail | R38 has exposed S1 teacher construction as the bottleneck |

If the SQuAD hard-tail screen cannot produce enough questions with low base closed-book score and high
gold-passage RAG score, then switch the primary to counterfactual for this run. Otherwise keep SQuAD as
primary and counterfactual as the mandatory audit.

## Data filters that matter

For SQuAD-hard-tail, I would filter more strictly than "base EM approximately zero":

- run several closed-book prompt templates for the base model;
- keep only examples with normalized EM `0` and very low token-F1 across templates;
- require gold-passage concat RAG to answer correctly, otherwise the item is not an answerability test;
- prefer answer spans of 1-8 tokens: people, organizations, places, dates, numbers, titles, and short noun
  phrases;
- exclude questions whose answer depends on vague pronouns, list aggregation, "why/how" explanation, or
  long free-form generation;
- group by article/title so streams are article-level, not randomly interleaved QA rows.

For the counterfactual arm:

- edit typed spans only: date to date, person to person, location to location, number to number;
- update all local mentions needed for paragraph consistency;
- record the original answer as a lure and report original-answer rate separately;
- ensure the edited answer appears explicitly in the edited passage;
- evaluate with questions whose correct answer is the edited span, not the historical original;
- keep the same closed-book, no-context final evaluation contract.

The counterfactual control is especially relevant to the project goal because it tests whether the new
source text can beat the base prior and become the model's no-memory answer.

## Harness sign-off with required diagnostics

The proposed lifecycle is sound:

1. Start stream `t` from committed model `M_{t-1}`.
2. Train transient scaffold `S_t` on current-stream passage chunks.
3. For the QA arm, add source-grounded QA/span targets from the current stream only.
4. Consolidate into `M_t` using new targets from `S_t`, old compact committed answer targets, and neutral
   base-capability anchors.
5. Store compact targets for committed-correct new QA.
6. Discard `S_t`; final inference uses only `M_t`.

I would add one diagnostic that is not optional: **evaluate `S_t` before consolidation on new-stream
closed-book QA**. Without this, a null result is ambiguous. If `S_t` cannot answer, consolidation is not the
failure; teacher construction is. If `S_t` answers but `M_t` does not, the consolidation loss or target mix
is the failure.

The minimum per-stream report should include:

- base closed-book score before ingestion;
- gold-passage RAG score;
- scaffold `S_t` new QA score;
- post-commit `M_t` new QA score;
- old-stream score immediately after each commit and at the final checkpoint;
- base-capability metric on neutral prompts only;
- answer length distribution and invalid/empty decode rate.

This makes R38 interpretable in the same way R36-A2 was interpretable: naive forgot, compact committed
targets retained, and target-source metadata made the compute/footprint claim clear.

## Compact target choice

Answer-sequence CE is the right first old target. R36-A2 already showed that `committed_dense_argmax`
matched snapshot replay in the synthetic answer-token setting: final all-seen around `0.875`, all-para
around `0.765`, and oldest-stream forgetting `0.000`, while avoiding a resident snapshot teacher and
replay-time teacher forwards. R38 should generalize the target from one token to a short answer sequence
before paying the cost of top-k sketches.

Implementation details I would lock down:

- store the prompt template version with each target;
- store answer token ids including a stop convention, such as newline/EOS after the answer;
- train CE only on answer tokens, not on the question prefix;
- cap answer length and report truncation;
- store targets only for committed-correct answers, and separately report how many new QA become eligible;
- keep aliases in evaluation normalization, but train the first target on one canonical answer sequence.

Top-k sequence sketches are the right fallback if the model often generates acceptable aliases that exact
CE over-penalizes. They should not be the default because they increase footprint and obscure the first
question: whether the cheap R36-A2-style target survives multi-token answers.

## Base anchor and R37 lesson

The neutral-anchor decision is correct and load-bearing. Do not apply base KL to old learned QA prompts.
The current repository history already exposed this risk in R37-A: using base behavior as the target on
learned counterfactual prompts can actively erase the learned answer. In R38, old article QA prompts must
be protected by committed answer targets, not by base logits.

So the anchor split should be explicit in the script:

- `old_qa_targets`: committed answer-sequence CE or later top-k sketches;
- `new_stream_targets`: scaffold/current-source passage and QA targets;
- `base_anchor_targets`: neutral prompts that should remain base-like;
- no overlap between `old_qa_targets` and `base_anchor_targets`.

This also preserves the project objective: old knowledge is retained as old answer behavior in weights,
not suppressed back to the pretrained base distribution.

## Arms

I would keep Claude's arm set, with two naming refinements:

| arm | role |
|---|---|
| `base_no_ingest` | base-knowledge and prompt-format floor |
| `rag_gold_passage` | answerability upper bound with inference memory, not a valid project solution |
| `naive_cpt` | sequential current-stream continued PT, no old compact replay |
| `compact_cpt_only` | transient LM-only scaffold plus compact old answer targets |
| `compact_cpt_qa` | transient LM+QA scaffold plus compact old answer targets |
| `joint_all` optional | full-data oracle ceiling only, never the main method |

The decisive comparison remains `compact_cpt_only` vs `compact_cpt_qa`. If LM-only reading fails and QA
scaffolding works, the bottleneck is not retention but conversion from passage text into answer-function
targets. That would be a useful result and a direct guide for S1.

## Pass/fail criteria

I agree with the proposed bars, with one extra split by data source:

- SQuAD base closed-book should be low after multi-template screening, not merely original-question EM=0.
- Counterfactual base should strongly prefer "not edited answer"; original-answer lure rate should be
  reported.
- Gold-passage RAG should be high enough to prove answerability, roughly `>=70` normalized F1/EM on this
  tiny set.
- `compact_cpt_qa` should beat base by at least `+25` absolute QA points on held-out paraphrases.
- Old-stream final retention should drop no more than `10-15` points from each stream's post-commit score.
- Final all-stream QA should beat `naive_cpt` by at least `+20` points.
- Neutral base capability should stay within about `5%` perplexity or `2-3` MCQA points.
- No final evaluation may use article text, retrieval, stream IDs, task IDs, key banks, or old snapshot
  teachers.

For growth: do not include growth in R38-A. Growth becomes relevant only after fixed-capacity
consolidation either saturates or shows a compute/capability tradeoff that growth can improve. Here the
question is raw-text-to-weights, not capacity expansion.

## Build guidance

Since `s3/` does not exist yet, a new `s3/wikibridge.py` plus a small `s3/__init__.py` is appropriate when
you build. I would make the first script save a reproducibility manifest before training:

- selected articles/passages;
- QA IDs, questions, answers, answer spans;
- source type: `squad_hard` or `counterfactual`;
- base closed-book scores;
- RAG gold-passage scores;
- stream assignment and seed;
- for counterfactuals, original answer and edited answer.

That manifest will be important because the hard-tail selection is itself a learned filter over the base
model. Without saving it, a later result will be hard to audit.

Recommended immediate build order:

1. Implement SQuAD-hard-tail ingestion and the manifest.
2. Implement gold-passage RAG scoring and base closed-book screening.
3. Implement the lifecycle with `base_no_ingest`, `naive_cpt`, `compact_cpt_only`, and `compact_cpt_qa`.
4. Add answer-sequence committed targets and per-stream retention curves.
5. Add the counterfactual builder before the first serious claim run, even if the first smoke uses only
   SQuAD.

Smoke should be tiny and structural: one or two streams, one article each, very few steps, verifying that
the scaffold trains, targets are stored, old CE replays, generation/eval runs, and no final eval receives
the passage.

## Final answer to the three questions

Use **SQuAD-hard-tail primary plus mandatory counterfactual audit**. Make counterfactual primary only if
SQuAD cannot satisfy the base-low/RAG-high filter at usable scale.

Use **answer-sequence CE first**. It is the cheapest faithful extension of R36-A2 and directly tests
closed-book answer behavior. Keep top-k sequence sketches as the first fallback if aliases or surface-form
entropy make CE brittle.

Use **gold-passage concat RAG** first. It is the clean answerability ceiling. A retriever arm should wait
until the weight-writing result exists.

With those constraints, I sign off on building `s3/wikibridge.py`. This is the right next experiment: it
tests the missing real-text bridge while preserving the no-memory inference and no-full-joint-training
contract.
