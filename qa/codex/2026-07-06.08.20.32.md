## Verdict

Yes: the R36-C smoke is a clean and useful negative for **margin-gradient OGD**, but it is not yet a clean negative for OGD as the strong C-arm.

The update-semantics fix worked. With realized-update reprojection, `upd-leak` is effectively gone, so the OGD arm is no longer confounded by AdamW rotating or decaying the update back into Q. The remaining signal is therefore interpretable:

- margin-OGD has `energy-occ=0.052`;
- its effective gradient is almost unchanged, `eff-grad=0.974`;
- newest is not hurt, but oldest forgetting is identical to `naive_fixed`;
- `nswrite` captures much more write-gradient energy, `energy-occ=0.74`, and protects S0 better in the same smoke.

That says the current protected object, `d(gold_margin)/dtheta`, is mostly not the object being moved by the new write loss. So I agree with the design fork: do not spend the 4h pilot treating margin-OGD as the definitive OGD result.

My call:

1. Add `BK_OGD_OBJ=margin|ce_gold`.
2. Run a tiny CE smoke first to verify occupancy and leakage.
3. If CE occupancy is materially above margin, run the 6x40x2 pilot with both `margin` and `ce_gold` OGD arms if the script can express two aliases cleanly. If not, run two deterministic jobs with the same seeds and separate `BK_OUT`s.
4. Do **not** implement literal `KL-to-committed` as a plain gradient column for this pilot. At the committed model, the gradient of `KL(p_committed || p_theta)` is zero. A KL-shaped protected object needs a Fisher/Jacobian basis, which is a different experiment.

## Direct answers

### 1. Is margin the wrong protected object?

For the fair strong OGD test, yes.

The margin result is still worth keeping because it proves something specific: protecting top-2 answer margin directions barely intersects the new-stream write direction in this lifecycle. That is useful evidence against "thin answer-margin gradients are enough."

But I would not interpret `energy-occ=0.052` as "old-answer interference is not first-order-visible from any answer objective." It only shows that the **margin** objective is nearly orthogonal to the CE/KL-shaped new write gradient. Since the write loss in `s2/lifecycle_bakeoff.py` is:

```python
CE(student_logits, teacher_argmax)
+ KL(student_distribution, teacher_distribution)
+ base_anchor_KL
```

the fair old protected object should first match the CE part of that loss. Margin is a ranking objective over gold versus runner-up; CE is a full softmax objective that moves the gold token against the whole distribution. Those are different local directions.

So the correct interpretation is:

- margin-OGD negative: valid and mechanistically informative;
- OGD negative: not established yet;
- next fair test: CE-to-gold OGD.

### 2. CE-to-gold or KL-to-committed?

Use **CE-to-gold** first.

Reasons:

- It is the canonical OGD/GPM protected object: old task loss gradient.
- It is nonzero at commit time for committed-correct facts unless the model is infinitely confident.
- It shares structure with the new write loss's CE-to-teacher-argmax term.
- It is cheap to add to the existing `margin_grad()` path.
- It keeps the pilot focused: if CE-OGD fails with high occupancy and clean update reprojection, the negative is much stronger.

I would implement it by renaming `margin_grad()` to something like `old_obj_grad()` and switching on `BK_OGD_OBJ`:

```python
if obj == "margin":
    old_obj = logits[gold] - masked.max()
elif obj == "ce_gold":
    old_obj = F.cross_entropy(logits[None, :], torch.tensor([gold], device=device))
```

The sign is irrelevant because Q is a subspace. Keep the committed-correct filter and per-vector L2 normalization.

I would **not** implement literal `KL-to-committed-distribution` as:

```python
KL(p_committed.detach() || p_theta)
```

if `p_committed` is taken from the same model at the commit point. At that point `p_theta == p_committed`, so the first-order KL gradient is zero. It will not produce useful Q columns.

If we want the KL-shaped version later, call it what it really is: a local distribution-preservation metric. For example:

- top-k log-prob Jacobian basis;
- Fisher / GGN basis using score vectors weighted by committed probabilities;
- sampled-token score-gradient basis from `p_committed`.

That may be a stronger preservation object, but it is no longer a one-line "KL gradient" OGD arm. It is more like functional preservation via a local Fisher subspace. That belongs after the CE pilot unless CE smoke immediately shows the same near-zero occupancy.

### 3. Run margin and CE together?

Yes, if it is operationally simple. The contrast is valuable.

The strongest pilot table would include:

- `naive_fixed`: unconstrained fixed writer;
- `nswrite`: input-activation null-space writer;
- `ogd_margin`: current thin answer-margin OGD;
- `ogd_ce`: fair canonical OGD;
- `ours`: replay/self-distill reference, clearly labeled as replay training state.

That table lets us separate three claims:

1. Is the protected object aligned with the write gradient? Compare `energy-occ` of margin versus CE.
2. If aligned, does first-order protection actually retain old facts? Compare CE retention versus margin and `nswrite`.
3. If retention improves, does it cost plasticity? Compare newest and base-hop.

If adding arm aliases is annoying, do two runs with identical deterministic stream settings:

```bash
BK_ARMS=naive_fixed,nswrite,ogd,ours BK_OGD_OBJ=margin BK_OUT=ogd_margin_pilot.json ...
BK_ARMS=naive_fixed,nswrite,ogd,ours BK_OGD_OBJ=ce_gold BK_OUT=ogd_ce_pilot.json ...
```

Because streams and scaffolds are seed-deterministic in this script, that is still comparable, though one combined table is cleaner.

## Pilot gate before spending 4h

I would insert a short CE smoke before the full pilot:

```bash
BK_ARMS=naive_fixed,nswrite,ogd,ours \
BK_OGD_OBJ=ce_gold \
LD_ROUNDS=2 LD_PER=20 LD_STEPS=60 LD_SEEDS=1 \
python -m s2.lifecycle_bakeoff
```

Smoke pass criteria:

- `upd-leak` remains near zero, say `<=0.01`, confirming the exact-update reprojection still works.
- `energy-occ` is materially above margin, ideally `>=0.15` and preferably much higher.
- newest is not immediately worse than `naive_fixed` by more than about 0.05 in this tiny smoke.
- `ncol` is not collapsing; if only a handful of committed-correct examples are collected, the basis is under-specified.

If CE `energy-occ` is still around 0.05, then the result is more important than another 4h pilot: even CE old-loss gradients are not seeing the write direction. At that point I would stop C-arm tuning and pivot to the A branch: realized functional preservation / constrained editing, because first-order answer-gradient bases are not intercepting the harmful motion.

If CE `energy-occ` is meaningfully nonzero, run the full pilot.

## Full pilot interpretation

For the 6x40x2 pilot, keep the previous gates:

- `ogd_ce all_seen >= nswrite + 0.05`;
- `ogd_ce oldest_forget <= nswrite - 0.10`;
- newest no worse than `nswrite - 0.05`;
- base-hop drop no worse than about 0.03.

I would add these interpretation rules:

- **CE occupancy high, CE retention fails, newest matched:** strong negative for first-order old CE-gradient protection. The write direction is being intercepted, but retention still fails through nonlinear or higher-order parameter motion.
- **CE occupancy high, retention improves, newest drops:** OGD is too blunt or too rank-heavy. Tune rank/objective before claiming success.
- **CE occupancy high, retention improves, newest matched:** real fixed-size no-replay progress. Then run a longer 12-stream horizon before talking about growth.
- **CE occupancy low like margin:** stronger evidence that this lifecycle's interference is not visible to simple first-order answer-loss gradients. Pivot away from OGD variants.

## Claim hygiene for the project objective

CE-OGD still fits the main project direction if it works:

- new facts are written into the dense model weights;
- inference uses a single dense checkpoint, no external memory;
- old data are not replayed during later writes;
- the method does not rely on full joint retraining.

But it uses answer identity at commit time to build the training-state basis. That should be reported explicitly. In the current `flags`, `ogd` is marked `uses_gold_old=False`; that is defensible only if we mean "no old gold replay during later updates." For paper-quality reporting, I would phrase it as:

> OGD stores only a low-rank training-state basis and uses no inference memory or old replay, but the basis is built from committed old answer identities at stream commit time.

This matters because `nswrite` is cleaner on labels: it protects old activation directions without old answer gradients. If CE-OGD beats `nswrite`, the gain comes with extra commit-time supervision. That is acceptable as a research arm, but it should not be blurred.

## Recommendation

Do not launch the 4h pilot with margin-only OGD.

Add `BK_OGD_OBJ=ce_gold`, smoke it, and then run the full pilot with both margin and CE if practical. Keep KL-to-committed for a later, explicitly Fisher/Jacobian-style preservation experiment, not as the immediate OGD objective.

This moves the project forward cleanly: either CE-OGD becomes a stronger no-replay, no-inference-memory weight-writing method, or it gives a much more defensible negative that tells us first-order answer-loss protection is not enough and the next branch should be functional preservation rather than more margin variants.
