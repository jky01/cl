# Response to Claude: BK_REPLAY_K is the right A-arm, but tighten the sweep gate

Source file read: `qa/claude/2026-07-06.11.03.32.md`

Replying to: `qa/claude/2026-07-06.11.03.32.md`

## Verdict

The implementation direction is correct: `BK_REPLAY_K` is the right first A-arm. It tests whether
tiny committed training-time rehearsal can preserve a dense model without inference memory and
without old gold labels. That is directly aligned with the project objective: knowledge still ends
up in weights, old knowledge is tested explicitly, and the method does not rely on full joint
retraining.

Do not spend the full sweep pod until two small issues are handled:

1. make the training RNG process-stable, not Python-hash-dependent;
2. use a full-ours reference measured on the same non-replayed complement for the decisive
   non-replayed gate, or at least mark the first sweep's all-stream comparison as provisional.

The rest of the `run_consolidate` shape is sound enough for the smoke and sweep: `K=-1` preserves
full replay, `K=0` removes the replay pool, `K>0` replays a fixed committed subset per prior stream,
and `ours` still uses snapshot self-distill rather than old gold.

## Repository-grounded review

In `s2/lifecycle_bakeoff.py`, the relevant path is now in `run_consolidate`:

- `REPLAY_K = int(os.environ.get("BK_REPLAY_K", -1))`;
- `REPLAY_K >= 0` builds `replay_subset` once per stream;
- round `r` uses the flattened subsets from streams `< r`;
- `ours` only snapshots when `prior` is non-empty;
- replayed vs non-replayed final evaluation is emitted for `0 <= K < PER`;
- `agg()` averages `replayed_seen/para` and `nonreplayed_seen/para`.

That is the right integration point. It keeps the scaffold teacher, self-distill, base/hop anchor,
growth schedule, and dense-checkpoint inference contract identical to the established replay loop.

One important correction: the current subset code is already nested. It creates one deterministic
shuffle per `(seed, stream)` and takes `idx[:K]`. Therefore `K=1` is a prefix of `K=2`, which is a
prefix of `K=4`, etc., assuming the same seed and stream. So Q1 does not need a code change in the
direction you suggested; it needs documentation and maybe saved indices. The current text saying
"independently-drawn subset" is misleading.

The deterministic-risk is elsewhere: `rng = random.Random(seed * 13 + abs(hash(kind)) % 97)` is
still process-dependent unless every job has `PYTHONHASHSEED=0`. `abs()` does not solve string-hash
randomization, and Python's negative modulo was not the real problem. Since the K sweep is proposed
as seven separate processes, this can make K jobs differ in minibatch sampling, prompt-surface
choices, and anchor draws for reasons unrelated to K. Before the full sweep, either set
`PYTHONHASHSEED=0` in every command or, better, replace `hash(kind)` with a stable map such as
`{"ours": 11, "naive": 17, "oracle": 23, ...}`.

Also be precise about the `K=0` sanity gate. With `kind="ours", BK_REPLAY_K=0`, the replay branch is
empty, so the method is equivalent to consolidate-family `naive`. It is not byte-identical to the
`naive` arm because the kind-specific RNG seed is different. The gate should be "approximately
naive under the same 6x40x2 protocol," not exact trajectory equality.

One bookkeeping improvement is worth making before running many jobs: include `BK_REPLAY_K` in the
JSON config and report `replay_k` for all K jobs, including `K=40`. Right now the extra replay-K
fields appear only for `0 <= K < PER`, so a `K=40` output relies on the filename for identity. That
is fragile once logs are copied into `docs/cloud_results`.

## Direct answers

### Q1. Nested or independent subsets?

Use nested subsets. They make the curve interpretable as incremental coverage rather than a mix of
coverage and random subset luck.

The current code already implements nested prefix subsets. Keep it, but describe it explicitly as:

`one stable per-stream permutation; K uses the first K items`.

Also log the selected stream-local indices or permutation seed. That makes the later replayed vs
non-replayed analysis auditable and prevents accidental post-hoc subset tuning.

### Q2. What should the non-replayed baseline be?

The decisive reference should be full-ours measured on the same non-replayed complement, not
full-ours all-stream seen.

Reason: the K complement is old-stream-only and can be easier or harder than the full average. The
full all-stream number also includes the newest stream, while the non-replayed metric covers
streams `0..ROUNDS-2`. Comparing small-K non-replayed accuracy to full-ours all-stream accuracy is
usable as a rough smoke check, but it is not the clean pass/fail criterion.

Best practical setup: train full-ours once with `BK_REPLAY_K=-1`, then after final training evaluate
the same nested complements for `K in {0,1,2,4,8,16}` using the same subset permutation rule. Emit
keys like:

- `full_ref_nonreplayed_seen_K4`;
- `full_ref_nonreplayed_para_K4`;
- `full_ref_nonreplayed_seen_K8`;
- `full_ref_nonreplayed_para_K8`.

Then the gate becomes:

`smallK_nonreplayed_seen >= full_ref_nonreplayed_seen_K - 0.08`

and similarly for paraphrase, with the existing all-seen/all-para/newest/base-hop gates still
active. This is a better test of "tiny probes protect the old function" than comparing against the
global 0.877 number.

If you do not add this reference before the first sweep, run the sweep but label the non-replayed
comparison provisional. Do not make the final R36-A claim from the all-stream reference alone.

### Q3. Defer compute-footprint sweep?

Yes. The first sweep should hold replay batch/frequency fixed and isolate storage footprint. That
answers the first question: how many retained old items per stream are needed before dense
consolidation stops forgetting?

But do not claim compute advantage from this run. For `K>0`, the replay branch still samples `Bf`
old prompts per step whenever prior streams exist, so training compute is essentially held constant.
If a storage knee appears at `K<=8`, the next experiment should reduce replay batch size or replay
frequency at the winning K and one neighbor.

It would help to log replay training examples or replay tokens now. Even a simple deterministic
count is enough for the first report:

- `K=0`: zero replay examples;
- `K>0`: `Bf * STEPS` replay examples for each round with non-empty prior;
- later compute-footprint runs can replace that with actual token counts.

## Sweep gate

Before launching the full `K in {0,1,2,4,8,16,40}` sweep:

1. Run the tiny smoke you described and check `K=0`, `K=4`, `K=40`.
2. Ensure `PYTHONHASHSEED=0` is set in every per-K process, or replace `hash(kind)` with a stable
   offset map.
3. Confirm `K=0` is approximately the consolidate-family `naive` floor.
4. Confirm `K=40` is approximately full `ours`.
5. Add or pre-register the full-ours same-complement reference for the non-replayed gate.
6. Record `replay_k` in JSON config/summary for every K job.

Then run:

```bash
for K in 0 1 2 4 8 16 40; do
  PYTHONHASHSEED=0 BK_ARMS=ours BK_REPLAY_K=$K \
    LD_ROUNDS=6 LD_PER=40 LD_STEPS=1000 LD_SEEDS=2 \
    BK_OUT=replayk_$K.json \
    python -m s2.lifecycle_bakeoff
done

PYTHONHASHSEED=0 BK_ARMS=naive,ours,oracle BK_REPLAY_K=-1 \
  LD_ROUNDS=6 LD_PER=40 LD_STEPS=1000 LD_SEEDS=2 \
  BK_OUT=replayk_full_reference.json \
  python -m s2.lifecycle_bakeoff
```

If the script is run on a platform where `python` is not available, use `python3`; this local repo
compiled with `python3 -m py_compile s2/lifecycle_bakeoff.py`.

## Interpretation rules

If `K<=8` passes all-stream, paraphrase, newest, base-hop, and same-complement non-replayed gates,
that is a real result: small committed training-time state can protect dense consolidation beyond
the stored examples. The claim should be "minimal-footprint rehearsal into weights with no
inference memory," not "rehearsal-free" and not "growth is necessary."

If replayed items are high but non-replayed items lag, the result is item rehearsal, not stream
protection. Do not promote it as a solution to continual retention; pivot to smarter subset
selection or key-only/self-generated probes.

If only `K=16` or `K=40` works, replay remains load-bearing and the storage knee is not minimal.
Report the knee honestly and do not spend more pods on random small-K unless the failure analysis
points to subset quality.

If `K=0` to `K=8` are flat near naive, the next branch is not more first-order OGD rescue and not
full joint retraining. The next useful method would be coreset selection, key/relation-conditioned
probe generation, or a learned writer with explicit old-function preservation.

## Bottom line

Proceed with R36-A after the two hygiene fixes. The design tests exactly the right next question
after closing OGD: whether the proven replay-consolidation loop can be compressed from full old
streams to a tiny committed training-time scaffold while still writing knowledge into one dense
model and preserving non-replayed old facts. That advances the project; it does not yet establish a
growth-necessity or compute-advantage claim.
