# Review decision: proceed, with three design constraints locked before the first run

Source reviewed in full: `qa/claude/2026-07-17.10.16.07.md`.

This is ready to move from generator/preregistration into the model and phased harness. The core move is
right: the LM port should not merely ask whether a transformer can fit another task. It should ask whether
multi-environment evidence causes an executable rule to enter the weights, whether that rule composes with
old rules, and whether it survives later interference without inference-time memory or joint retraining.

I would make the following decisions now.

## 1. Build one shared transformer with dormant growth hooks; run the monolith first

Do not build a throwaway plain model and design the growth architecture only after seeing its failures. Build
one harness and one trunk containing disabled residual extension points from the start. The initial
plain-shared arm keeps every extension disabled. The growth arm may activate them at the registered phase
boundary. This preserves the useful ordering—first establish identifiability and retention in the
monolith—without making the later growth comparison a post-hoc architecture change.

A small pre-LN decoder is appropriate for the RTX 2070. I would fix one configuration rather than sweep
architecture: roughly 4 layers, width 192, 6 heads, FFN width 768, and enough context for the complete
length-40 input/output serialization. More important than the exact width are these constraints:

- Use relative, rotary, or another position treatment that is defined beyond training lengths. Learned
  absolute positions 13–40 would be untrained, so failure at length 16–40 would confound failure to acquire
  the recurrence with a positional-embedding failure.
- Freeze the tokenization and serialization before training. `RESET`, values, operator separators, input
  boundaries, and output boundaries should have an unambiguous representation. Operator-name/permutation
  interventions should be generated deliberately, not emerge from tokenizer accidents.
- Autoregressive output serialization must permit the intended state computation. Report exact-match by
  sequence and token accuracy, but make exact-match and reset-distance-stratified accuracy decisive.
- No environment, phase, or external task ID may select a module at inference. If a growth branch is routed,
  routing must be inferred from the ordinary instruction/input tokens and must work for held-out
  compositions.

For growth, a residual bottleneck/FFN branch is enough for the first test. Only one branch should be active
per layer/token if the claim is matched active inference compute. Report separately: total stored parameters,
active parameters, inference FLOPs, training FLOPs, and phase-specific wall time. Include both a static
capacity-matched sparse control and an active-compute-matched dense control; otherwise apparent “growth
necessity” may only mean “more total parameters.” The joint arm remains a ceiling, never a candidate method.

So my answer to question 1 is: **plain-shared first in the experiment order, but growth-compatible in the
harness from day one**.

## 2. Make multi-environment ERM primary; use group-DRO as the registered objective intervention

Start with plain ERM over the sufficient multi-environment mixture. That is the cleanest test of whether the
intervention diversity itself removes the shortcut equivalence class. Then run a worst-environment objective
using the same data and budgets. I would use the precise term **group-DRO** for that arm; worst-environment
optimization and IRM are not interchangeable mechanisms.

The minimum causal comparison is:

1. insufficient environments + ERM;
2. sufficient environments + ERM;
3. sufficient environments + group-DRO.

If budget permits, add insufficient environments + group-DRO. That fourth cell reveals whether the objective
can compensate for missing identifiability evidence, which in principle it should not. Rename the existing
“flexible-no-invariance” arm so its environment set and objective are explicit; otherwise environment
sufficiency and optimization pressure can be accidentally conflated.

I would reserve “rule induced” or “discovered” for a model receiving only input/output supervision (plus
training-time environment groups where applicable), with no recurrence-state labels, program trace, or
correct operator module. OOD length accuracy alone is not enough to establish discovery. Require the same
model checkpoint to pass:

- unseen lengths;
- reset-position and distance-since-reset strata;
- held-out combinations of familiar interventions;
- the preregistered unseen nuisance;
- both old→new and new→old compositions.

This triangulates executable recurrence rather than a single lucky extrapolation. The minimal-environment
equivalence-class analysis is especially valuable: the empirical result should be compared directly with
the generator-level identifiability prediction.

So my answer to question 2 is: **multi-env ERM first, group-DRO second, and no IRM penalty in the initial
compute budget unless group-DRO leaves a specific unresolved failure**.

## 3. Treat model-generated self-distillation as synthetic replay, not as the primary no-replay result

Self-distillation over generated old-task inputs is scientifically legitimate under “no stored raw replay,”
and the teacher can be discarded before inference. But it is still functional rehearsal: the old support is
reconstructed, labeled by a phase-boundary teacher, and revisited during later training. Calling it simply
“consolidation without replay” would make the central claim too easy, especially if the known grammar can
generate unlimited perfect old-task inputs.

Use it as an explicit **synthetic-replay comparator** and count its teacher storage, generation cost, old-task
queries, and training FLOPs. For the primary non-rehearsal consolidation arm, store only a bounded
parameter-space summary at the phase boundary—initially a diagonal importance estimate and reference
weights is sufficient—and prohibit old input generation and old-task forward queries during phase 3. The
protected-module/growth arm provides the stronger parameter-isolation alternative. If the bounded-summary
monolith fails while growth retains and still composes, that is informative evidence for growth necessity,
not a reason to hide the failure with unlimited pseudo-replay.

The hierarchy of evidence should therefore be:

- strongest: no old examples, no generated old examples, no old-task queries, no frozen teacher during the
  later phase;
- useful secondary result: bounded synthetic replay with all storage and compute disclosed;
- upper reference only: joint training.

So my answer to question 3 is: **acceptable as a named comparator, but not as the primary mechanism behind a
“no replay” or compute-advantage claim**.

## Two final preregistration checks

Before spending the first full-run compute, freeze the random seeds, checkpoint-selection rule, per-arm
hyperparameter budget, stopping rule, and what happens when an acquisition gate fails. In particular, do not
let phase-3 retention results select the phase-2 checkpoint; selection must use phase-2 information only.

Also separate two conclusions that are easy to blur:

- A monolith that learns and retains `csum_reset` demonstrates knowledge-into-weights and continual
  retention, but does not demonstrate that growth is necessary.
- A growth arm that retains by isolating modules demonstrates retention, but does not demonstrate integrated
  knowledge unless the held-out cross-compositions succeed without an external router or memory.

With those constraints recorded, the transformer and phased harness should be built. The first cheap gate
should be phase 1→2 acquisition on insufficient-ERM, sufficient-ERM, and sufficient-group-DRO. Only models
that cross the preregistered ID, length-OOD, reset-stratified, and intervention-combination thresholds should
proceed into the expensive phase-3 retention comparison. This keeps the experiment aimed at the real target:
new algorithmic knowledge entering weights, remaining usable after interference, and composing with prior
knowledge under a path that can eventually justify growth by capability and compute—not merely by adding
parameters.
